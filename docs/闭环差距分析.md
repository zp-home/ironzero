## 0. 结论速览

**一句话：协议链路已经"通"，学习闭环还没有"闭合"。**

- 真机 `reset → obs → step → reward → checkpoint → 推理回放` 端到端能跑，`runs/` 里有真实对局产物；
- 但修复前的训练/评估**拿不到可信的终局信号**（bench4 引擎已判 Game Over 仍记 timeout；bench3 的 240 个决策全部记为"1 步胜"），
- 观测/动作契约是**按 mock 的 8v8 写死的**，真机 22v25 只能看/打前 8 个实体，
- 评估只有 1 局、没有置信区间，checkpoint 保存的是"最后一轮"而不是"最好一轮"，
- 推理脚本默认关闭迷雾、HP 分母口径与训练不同，**复现不了训练观测契约**。

修复后（本会话并行修复，未验证）真机侧已经出现**真实 `defeat` 终局**（`runs/platform/rwpp-ppo-ppo-07de6fc6`，20 updates / 75.7s / final eval loss=1.0 / 125 decisions），说明"胜负信号"这一环形式上通了；但 25v25 固定地图、≥20 局确定性评估、60% 胜率**都还没有任何可审计证据**。

### 0.2 关键结论 Top 5

1. **修复前的"胜利"是假的、修复前的"超时"是漏判的**：bench3 的 240 个决策 = 240 个"1 步胜局"（`episodes=40/update × 6`，全部 `win_rate=1.0`、`mean_return=1.0`）；bench4 的 6 个 update `episodes=0`，而同一时段的真机日志明确出现 `Game Over! Team 1 wins!`（引擎已判负）却仍以 180 决策 timeout 收尾。
2. **观测/动作契约按 8v8 mock 写死，真机 22v25 严重失真**：`flat_obs_dim=364`（12 + 2×8×10 + 3×8×8），只编码实体列表前 8 个；22 个己方单位的总 HP 除以 `units_per_team×unit_hp=1680` 得到 2.75（超出 [0,1] 设计范围）；25 个敌人只有前 8 个进入目标掩码；真机不输出 `group_id`，group 掩码实际只剩 group0+广播。
3. **PPO 采样结构与单局长度不匹配**：默认 `rollout_steps=20`（envs=2 共 40 决策/update），而 22v25 一局要 125–360 个决策；于是 `episodes=0` 成为常态（bench4 全部 0；修复后真机 20 updates/800 决策只有 2 个终局）。这不是"训练慢"，是**大多数 update 里没有 `terminated` 样本**。
4. **验收证据链不成立**：评估只有 1 局、无置信区间、评估种子没有真正注入游戏（`reset(seed)` 只改 episode id，不传给引擎；日志里 `global Seed: 837538128` 不可控）；保存的是最后一轮 checkpoint，`checkpoint_latest.pt` 与 `checkpoint.pt` 内容相同、没有 best 追踪；推理默认 `vision=0`、HP 分母用"当前存活总血量"，与训练 eval 的"开局总血量分母"不可比。（工作树已补 Wilson/逐局报告/best/推理参数透传，但 **HP 分母与确定性种子仍未修**，见 §0.1 与 §3。）
5. **25v25 的三个关键前置风险已定位**：① 无建筑地图会被引擎 `Team.updateDefeatCheck` 立即标 `defeated`（必须先有 annihilation 模式与开图保护期）；② 地图预置的 AI 单位带 `aiLimitedUse=true`，不解除就**不参战**（`--unlock-ai` 必须做）；③ 地形不进观测时，"考虑地形"的要求无法从策略层面达成（需要 terrain 通道 + 目标点通行性约束）。**并行修复已落地并有 300 tick 冒烟（`verify.json`/`_smoke25`），但 AI 是否真的参战、Python 25v25 端到端仍未验证。**

> **审计纠偏（请 Lead/环境负责人注意）**：任务描述中的"雾参照 hp 失真"在**训练/评估路径上不成立**。当前 `RwppDuelEnv.reset` 用**全量** `self.state` 计算 `own_max_ref/enemy_max_ref`（HEAD `rwpp_env.py` 的 `reset`，L426–431；工作树进一步抽成 `army_hp_reference`，L519–522），雾只作用于 `obs_state`（L421、L619–625），因此 eval 的 HP 分数不会因"开局看不见敌人"被压成 1。真正失真在**推理/展示路径**：`scripts/play_rwpp_policy.py` 的 `state_to_frame` 调 `hp_fractions(state)` 未传参照（HEAD L63 / 工作树 L64），以及 summary 同样未传（HEAD L217 / 工作树 L246–252）。**不要**把 reset 的参照改成"可见敌人求和"，否则会把当前正确实现改坏；若要修，应修推理脚本并加"参照来自 reset 全量观测"的单测。

## 2. 闭环逐环节判定

### 2.1 reset / 进程生命周期

**结论：可用，但没有"固定种子"，且进程/端口生命周期有实测故障。**

- `RwppDuelEnv.reset()`（HEAD `rwpp_env.py` L408–461）：先 `_shutdown_game()` 再 `_start_game()`，等待首帧 obs（`start_timeout 90s + obs_timeout 60s`）。真机不可原地 reset，每局重启 JVM 是设计选择（L14–17 注释）。
- **种子没有传给游戏**：`reset(seed=...)` 只设置 `self.seed` 与 `episode_id`（L409–412）；启动参数只有 `--bridge-port/--ticks/--map/--frame-ms`（L137–149）；Java `parseArguments` 同样没有 seed 参数（L146–161）。因此"固定种子评估"目前**只在 Python 侧（torch/numpy）成立**，引擎侧不成立。
  - 旁证：真机日志打印 `global Seed: 837538128`（`runs/_rwpp_ppo/game-5200-44250.log`），该种子既不可指定也不可记录进产物。
- **端口冲突有实测**：4 份日志出现 `java.net.BindException: Address already in use: bind`（`runs/_rwpp_ppo/game-5140-39113.log` L116、`game-5141-39114.log` L116、`game-5140-71741.log` L116、`game-5141-71742.log` L116，均为 2026-11-07 13:47/13:51），另有 1 次 accept 超时。这两组正是 5140/5141 两个训练 env 同时启动、上一轮进程尚未释放端口的情形。
- `_shutdown_game()`（L754–777）只对 `subprocess.Popen` 句柄发 `shutdown` + `wait(15s)` 再 `kill()`；`rwpp-server.bat` 会再派生 Java 子进程，Windows 下杀 bat 不保证杀进程树，存在"端口仍被占用"的隐患（与上面的 BindException 现象一致，但是否同因需在修复版验证）。

**本次修复：未涉及**（Lead/环境负责人应验证：训练结束 `tasklist` 无残留 `java.exe`；连续两轮训练不出现 BindException）。

### 2.2 action 注入与组语义

**结论：协议可用，但"4 组控制"的动作空间在真机上被掩码废掉 3/4。**

- 动作头 `[kind(5), group(5), x(8), y(8), target(9)]`（`micro_config.py` L74–82），Java `applyStep` 支持 `move_group/attack_move/attack_target/stop/hold` 五类（Java L363–418）；`unit_group` 0–3 按 `unit.id % 4` 选组，4 为广播（Java L420–437、L443–468）。
- **但真机 bridge 的实体 JSON 没有 `group_id`**（HEAD Java `entityJson` L244–256，只有 entity_id/team/x/y/hp/max_hp/is_building 等）；Python `build_masks` 从 `unit.get("group_id", 0)` 取组（HEAD `observations.py` L165–192），结果所有单位都算 group 0 → `group_mask[1:4]=False`、只留 group0 与广播槽（L176–179）。
- 影响：真机上策略**学不到"分兵/多方向包抄"**；同时训练分布里从未出现 group 1–3 的动作，推理时这三个头也永远不可选。
- **雾下 target 索引错位（本审计新发现）**：`step` 里 `decode_action(action, self.state, ...)` 用的是**全量** state（HEAD `rwpp_env.py` L463–472），而 `masks` 是用 `self.obs_state`（雾过滤后）构建的（L511、L423）。`attack_target` 用 `enemies[target_index]` 取目标（L250–263），于是"掩码里第 i 个可见敌人"会被解码成"全量列表第 i 个敌人"——有雾时策略会**攻击看不见的敌人**（迷雾泄漏 + 打错目标）。
- 本次修复（工作树，未验证）：Java 的 `entityJson` 已输出 `"group_id": unit.id % 4`（工作树 L308）；Python `build_masks` 增加 `group_ids_known` 分支，真机无 group_id 时 4 组全部可选（工作树 `observations.py` L306–316）。**雾下索引问题也已改**：工作树 `rwpp_env.py` L568–570 `decode_action(action, self.obs_state, ...)`，注释明确"target slots index the visible enemy list"，并新增 `tests/test_rwpp_25v25.py` 覆盖；仍需真机/雾场景复验。

### 2.3 observation：契约、截断与归一化

**结论：修复前的 364 维观测是"8v8 mock 契约"，对真机 22v25 同时存在截断、归一化越界、槽位不稳定、无地形四个问题。**

- 维度公式（HEAD `micro_config.py` L84–88）：
  `flat_obs_dim = global_dim(12) + 2×max_entities×entity_features + map_channels×map_grid²`
  = `12 + 2×8×10 + 3×8×8` = **364**；`runs/rwpp_ppo_bench3/checkpoint.pt` 的 trunk 输入确实是 364（本次读 checkpoint 元数据确认）。
- **观测截断**：`encode_observation` 只写前 `max_entities=8` 个己方/敌方（HEAD `observations.py` L61–82）；真机 Artillery 是 22 己方 + 25 敌方（`docs/平台搭建方案.md` L320；日志 `world ready: units=47` 共 380 次）。策略只看到 ≤8 个己方单位、≤8 个敌人，`target_mask` 也只开前 8 个目标槽（L182–185，`target_slots=9` 中 8 个敌人槽）。
- **归一化越界**：`total_hp = units_per_team × unit_hp = 8×210 = 1680`（L35），再算 `own_hp / total_hp`、`enemy_hp / total_hp`（L43–46），且未 clip。22 个满血单位 → **2.75**；25 个 → **3.125**。全局观测里本应 ~1.0 的"兵力比例"实际是 2–3 倍，属于契约级错误。
- **槽位不稳定/无身份**：实体按 `Unit.unitList` 顺序写入固定槽，死亡后槽位左移，实体特征里没有 entity_id/team 字段（L100–142），策略无法跟踪"同一个单位"。
- **无地形观测**：只有 3 个通道（己方占格、敌方占格、差值，L85–94），没有 blocked/可通行先验；目标 x/y 掩码恒为 True（L180–181），动作可把坦克派进水里/悬崖；Java 侧也不做目标点可通行校验（`applyStep` 只下发 waypoint）。
- 本次修复（工作树，未验证）：`MicroDuelConfig` 增加 `terrain_path` 与第 4 通道约定（工作树 L65–69、L99 `terrain_channel`），`observations.py` 增加 `terrain_passable_channel`（工作树 L100–142）；`RwppGameConfig` 增加 `units_per_team/max_entities/target_slots/terrain_path`（工作树 L81–88）；`train_rwpp.py` 已接线 `--units-per-team/--max-entities/--target-slots/--terrain/--win-mode/--unlock-ai/--save-best`（工作树 L57–68、L93–98），并新增 `tests/test_rwpp_25v25.py`（25v25 观测/动作/地形/CI/best 共 26 个用例）。**注意**：`observations.py` 的 `total_hp` 仍是 `units_per_team × unit_hp`（工作树 L42）——25v25 时 `units_per_team=25` 恰好正确，但 legacy 22v25（仍用 8）依旧会得到 2.75，且没有 clip；旧场景与 25v25 的数字不可混用。

### 2.4 reward

**结论：分项齐全，但 90% 的 update 里只有 dense shaping，终局 ±1 极少出现。**

- 分项（HEAD `rwpp_env.py` L531–546）：`potential`（0.5×ΔHP 势差）、`engagement`（2.0×接近敌军）、`strategy`（战略层目标点）、`kills`、`losses`、`invalid`、`idle`、`terminal`、`timeout`（恒 0）。
- 修复后真机 run 的 reward 明细可见（`runs/platform/rwpp-ppo-ppo-07de6fc6/metrics.json` update 13：`losses=-2.75`、`idle=-1.12`；update 17：`terminal=-1.0`、`losses=-4.0`），说明分项已真实生效。
- **问题**：`timeout` 项恒 0（L545），超时局没有任何终局惩罚；配合 `episodes=0`，绝大多数 rollout 的 return 只是 shaping 噪声。没有 curriculum/对手课程（`opponent` 只有 scripted，Java 侧 AI 难度未参数化）。
- 另：`potential/engagement` 用 `self.state`（全量），雾下奖励"知道"看不见的敌人。这不污染策略输入，但与 `训练推理与演示架构.md` §10.3 的迷雾审计口径需要在文档里讲清楚（奖励可用全量、策略输入不可以）。

### 2.5 termination：修复前"假胜 + 漏判"的双重缺陷

**结论：修复前训练数据里的 `terminated` 要么是伪造的（bench3），要么根本不存在（bench4）。**

**证据 A：bench4 —— 引擎已判负，环境仍记 timeout（漏判）。**
- `runs/rwpp_ppo_bench4/metrics.json`：6 个 update 全部 `episodes=0`；final_eval = 1 局、`timeout_rate=1.0`、`mean_decisions=180`、`mean_own_hp_frac=0.1839`（L94–119）。
- 同一时段的真机日志：`runs/_rwpp_ppo/game-5200-90934.log` L152–153 出现
  `Player was defeated (Team: A)` + `Game Over! Team 1 wins!`，而桥接继续跑到 `bridge finished frames=1800 tick=1800`（末行），没有 `result=` 字段。
- 根因（A 级）：HEAD 之前 Java `sendObservation` 不写 `result`（`docs/平台搭建方案.md` §5.10 明确"此前写死 terminated=false / sendDone result=timeout"），Python 只能按"敌方可见全灭"回退判胜（HEAD `rwpp_env.py` L561–571 的 fallback 分支），敌人没全灭就只能是 timeout。

**证据 B：bench3 —— 240 个决策 = 240 个"1 步胜局"（假胜）。**

### 2.6 training loop：采样长度与单局长度不匹配

**结论：闭环"形式通"之后，最大的学习瓶颈是 `episodes=0`。**

- 默认：`train_rwpp.py` updates=4、envs=2、`rollout_steps=8`（L32–34）；平台默认 20（`web/backend/app.py` L104）。一次 update 的决策数 = `rollout_steps × num_envs`（如 20×2=40）。
- 单局决策数 = `episode_ticks / DECISION_TICKS = 3600/10 = 360`，而实际分出胜负的局在 125–180 决策、超时局 360 决策（见 §2.5 evidence C：final eval 125 decisions；bench4 eval 180；`_verify_ppo` 120）。
- 因此 **40 决策/update ≪ 125–360 决策/局** → 大多数 update 没有 episode 结束（bench4 全部 6 个 update `episodes=0`；bench3 因假胜每步结束，属另一个极端）。修复后真机 20 updates × 40 = 800 决策只完成 **2** 个 episode（`07de6fc6`），再次证明不是偶发。
- 影响：GAE 在 update 边界靠 bootstrap，`terminal ±1` 极少出现；value 学的是 shaping 的局部漂移，策略主要被 `engagement/idle` 牵着走，很难学到"打赢"。
- 修复建议（未在本次修复计划内，需 Lead 决策）：`rollout_steps ≥ ceil(单局决策数 × 1.2)`（如 3600 tick 局至少 450，即 envs=2 时 ≥900 决策/update），或缩短 `episode_ticks` 到与 rollout 匹配的小场景；同时保留跨 update 的 episode 连续（当前 `persistent=True` 已做，`vec_rwpp.py` L72–86）。
- 其他小样本问题：`minibatch_size=64` > 单 update 样本数（40），等于全量单 batch；`epochs=4` 每 update 只有 4 次梯度更新；无 curriculum、无自适应 LR、无 KL 早停。

### 2.8 checkpoint 与模型加载

**结论：能存能读，但不满足"可晋级、可追溯、可恢复"的要求。**

## 6. 最终验收判据建议（专业版）

> 目标不是"跑出一局胜利"，而是"在预先声明的评估协议下，用统计上站得住脚的证据证明 win_rate ≥ 60%"。

### 6.1 评估协议（必须固定并写进报告）

| 项 | 建议 |
|---|---|
| 评估局数 | **N ≥ 20**（最低）；建议 N=30–50，若要做"显著 > 50%"的统计声明则需要 N≥91（见 6.2） |
| 策略模式 | 确定性（argmax），禁用采样/熵噪声（`deterministic=True`） |
| 环境 | 固定地图（IronZero25）、固定 tick 上限（3600）、固定 `vision_radius`（与训练一致） |
| 对手 | 固定 AI（`--unlock-ai`，basicAI）+ 可额外报"AI 未解锁"对照，禁止中途换难度 |
| 种子 | 每局记录 `run_seed/episode_seed`；由于引擎 seed 不可控，**必须报告"同 seed 重跑结果可能不同"**，用多局统计而非单局复现 |
| 进程隔离 | 每局独立 `rwpp-server` 进程；评估端口段独立（如 5200+）；评估与训练不同时跑（409 互斥） |
| 数据落盘 | `runs/eval-<stamp>/eval_report.json`：逐局 `{episode, seed, result, ticks, decisions, own_hp_frac, enemy_hp_frac, return, replay_path}` + 汇总 + Wilson CI + 二项检验 p 值 |

### 6.2 主指标与统计判定

主指标：`win_rate = victories / N`，同时报 `loss_rate`、`timeout_rate`、`mean_own_hp_frac`、`mean_enemy_hp_frac`、`mean_decisions`、`mean_ticks`。

**Wilson 95% 置信区间**（推荐，小样本比 Wald 稳）：

```
p̂ = k/N,  z = 1.96
center = (p̂ + z²/(2N)) / (1 + z²/N)
half   = z·sqrt(p̂(1-p̂)/N + z²/(4N²)) / (1 + z²/N)
CI = [center-half, center+half]
```

**二项检验**（单侧）：
`p_value = P(X ≥ k | n=N, p0)`，对"优于随机（50%）"用 `p0=0.5`；对"达到 60%"用 `p0=0.6`。

本审计实测的一组关键数字（供写报告时引用，避免拍脑袋）：

| 观测 | win_rate | Wilson 95% CI | 单侧 p vs 0.5 | 单侧 p vs 0.6 |
|---|---|---|---|---|
| N=20, k=12 | 60% | [38.7%, 78.1%] | 0.252 | 0.596 |
| N=20, k=15 | 75% | [53.1%, 88.8%] | 0.021 | 0.126 |
| N=30, k=20 | 66.7% | [48.8%, 80.8%] | 0.049 | 0.292 |
| N=50, k=33 | 66% | [52.2%, 77.6%] | 0.016 | 0.237 |
| N=100, k=60 | 60% | [50.2%, 69.1%] | 0.028 | 0.543 |

**结论（务必写清楚）**：
- N=20、赢 12 局（60%）时，Wilson 下限只有 38.7%，**不能宣称"胜率显著高于 50%"**；
- 要在 60% 观测值上让 Wilson 下限 > 50%，需要 **N≈91**（60/100 时下限 50.2%）；观测 65% 时 N≈41 即可；
- 若验收只要求"点估计 ≥60% 且 N≥20"，可以执行，但报告必须注明"CI 下限 <60%、未做显著性声明"，否则就是过度解读。

**建议的门禁写法（二选一，提前写死）**：
- 保守门禁：`win_rate ≥ 60%` **且** `Wilson 下限 > 50%`（需要 N≥91 或更高胜率；N=30 需 ≥21 胜、N=50 需 ≥32 胜、N=100 需 ≥60 胜，见下表）。
- 务实门禁：`win_rate ≥ 60%` **且** 单侧二项检验 vs 0.5 的 p<0.05（N=20 需 ≥15 胜；N=30 需 ≥20 胜；N=50 需 ≥32 胜），并在报告里同时给出 Wilson CI。

| N | Wilson 下限 >0.5 所需最少胜局 | 折合胜率 |
|---|---|---|
| 20 | 15 | 75% |
| 25 | 18 | 72% |
| 30 | 21 | 70% |
| 40 | 27 | 68% |
| 50 | 32 | 64% |
| 64 | 40 | 62% |
| 100 | 60 | 60% |

### 6.3 过程/鲁棒性指标（必须同时达标）

| 指标 | 建议阈值 | 说明 |
|---|---|---|
| timeout_rate | ≤ 10%（并在报告里单列） | timeout 不是胜利；评估 horizon 要足够（≥3600 tick） |
| mean_own_hp_frac | 胜利局 ≥ 0.5；总体 ≥ 0.5 | 胜得越"残"越说明是地形/运气 |
| mean_enemy_hp_frac | 胜利局 ≤ 0.2 | 与 own_hp 联合判断"是否真打崩对手" |
| mean_decisions | 60–360（合理区间） | <2 决策的"胜局"直接判为 bug（bench3 教训） |
| timeout/异常短局 | 0 次 | 任何 `frames<30` 或 `decisions<2` 的终局必须人工复核 |
| 非法动作率 / rejected | ≤ 5% | 来自 receipt `accepted/rejected` |
| bridge_error_rate | 0（或 <1%） | 断连、BindException、无首帧 |
| 决策延迟 p95 | 记录即可（Python 侧） | 训练 lockstep，推理 realtime，不可混用 |

### 6.4 回放复现

- 每局必须产出 `ironzero.replay/1`：`meta.result/terminated/truncated` 与 `done` 事件一致；`frames` 覆盖到终局帧；`result` 不允许被脚本覆盖成 timeout（`docs/平台搭建方案.md` §5.10 的回归点）。
- 抽检 3 局：回放末帧 `result` == eval_report 的 `result`；末帧 tick == `mean_ticks` 对应单局 tick。
- 同 checkpoint + 同地图 + 同 `episode_ticks` 重跑：允许结果不同（引擎 seed 不可控），但必须**同一代码版本、同一配置**；建议在报告里明确"确定性策略、非确定性环境"的边界，并给出 2 次重跑的 win_rate 差值作为环境噪声估计。
