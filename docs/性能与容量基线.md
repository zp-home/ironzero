# 性能与容量基线

> 文档状态：v0.1 基线
> 作者：周培智
> 适用范围：本机 RWPP Headless 训练、评估、推理和演示
> 配套文档：[训练、推理与演示架构](../训练推理与演示架构.md)

本文档用于回答三个问题：

1. 单局环境能不能跑得足够快。
2. 一台机器能并行跑多少个环境。
3. 模型推理和 Bridge 是否满足训练与实时演示的时限。

在完成实测前，本文档中的预算都是“初始目标”，不是已实现指标。

---

## 1. 性能定义

### 1.1 基本单位

```text
tick
  游戏模拟的最小时间单位。

decision
  模型获得一次观测并输出一次动作。

step
  从一次决策到下一次决策的环境推进。

episode
  从 reset 到 terminated/truncated 的一局。

realtime_factor
  游戏模拟时间 / 墙钟时间。
```

### 1.2 关键公式

单环境训练速度：

```text
steps_per_second =
  decision_interval_ticks / tick_wall_time_seconds
```

多环境总速度：

```text
total_steps_per_second =
  num_envs × steps_per_second
```

每小时样本数：

```text
samples_per_hour =
  total_steps_per_second × 3600
```

容量上限：

```text
N_max = min(
  floor(available_cpu_cores / cpu_cores_per_env),
  floor(available_ram_gb / ram_gb_per_env),
  floor(available_ports / ports_per_env),
  floor(gpu_capacity / gpu_share_per_env)
)
```

实际并行数应取 `N_max` 和训练收益曲线的较小值，不要为了追求环境数量导致推理排队。

## 4. Benchmark 场景

### 4.1 B0：空环境

```text
RWPP 启动
加载固定地图
不加载模型
只推进 tick
```

目的：测游戏引擎和进程基线。

### 4.2 B1：随机合法策略

```text
固定场景
随机合法动作
动作掩码开启
```

目的：测 Bridge 和动作回执开销。

### 4.3 B2：小模型推理

```text
固定观察
小型 MLP/Transformer
单条推理
```

目的：测推理延迟，不让训练采样掩盖模型开销。

### 4.4 B3：训练采样

```text
真实 PPO 推理
rollout 收集
日志和录像开启
```

目的：测端到端训练吞吐。

### 4.5 B4：多实例

```text
1、2、4、8、16 实例
相同场景
相同模型
```

目的：找容量曲线和资源瓶颈。

## 5. 初始性能预算

以下是 micro 场景的初始目标，最终数值以实测为准：

| 指标 | 初始目标 |
|---|---|
| Bridge RTT P95 | ≤ 20 ms |
| 观测编码 P95 | ≤ 10 ms |
| 观测解码 P95 | ≤ 10 ms |
| 小型策略推理 P95 | ≤ 50 ms |
| 单实例启动 P95 | ≤ 30 s |
| reset P95 | ≤ 30 s |
| 动作超时率 | ≤ 0.1% |
| Bridge 错误率 | ≤ 0.1% |
| 100 局环境崩溃率 | 0 |
| 4 实例连续运行 | ≥ 30 分钟 |

如果超过预算，先定位是游戏引擎、Bridge、序列化、推理还是磁盘 I/O，不能直接通过增加环境数掩盖问题。

## 6. 容量规划

### 6.1 第一轮

```text
1 个 Trainer
1 个 Policy Service
4 个 RWPP 实例
4 个 Bridge 连接
```

记录：

- 总 CPU。
- 峰值内存。
- 每实例内存。
- 每秒决策数。
- 每秒样本数。

### 6.2 扩展顺序

```text
1 → 2 → 4 → 8 → 16
```

每次只改变实例数，其他条件不变。

### 6.3 停止扩展的条件

出现以下任一情况时停止增加实例：

- 总吞吐不再增长。
- P95 推理延迟超过预算。
- 单实例内存持续增长。
- 端口或进程清理开始失败。
- 训练更新 GPU 利用率明显下降。
- 错误率超过预算。
- 系统开始使用交换分区。

## 7. 性能瓶颈定位顺序

按以下顺序排查：

1. 游戏进程是否正常推进 tick。
2. 是否在等待模型。
3. 是否在等待 Bridge。
4. 是否在等待磁盘写入。
5. 是否在序列化超大观测。
6. 是否在进行低效实体遍历。
7. 是否在 GPU 和 CPU 之间频繁拷贝。
8. 是否发生 Python GIL 竞争。
9. 是否发生端口或进程争用。
10. 是否发生内存回收抖动。

不要一开始就优化神经网络结构。RTS 环境通常是 Bridge、序列化和进程管理先成为瓶颈。

---

## 8. 优化顺序

### 8.1 第一优先级

- 减少不必要的进程启动。
- 缩短地图加载时间。
- 避免每个 tick 发送完整状态。
- 使用稀疏观测和增量更新。
- 限制日志和录像写入频率。
- 避免同步等待推理。

### 8.2 第二优先级

- 实体列表使用数组或张量批处理。
- 避免重复 JSON 编解码。
- 对稳定字段使用固定 schema。
- 使用二进制协议或压缩传输。
- 减少跨进程数据复制。
- 对模型输入做预分配和复用。

### 8.3 第三优先级

- 引入批推理。
- 使用 ONNX Runtime。
- 使用更小的实体编码器。
- 使用局部地图裁剪。
- 使用异步环境采样。

只有在前面指标明确后，才进入第三优先级。

## 10. 性能验收门禁

### 10.1 训练前

- [ ] 单实例可以稳定推进 tick。
- [ ] Bridge RTT 在预算内。
- [ ] reset 不泄漏进程和端口。
- [ ] 观测大小在可控范围内。
- [ ] 动作回执不增加明显延迟。

### 10.2 训练中

- [ ] 4 实例连续运行 30 分钟。
- [ ] 无内存持续增长。
- [ ] 无进程数持续增长。
- [ ] 无端口耗尽。
- [ ] 采样速度满足训练计划。

### 10.3 演示前

- [ ] realtime 模式不会等待模型。
- [ ] 推理 P95 满足截止 tick。
- [ ] 超时兜底不产生新的错误。
- [ ] 4 实例演示不会拖慢观察客户端。

## 12. 一句话总结

**先测单实例，再谈并行；先测 Bridge 和 reset，再谈模型优化；所有吞吐结论都必须绑定硬件、版本、场景和原始数据。**
