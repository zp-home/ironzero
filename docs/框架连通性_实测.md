## 3. 关键一跳：真机服务如何起 trainer、trainer 如何起 JVM

### 3.1 服务 → trainer

- 入口 `scripts/rwpp_service/launch.py::StartMixin._start_ppo()`：先 `resolve_preset()` 收敛 arena 参数，再 `resolve_init_state()` 收敛 checkpoint，再跑 `_PPO_CHECKS` 六段数值校验（`launch.py::_PPO_CHECKS`）。
- 准入是**互斥**的：已有 running 的 `ppo` 任务返回 409（`_start_ppo()` 里判 `running_ppo` 的分支），已有 running 的 `infer`/`train` 也返回 409（`_start_ppo()` 里判 `running_real` 的分支）。
- `job_id = f"ppo-{uuid.uuid4().hex[:8]}"`（`_start_ppo()` 里 `job_id = f"ppo-{uuid.uuid4().hex[:8]}"`），本次即 `ppo-62933331`。
- 任务记录先落盘再起线程（`_start_ppo()` 里创建任务后立刻 `_persist_job()`），落盘位置 `runs/_rwpp_service/jobs/ppo-62933331.json`（本次实测存在，19412 字节）。

### 3.2 trainer → JVM

- `train_rwpp.py` 默认 `--port-base 5140`、`--eval-port-base 5200`（`train_rwpp.py::build_parser()` 的 `--port-base` / `--eval-port-base`）。
- `VecRwppEnv` 按 `port = port_base + index` 分配（`src/ironzero/training/vec_rwpp.py` 里的 `port=self.port_base + index`），所以 4 个训练 env 正好占 `5140..5143`。
- JVM 命令行由 `src/ironzero/rwpp/process.py::_bridge_command()` 拼装，实测形态：


## 4. 回传链路与已观测到的真实状态流

### 4.1 数据流向

```
trainer 写 <run>/live.jsonl（每行一个 JSON，seq 严格递增）
   → 宿主服务  GET /ppo/{id}/events?after=N      （`handler.py` 里 `/ppo/{id}/events` 分支，按 `seq > after` 过滤）
   → 平台后端  GET /api/rwpp/ppo/{id}/events?after=N（`routers/rwpp.py::rwpp_ppo_events()`，纯转发）
   → 前端      fePollPpo() 每 1500ms 一次（`ppoRun.js::startFePpoPolling()`），用 cursor 去重
```

- 服务端返回 `{next, events, status, job}`（`scripts/rwpp_service/README.md` §3 路由表）；`next` 是 `pending` 最后一个 `seq`，没有新事件时原样返回 `after`。
- 平台侧同一份数据还能从 `GET /api/rwpp/jobs/ppo-62933331` 拿到（`web/backend/app/routers/rwpp.py::rwpp_job()`），这就是前端「状态查询」的来源。

## 7. 已知风险点（全部在本次实践中踩到或验证过）

### 7.1 容器重启丢 `JOBS`，靠 `recover.py` 接管

- `JOBS` 是宿主服务进程内的 `dict`（`scripts/rwpp_service/state.py` 的 `JOBS`）。服务一重启，表就空了。
- 两层补救：① `paths._persist_job()` 每次更新都落盘到 `runs/_rwpp_service/jobs/{job_id}.json`（`paths.py::_persist_job()`，本次实测该文件存在）；② `recover.py` 启动时 `recover_jobs()` 优先读落盘记录，没有记录的再从 `rwpp-ppo-*` 目录的产物反推（`recover.py` 模块 docstring）。
- 终态判定优先看产物：`rwpp_summary.json` 出现 = `done`；`train.log` 出现 `Traceback` = `failed`；`live.jsonl` 超过 `STALE_SECONDS=300` 没更新且无 summary = `stale`（**不会**报 failed）。
- adopted 任务没有本地 `Popen` 句柄，停止时按 pid `taskkill /T /F` 整棵杀（`recover.py::kill_pid_tree`）。
- 结论：可以重启，但**不要**指望前端内存里的 `ppo.events` 还在 —— 前端要靠 `feRestorePpoJob()` 重新拿 `jobId` 并从 `after=0` 重拉。详见 [scripts/rwpp_service/README.md](../scripts/rwpp_service/README.md) §1.3。

### 7.2 `/app` 前缀必须改写，两处都要有

- 平台后端 `web/backend/app/routers/rwpp.py::_host_path()` 剥 `/app/` 前缀，`/infer` `/record` `/train` `/ppo` 四条路径共用。
- 宿主服务 `scripts/rwpp_service/paths.py::_strip_container_prefix()` 再兜一层，让绕过平台直接打 8300 的客户端也能用同一份路径。
- 该函数只在 `"/app/"` 前缀存在时才动字符串；反斜杠仅在**判定前缀**时归一化，否则 Windows 相对路径会被改成 `runs//platform//c.pt`。
- 症状：`init_checkpoint not found on the host: /app/runs/... (resolved to ...)`，HTTP 400。本次实测 `init_checkpoint` 在 `/jobs/ppo-62933331` 里是宿主机绝对路径，说明改写生效。

### 7.3 jar 与源码必须同步

- JVM 用的是 `E:\IronZeroBuild\rwpp-runtime-1.15\lib\rwpp-server-2.0.0.jar`（本次实测存在），而 bridge 的行为由 `io.github.rwpp.server.Main` 决定。
- 改了 bridge 源码却没重新构建 / 没分发到所有 runtime，就会出现「命令行参数传了但引擎不认」的现象（例如 `--physics-ms` 被老 jar 忽略，表现是 `episode_ticks` 与真实游戏 tick 脱钩）。
- 构建、分发、三处哈希校验的步骤见 [scripts/rwpp_service/README.md](../scripts/rwpp_service/README.md) §1.2。

### 7.4 `-X utf8` 与 cp936：两层编码坑

这是本次实测**真实踩到**的，有两层，互不相同：

**(a) Python 侧：子进程输出按 UTF-8 解码（代码保证，本次未触发失败）**

- `scripts/rwpp_service/proc.py` 里解码子进程输出的那段（注释从 `# Decode explicitly.` 起）显式指定 `encoding="utf-8", errors="replace"`。若用 `text=True` 而不指定编码，中文 Windows 会走 cp936，UTF-8 字节解不开就在 `communicate()` 里抛 `UnicodeDecodeError`，被兜底 `except` 吞掉后返回 `(-1, "")` —— 任务落成 `status=failed, error=None, last_log=""`，日志全丢。
- 本次 `status=done`、`train.log` 完整 24 行，说明这条路径正常；`proc.py` 里的注释记录了它曾被触发过的历史。

**(b) PowerShell 侧：控制台按 cp936 解码 UTF-8 文件（本次真实踩到）**

本次实测环境是 Windows PowerShell 5.1，`[Console]::InputEncoding` = `gb2312`：

| 命令 | 结果 |
|---|---|
| `Get-Content runs\platform\rwpp-ppo-ppo-62933331\live.jsonl -Tail 1` | 路径字段显示成 `E:\qwq\寮哄寲瀛︿範绗旇\...` 这类乱码 |
| `Get-Content ... -Encoding utf8 -Raw` | 与 `[System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)` **逐字符相等**（`-ceq` 为 True） |
| `(Get-Content docs\产物目录规范.md).Count` vs `-Encoding utf8` | `113` vs `142` —— 默认解码不只是显示乱码，还会把部分中文行**合并**，连行数都不可信 |

结论：文件本身是合法 UTF-8，没有损坏；**只是不带 `-Encoding utf8` 的 `Get-Content` 会解码错**。同一份 `live.jsonl` 的字节按 UTF-8 严格解码也能通过（`UTF8Encoding($false,$true)` 不抛异常）。所以本文所有读 `.jsonl` / `.log` 的命令都带 `-Encoding utf8`。

同一条事实的第二层证据：

- `Invoke-WebRequest http://127.0.0.1:8300/jobs/ppo-62933331` 的响应头是 `application/json; charset=utf-8`，`.Content` 里中文路径正常。
- 平台侧 `http://127.0.0.1:8000/api/rwpp/ppo/.../events` 的响应头是裸 `application/json`（没有 charset）；同一份字节按 UTF-8 解码能得到 `强化学习笔记`，而 `.Content` 里没有。所以**读平台接口的中文时**要用 `[System.Text.Encoding]::UTF8.GetString($resp.RawContentStream.ToArray())`，不要直接信 `.Content`。

`-X utf8` 的作用域：它只影响 Python 自己的 stdio 与 `open()` 默认编码，**不能**修正 PowerShell 的显示。两者要分别处理。

### 7.5 `physics_ms` 必须显式钉住

- trainer 自己的 `--physics-ms` 默认值是 `16`（`build_parser()` 的 `--physics-ms`），但它历史上挪过位置；`--frame-ms` 默认 `2`（`build_parser()` 的 `--frame-ms`）。
- 前端在 `ppoRun.js::feStartPpo()` 里的 `physics_ms: 16` 写死，服务在 `run_ppo()` 里无条件拼进 argv（`command.extend(["--physics-ms", ...])`），模型层 `RwppPpoRequest.physics_ms` 也保留该字段。三处都钉住，才保证「`episode_ticks` 就是游戏 tick，`frame_ms` 只控墙钟」。
- 本次实测：argv 里 `--frame-ms 1 --physics-ms 16`，JVM 命令行里同样 `--frame-ms 1 --physics-ms 16`，逐层透传成功。
- 若省略 `--physics-ms`：`src/ironzero/rwpp/process.py::_bridge_command()` 里 `if physics_ms > 0:` 不成立，bridge 命令行里就没有这一项，引擎回落到自己的默认值 —— 表现是「同 `episode_ticks` 但每局实际时长变了」，且历史 `P0修复后训练结论.md` 里记录的 physics 步长 bug 会复现。

### 7.6 `frame_ms <= 0`：`physics_ms>0` 时合法，否则钳到 1

- `process.py::effective_frame_ms(frame_ms, physics_ms=0)`：
  - `physics_ms > 0` 且 `frame_ms <= 0` → 返回 **0**，即「完全不 sleep」。此时引擎的 delta 由 `--physics-ms` 钉死，`frame_ms` 只剩 pacing 作用，0 不会改变仿真（契约 §0 结论三、§2）。
  - `physics_ms == 0` 且 `frame_ms <= 0` → 仍钳到 `1` 并打印一次警告，因为这时 `frame_ms` 本身就是 frame delta，0 会让引擎零步长推进。
- 实测（Lake，`--physics-ms 16`，6000 tick）：`--frame-ms 1` → 9.0 s，`--frame-ms 0` → 4.25 s（约 2.1×）；1200 tick 的 120 帧采集窗口 1.178 s → 0.136 s（约 8.7×）。`frame_ms=1` 里大部分墙钟是 `Thread.sleep` 的固定唤醒开销。
- `RwppGameConfig.frame_ms` 默认已从 `2` 改成 `0`。表单里填 `0` 现在真的等于「不限制速度」，前提是同一次运行里 `physics_ms > 0`（默认 16）。
