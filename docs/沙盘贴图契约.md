## 0. 为什么要有这份契约

2026-11-12 实测真实回放
（`runs/platform/real-rwpp-20261111-092721-4f66bf/replays/replay-rwpp-20261111-092721-4f66bf.json`，
5294 帧）第 45% 帧的 34 个单位，**全部落到矢量保底绘制**，没有任何一个画出贴图。根因是四个独立断点叠加：

| # | 断点 | 位置 | 后果 |
|---|---|---|---|
| 1 | `normalizeUnit` 只保留 9 个字段，丢掉 `unit_type/is_building/is_builder/is_factory` | `app.js:276-291` | 分类判定全部拿不到类型 |
| 2 | `interpolateUnits` 用 9 个字段**重建**单位对象，二次丢字段 | `app.js:4570-4580` | 即使修好 #1，渲染时仍无类型 |
| 3 | `unit.type === 'tank'` 恒假（单位对象永远没有 `type` 字段） | `app.js:3792` | 坦克也进不了贴图分支 |
| 4 | 贴图清单只有 8 个固定键，实机 28 种单位类型绝大多数无图 | `maps.py:390-420` | 有类型也找不到图 |

另外两个次级问题：
- **尺寸失真**：所有单位统一按 24 世界像素画，指挥中心（53×68）和坦克（12.8×24）一样大。
- **多帧贴图未切帧**：`base.png` 212×68 是 4 帧（每帧 53×68），`tank.png` 48×30 是 3 帧（每帧 16×30），`extractor.png` 148×59 是 4 帧（每帧 37×59），旧代码靠魔法数字硬切。

## 1. 后端契约：`GET /api/maps`

保留原有 `units` 字段（扁平 `key -> relPath`，兼容旧键 `tank/tank_turret/builder/extractor/factory/turret_base/turret_top/command_center`），
**新增** `unitSprites` 字段：

```jsonc
{
  "units": { "tank": "units/tanks/tank.png", "...": "..." },   // 旧：不动
  "unitSprites": {
    "version": 1,
    "byType": {
      "c_tank": {
        "image": "units/tanks/tank.png",  // 相对 ASSETS_ROOT，经 /api/assets/{path} 读取
        "frames": 3,                       // 横向帧数，0 或 1 都表示单帧
        "frameW": 16,                      // 单帧宽（贴图原始像素）
        "frameH": 30,
        "scale": 0.8,                      // 游戏 ini 的 imageScale，缺省 1.0
        "kind": "mobile",                  // "building" | "mobile"
        "turretImage": "units/tanks/tank_turret.png",  // 可缺省
        "turretFrames": 1,
        "turretFrameW": 10,
        "turretFrameH": 40,
        "turretScale": 0.8
      }
    },
    "aliases": { "command_center": "commandCenter" },
    "fallback": {
      "mobile":   { "image": "...", "frames": 1, "frameW": 16, "frameH": 30, "scale": 0.8, "kind": "mobile" },
      "builder":  { "image": "...", "frames": 1, "frameW": 20, "frameH": 20, "scale": 1.0, "kind": "mobile" },
      "building": { "image": "...", "frames": 1, "frameW": 35, "frameH": 44, "scale": 1.0, "kind": "building" }
    }
  }
}
```

约束：
1. `byType` 的键**就是**回放/帧里的 `unit_type` 原值（`c_tank`、`commandCenter`、`extractorT2`…），大小写敏感。
2. `frames`、`frameW`、`frameH` 必须与 `image` 真实尺寸自洽：`frames * frameW == image.width` 且 `frameH == image.height`。
   唯一例外是少数按行切帧的贴图，此时 `frameH * 行数 == image.height`，需在生成脚本里显式算出并在 manifest 里写成单行帧数。
3. `scale` 取自该单位 ini 的 `imageScale`（缺省 1.0）；`turretScale` 取自 `turretImageScale`。
4. `kind == "building"` 的单位渲染时**不旋转**；`mobile` 按航向旋转。
5. 所有 `image` 必须真实存在于 `.game_cache/` 下，否则生成脚本报错退出（不允许静默产生坏 manifest）。

## 2. 前端渲染规则

### 2.1 字段透传（硬性）

`normalizeUnit` 必须保留：

| 输出字段 | 来源（任一存在即可） |
|---|---|
| `unitType` | `unit_type` / `unitType` / `type` |
| `isBuilding` | `is_building` / `isBuilding` |
| `isBuilder` | `is_builder` / `isBuilder` |
| `isFactory` | `is_factory` / `isFactory` |

`interpolateUnits` 必须**逐字段透传**上述 4 个字段（左右帧取左帧值即可，类型不会中途变），不得重建丢字段。

### 2.2 解析顺序

```
unit.unitType
  → unitSprites.byType[type]
  → unitSprites.byType[aliases[type]]
  → unitSprites.fallback[builder|building|mobile]
```

### 2.3 绘制尺寸（1:1 世界像素，禁止统一尺寸）

```
drawW = frameW * scale * cam.scale
drawH = frameH * scale * cam.scale
若 drawH < MIN_VISIBLE_H(=10) 则整体等比放大到 10
```

即以“贴图原始像素 = 世界像素”为基准。指挥中心（53×68）必须明显大于坦克（12.8×24），
不允许再出现 `size = baseSize * 2.2` 这类魔法倍数。

### 2.4 帧动画

移动单位按时间取帧：`frame = floor(time * FPS) % frames`（FPS 取 6）。
建筑固定第 0 帧。**禁止**再用 `if (img.width >= 200) { frameW = 53 }` 之类硬编码。

### 2.5 锚点

以单位 `x,y` 为贴图**中心**（游戏内单位坐标即中心），`ctx.translate(x, y)` 后
`drawImage(img, frame*frameW, 0, frameW, frameH, -drawW/2, -drawH/2, drawW, drawH)`。
移动单位在 translate 后 `rotate(heading + Math.PI/2)`（贴图默认朝上）。
炮塔单独 rotate(`turret + Math.PI/2`)，围绕中心点绘制。

## 3. 回归验证标准

1. `node --check web/frontend/app.js` 通过。
2. 用真实回放帧跑渲染探针：**凡是 manifest 能解析到贴图的单位，必须走 `drawImage`，矢量保底计数为 0**。
3. 矢量保底只在 `unitSprites` 缺失或图片加载失败时出现，且必须记录一次 `console.warn`（不得静默）。
4. `pytest -q` 全绿。

可复用的验证脚本（均在 `.runtime/`，已 gitignore）：

| 脚本 | 用途 |
|---|---|
| `verify_manifest.py` | 逐张读 PNG 头，核对 `frames*frameW == png宽` / `frameH == png高`，并统计 31 种真实 unit_type 的命中情况 |
| `e2e_strict.js` | **端到端**：拉真实 `/api/maps`，抽出真实 `app.js` 的渲染函数，跑真实回放全帧，输出 SPRITE / VECTOR-FALLBACK 计数与每类单位的实体尺寸、旋转次数、炮塔层数 |
| `render_preview.py` | 用真实 manifest + 真实 PNG 渲染一帧出图，供肉眼确认 |

`e2e_strict.js` 用法：

```powershell
node .runtime/e2e_strict.js http://127.0.0.1:8000 runs/platform/<回放>/replays/<回放>.json 1.0 0.4
#                                             ^api base      ^真实回放                      ^camScale ^time
```

## 4. 上线注意（重要）

`web/backend` 是以**只读卷**挂进容器的（`docker-compose.yml`：`../web/backend:/app/web/backend:ro`），
代码改动**不会热加载**，必须重启一次容器才会体现在 8000 端口：

```powershell
docker restart ironzero-platform
```

重启前 `/api/maps` 不带 `unitSprites`，前端按 §2.2 会走 fallback 矢量绘制（不会崩），
所以重启窗口期是安全的，只是暂时看不到贴图。

自检命令（确认线上真的下发了清单）：

```powershell
(Invoke-RestMethod http://127.0.0.1:8000/api/maps).unitSprites.version   # 期望 1
(Invoke-RestMethod http://127.0.0.1:8000/api/maps).unitSprites.byType.PSObject.Properties.Count  # 期望 135
```
