## A1【致命】gamma 与 episode 长度不匹配 · `ppo.py:33` ✅ 已修

```python
# 现状
gamma: float = 0.99
```

**实测**：真机 `DECISION_INTERVAL=10` ticks，`episode_ticks=3600` → **一局 360 个决策**。

```
0.99^360  = 0.027   ← 终局 +1.0 在第 1 步只剩 +0.027
0.997^360 = 0.339
0.999^360 = 0.698   ← 这个量级才合理
```

**这意味着模型在数学上“看不见”胜负**。这不是猜测——[训练监控诊断_20261112](../audit/训练监控诊断_20261112.md) 那次 105 update 的运行里，`terminal / potential / kills / bonus_build / income / strategy` **全部为 0.000**，唯一非零的是 `invalid −3.083` 和 `idle −3.344`。策略在学“怎么少挨罚”，因为**只有惩罚项落在它的折扣视界内**。

**改法**：

| 方案 | 值 | 说明 |
|---|---:|---|
| 最快验证 | `gamma=0.999` | 一局 360 步，视界 ≈ 1000 步，覆盖整局 |
| 折中 | `gamma=0.997` | 视界 ≈ 333 步，接近整局，方差更小 |
| 治本 | 缩短 episode 到 1200 ticks（120 步）+ `gamma=0.99` | 微操战斗本就该在 20 s 内分胜负 |

改动点：`src/ironzero/training/ppo.py:33` 默认值、`src/ironzero/training/train_rwpp.py:48` CLI 默认值。
**不需要重训**——gamma 不进 checkpoint，只影响 GAE。

## A2【致命】`potential` 在奖励“摊伤害”而不是“集火” · `rwpp/reward_shaping.py:95` ✅ 已修

```python
"potential": float(micro.potential_coef) * (potential - previous_potential)
# potential = hp_potential() = 己方HP占比 − 敌方HP占比   ← 线性
```

**实测推算**（25v25，总 HP 10500）：

| 打法 | 敌方 HP 减少 | potential 收益 |
|---|---:|---:|
| **集火打死 1 辆**（210 HP） | 210 | `0.5 × 210/10500 = +0.0100` |
| **摊伤害**：5 辆各打掉 200 HP | 1000 | `0.5 × 1000/10500 = +0.0476` |

**摊伤害的奖励是集火的 4.8 倍。** 而铁锈战争里打死一辆坦克 = 永久移除它 20 DPS，打残 5 辆 = 5 份 DPS 一点没少。
这条奖励在**主动教模型打出新手才有的错误打法**。

**改法**（三选一，推荐第 3 个）：

```python
# 方案 1：HP 用非线性（每单位存活即价值，残血仍满威胁）
phi = log(Σ己max_hp_存活 / Σ敌max_hp_存活)   # 或 sqrt

# 方案 2：把击杀权重提上来压过摊伤害（最小改动）
kill_bonus: 0.25 -> 1.0        # 1 杀 = +1.0，与终局同量级
potential_coef: 0.5 -> 0.1     # 削弱线性摊伤害的诱惑

# 方案 3（推荐）：potential 改成"有效战斗力差"
#   每单位战力 = 存活? (0.4 + 0.6*hp_frac) * 单位价值权重 : 0
#   残血单位仍有 70% 战力，死亡直接归零 -> 集火天然占优
```

# P2 空间分辨率与记忆

## P2-1【高】动作网格比武器射程粗 3 倍 · `micro_config.py:62`

**实测**（2700×2500 地图，8×8 网格，margin 24）：

```
grid  8: 每步 378.9 px   (attack_range 130 px → 步长/射程 = 2.91)
grid 16: 每步 176.8 px   (→ 1.36)
grid 20: 每步 139.6 px   (→ 1.07)
```

**每一步的动作位移是自己射程的 2.9 倍**——模型没法表达「走到刚好能打的距离」，只能「大概往那个方向走」。而铁锈战争的微操本质就是**射程边缘走位**（坦克 130 vs 火炮 290 vs 炮兵 310）。

**改法**：`map_grid: 8 → 16`（观测网格 + 动作网格一起，`position_grid` 也 → 16）。

代价：
- 观测 `4×16×16 = 1024`（vs 256），**+768 维** → 总维度 **2098**
- 动作 x/y 头各 `8 → 16`，`nvec` 从 `(11,5,8,8,26)` → `(11,5,16,16,26)`，**位置动作空间 4 倍**（x/y 两头的组合 `64 → 256`）

若嫌动作空间太大，可只放大**观测网格**、动作仍用 8 格 + 「relocate within cell」微调，但这需要新增动作头，工作量大。

## P2-2【高】没有观测历史，纯 POMDP · 无

`vision_radius=260` 默认开启，但：

```
260 px 视野圆覆盖 2700×2500 地图的 3.15% 面积
remembered_enemies 字段存在但恒为空列表
策略网络是纯 MLP，无 GRU/LSTM
```

**没有记忆 = 学不会「4 秒前看到 6 辆坦克往左」。** 而铁锈战争的核心决策（预判、包抄、提前出防空）全部依赖短时记忆。

**改法（按成本排序）**：

| 方案 | 维度 | 工作量 | 评价 |
|---|---:|---|---|
| `frame_stack=2` | ×2（2098 → 4196） | 小（env 里存 deque） | 最省事，但只覆盖 0.33 s |
| `frame_stack=4` + 拉长 decision_interval 到 20 ticks | ×4（0.67 s 覆盖） | 小 | 覆盖更久 |
| frame_stack 只对**实体块 + 全局块**做（网格不堆） | +1330×3 ≈ +3990 | 中 | 省一半 |
| GRU/LSTM（recurrent PPO） | 不变 | 大（改 rollout/GAE/序列 minibatch） | 正解但工期长 |

**实测建议**：先做 `frame_stack=2`（0.33 s 记忆）验证有没有收益，再决定要不要上 GRU。

## P2-3【中】`vision_radius=260` 太小

260 px 只有 3.15% 地图，比坦克射程（130）的 2 倍还小。真机训练时敌方在 260 px 外就“不存在”，但**AI 的炮火能打到 290 px**（火炮 `maxAttackRange: 290`）。

**改法**：`vision_radius: 260 → 500`（≈ 10% 地图，覆盖大多数射程），或用「己方单位视野 + 建筑视野」组合。注意这会让观测分布变化，**必须和训练配置同步**——[inference-web-findings](../audit/inference-web-findings.md) 已经记录过一次训练/推理 `vision_radius` 不一致（260 vs 0.0）的 bug。

## P2-4【中】矿点坐标缺失

现在只有「已占矿点个数」1 维。铁锈战争的经济核心是**哪个矿、离基地多远、对面在不在抢**。

**改法**：全局块加最近 3 个矿点的 `(x, y, occupied, extractor_level)` → 12 维；或单独做一个 `resource_slots` 编码块（`configs/maps/*.meta.json` 里矿点位置是静态的，可以预先算好距离图）。

| 缺的动作 | 现状 | 影响 |
