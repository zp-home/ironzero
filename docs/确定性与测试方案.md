# 确定性与测试方案

> 文档状态：v0.1 基线
> 作者：周培智
> 适用范围：本机 RWPP Headless 训练、评估、推理与受控内网人机评估
> 配套文档：[环境规格说明](./环境规格说明.md)

本文档定义“可复现”的含义、测试分层和 CI 门禁。目标不是追求所有环节逐位一致，而是明确每一层能复现到什么程度，并让失败可以被定位。

---

## 1. 复现等级

不同环节允许有不同的确定性等级：

| 等级 | 名称 | 含义 |
|---|---|---|
| D0 | 不可复现 | 无法重复，禁止用于训练和评估 |
| D1 | 统计可复现 | 多次运行的指标在置信区间内一致 |
| D2 | 轨迹可复现 | 关键事件、终止条件和最终结果一致 |
| D3 | 逐位可复现 | 相同输入产生完全相同的字节和数值 |

要求：

- 环境启动和 Bridge 协议测试应达到 D2。
- 固定回放测试优先争取 D2，确认游戏引擎能力后再评估 D3。
- 神经网络推理在同一设备、同一版本、同一输入下应力争 D3。
- 训练整体通常只要求 D1；跨机器训练不承诺 D3。
- 任何无法达到的等级必须记录原因，不能默默降低要求。

## 2. 种子体系

一个 run 至少包含以下独立种子：

```text
run_seed
episode_seed
map_seed
initial_state_seed
opponent_seed
policy_seed
action_sampling_seed
```

### 2.1 种子生成

推荐使用确定性派生：

```text
episode_seed = H(run_seed, episode_index)
map_seed = H(run_seed, map_id)
opponent_seed = H(episode_seed, "opponent")
policy_seed = H(episode_seed, "policy")
action_sampling_seed = H(episode_seed, "sampling")
```

`H` 必须是版本固定的哈希或伪随机函数，不能依赖语言默认的 `hash()`。

### 2.2 种子记录

每个 episode 记录：

```text
run_seed
episode_seed
map_seed
initial_state_seed
opponent_seed
policy_seed
action_sampling_seed
```

同一 seed 在不同版本、不同地图或不同模组下不保证相同结果。

## 3. 非确定性来源

必须逐项排查：

- 游戏随机数生成器。
- Java 线程调度。
- 多线程模拟和网络回调顺序。
- 浮点运算顺序。
- 单位 ID 分配。
- 实体集合迭代顺序。
- 文件遍历顺序。
- Python 字典、集合和 `hash()`。
- 系统时间、时区和高精度计时。
- PID、端口和临时目录。
- 网络重连和消息重排。
- 模型推理服务的批处理和 GPU 非确定性。
- 日志写入顺序。
- 进程启动和关闭的竞态。

任何被确认为不可控的来源，都必须在复现报告中注明影响范围。

## 4. 确定性控制措施

### 4.1 游戏侧

- 固定游戏、RWPP、地图和模组版本。
- 固定 tick 推进方式。
- 训练使用 lockstep。
- 禁止在 episode 内动态加载模组。
- 禁止依赖客户端窗口和渲染状态。
- 所有游戏状态修改回到游戏线程。
- 为动作和观测添加递增序列号。

### 4.2 Python 侧

- 固定 Python、PyTorch 和 CUDA 版本。
- 配置 Python、NumPy 和 PyTorch 随机种子。
- 禁用不必要的线程并行，或记录线程数。
- 固定实体排序和 JSON 序列化键顺序。
- 使用规范化的浮点格式。
- 训练和评估使用相同的数据变换。

### 4.3 推理侧

- 固定模型版本、运行时版本和硬件类型。
- 推理前预热。
- 单条推理关闭动态批处理。
- 记录是否使用了确定性算子。
- 对 ONNX/TorchScript 转换前后做数值对齐测试。

## 5. 固定回放与轨迹哈希

### 5.1 回放内容

每个固定回放至少包含：

```text
replay_id
game_version
rwpp_commit
adapter_version
protocol_version
scenario_version
map_id
map_hash
seeds
action_sequence
tick_boundaries
terminal_state
reward_breakdown
observation_schema_version
```

### 5.2 轨迹哈希

对规范化后的状态快照计算哈希：

```text
trajectory_hash =
  SHA256(
    canonical_json(
      tick,
      controlled_team,
      entities,
      resources,
      visible_enemies,
      terminal_flags
    )
  )
```

比较层级：

```text
state_hash      单次快照
trajectory_hash 整局轨迹
reward_hash     奖励分量的规范化哈希
action_hash     动作序列哈希
```

浮点数必须使用固定精度序列化，例如保留 6 位小数。精度选择必须写入 schema。

## 6. 测试分层

### 6.1 单元测试

覆盖：

- 动作解码。
- 动作掩码。
- 奖励计算。
- 终止和截断判断。
- 规范化和反归一化。
- 实体排序和 padding。
- schema 校验。
- 版本兼容检查。

要求：

- 不依赖游戏进程。
- 每次提交都运行。
- 失败必须阻断合并。

### 6.2 契约测试

覆盖：

- `hello` 握手。
- `reset`。
- `step`。
- `obs`。
- `reward`。
- `done`。
- `error`。
- `heartbeat`。
- `shutdown`。

重点验证：

- 字段必填。
- 类型正确。
- 未知字段处理。
- 消息大小限制。
- 过期 episode。
- 重复 decision。
- 乱序消息。
- 非法 JSON。

### 6.3 集成测试

需要真实 RWPP：

- 启动服务端。
- 加载固定地图。
- 加载测试扩展。
- 创建比赛。
- 推进固定 tick。
- 读取单位状态。
- 执行移动动作。
- 验证动作回执。
- 关闭进程和端口。

集成测试可以放在 nightly，不要求每次提交运行。

### 6.4 Golden trace 测试

预先保存一局标准轨迹：

```text
固定场景
+ 固定种子
+ 固定动作序列
→ 固定关键状态和结果
```

每次修改动作、奖励、观测或游戏适配层时，必须比较：

- terminal result。
- 关键 tick 状态。
- 奖励分量。
- 实体数量和 ID。
- 轨迹哈希。

### 6.5 迷雾测试

测试用例：

1. 敌人位于迷雾外，观测中不存在。
2. 敌人进入视野后出现。
3. 敌人离开视野后只保留最后位置。
4. 不可见敌人的血量变化不影响观测。
5. 不可见敌人的资源变化不影响观测。
6. 动作回执不包含不可见目标信息。

### 6.6 奖励漏洞测试

建立专门场景，检查模型是否通过以下方式刷奖励：

- 反复建造和取消。
- 无效移动。
- 攻击无价值目标。
- 故意拖延比赛。
- 反复切换目标。
- 利用地图边界或寻路 bug。
- 利用生产队列和资源漏洞。

### 6.7 稳定性测试

- 连续运行 30 分钟。
- 连续运行 100 局。
- 4、8、16 个实例并行。
- 进程被强制终止后恢复。
- 端口被占用后恢复。
- 磁盘空间不足时安全退出。

### 6.8 故障注入

必须能模拟：

- 游戏进程崩溃。
- Bridge 断开。
- 消息延迟和乱序。
- 消息重复。
- 推理超时。
- 模型输出非法动作。
- 模型返回 NaN。
- 地图加载失败。
- 扩展加载失败。
- 日志写入失败。
- 端口耗尽。
- 子进程无法关闭。

每个故障必须有明确的：

```text
检测方式
错误码
清理动作
是否计入训练
是否告警
```

## 7. CI 分层

### 7.1 每次提交

运行时间目标：5 分钟以内。

```text
格式检查
静态类型检查
单元测试
schema 校验测试
协议契约测试
Mock Bridge 训练冒烟测试
```

### 7.2 每次合并到 main

运行时间目标：15 分钟以内。

```text
完整单元测试
协议兼容测试
回放解析测试
奖励计算测试
模型 manifest 测试
短时稳定性测试
```

### 7.3 夜间任务

运行时间目标：1 小时以内。

```text
真实 RWPP 启动
地图加载
动作回执
迷雾测试
100 局稳定性
4 实例并行
轨迹哈希回归
```

### 7.4 发布前

```text
8/16 实例压力测试
长时运行
故障注入
许可证和第三方清单检查
模型晋级评估
演示彩排
```

真实游戏资源不应提交到仓库。CI 使用受控的 runner 或本地发布检查，不把游戏 assets 打进构建产物。

---

## 8. 测试矩阵

至少覆盖以下维度：

| 维度 | 取值 |
|---|---|
| 操作系统 | Windows 目标版本 |
| Java | 项目锁定的 JVM 版本 |
| RWPP | 项目锁定的 commit |
| 游戏资源 | 锁定的测试资源版本 |
| 地图 | micro、固定地图、评估地图 |
| 迷雾 | 关闭、开启 |
| 对手 | 随机、规则脚本、原生 AI |
| 环境数 | 1、4、8、16 |
| 调度模式 | lockstep、realtime |
| 故障 | 进程、端口、Bridge、推理超时 |

不允许用“在我的机器上能跑”代替版本矩阵测试。

## 9. 验收门禁

### 9.1 进入训练前

- [ ] 固定回放达到 D2。
- [ ] 100 局无崩溃。
- [ ] reset 无残留。
- [ ] 动作回执和错误码完整。
- [ ] 迷雾审计通过。
- [ ] 训练截断和 GAE 边界有单元测试。
- [ ] 模型不兼容 schema 时拒绝加载。

### 9.2 进入评估前

- [ ] 评估种子、地图和对手完全固定。
- [ ] 评估不使用训练随机化。
- [ ] 评估报告包含版本、种子和轨迹哈希。
- [ ] 置信区间和评估局数已记录。
- [ ] 至少包含随机策略和规则脚本基线。

### 9.3 进入演示前

- [ ] realtime 推理超时测试通过。
- [ ] 急停测试通过。
- [ ] 进程树和端口清理测试通过。
- [ ] 观察端不会改变模型输入。
- [ ] 模型、场景、奖励和游戏版本匹配。

### 9.4 进入内网人机评估前

- [ ] 公网隔离检查通过。
- [ ] 服务端未进入公共服务列表。
- [ ] 防火墙仅允许白名单客户端。
- [ ] 参与者知情同意记录完整。
- [ ] AI 可见性审计通过。
- [ ] 对局结束自动关闭监听。

## 10. 失败处理与 flaky test 规则

- 测试失败不能通过无限重试掩盖。
- 同一测试连续失败两次必须创建问题记录。
- 随机失败必须记录 seed、日志和轨迹。
- 非确定性测试必须标记为 `flaky`，并限制运行次数。
- flaky 测试不能作为唯一验收依据。
- 真实游戏测试失败时，先保留现场，再清理进程。
- 清理失败必须单独告警，不能只报告原测试失败。

## 11. 测试产物

每次测试 run 保存：

```text
run_id
test_suite
commit
environment_manifest
seed
stdout/stderr
failure_snapshot
trajectory_hash
latency_metrics
process_tree
port_list
```

产物默认不提交到 Git，通过 `.gitignore` 排除。

## 12. 当前必须补的测试

第一版至少补齐：

1. 动作掩码单元测试。
2. 观测 schema 测试。
3. Bridge 契约测试。
4. 固定动作序列回放测试。
5. 迷雾泄漏测试。
6. 进程和端口清理测试。
7. 推理超时兜底测试。
8. 奖励分量测试。
9. episode 终止/截断测试。
10. 4 实例并行稳定性测试。

这十项没有通过，不进入 PPO 训练。
