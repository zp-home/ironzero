# 环境规格说明

> 文档状态：v0.1 基线
> 作者：周培智
> 适用项目：铁锈战争强化学习
> 适用范围：本机 RWPP Headless 训练、评估、推理与受控内网人机评估
> 配套文档：[训练、推理与演示架构](../训练推理与演示架构.md)

本文档定义强化学习环境的行为契约。代码实现、Bridge 协议、训练配置和评估报告都必须引用本文档的版本号。

本文中的“必须”表示不满足就不能进入训练；“应该”表示允许在明确记录原因后暂时豁免。

---

## 1. 目标与非目标

### 1.1 目标

1. 把《铁锈战争》的交互过程定义成一个可验证的部分可观测马尔可夫决策过程（POMDP）。
2. 明确真实状态、观测、动作、奖励、终止和截断之间的边界。
3. 明确训练使用的 lockstep 时序与推理使用的 realtime 时序。
4. 为 Gymnasium 环境、Bridge、动作掩码和测试提供统一契约。
5. 保证训练、评估和推理不会因为语义不同而产生行为漂移。

### 1.2 非目标

- 本文档不定义具体神经网络架构。
- 本文档不定义 PPO 超参数。
- 本文档不定义地图编辑器和模组制作流程。
- 本文档不承诺未经验证的游戏版本兼容性。
- 本文档不允许全图信息泄漏或自动化多人作弊。

## 2. 形式化定义

环境是一个部分可观测、离散时间、双人或多人零和对抗问题：

```text
POMDP = (S, O, A, T, R, Ω, γ, H)

S  真实游戏状态
O  单个受控队伍的观测空间
A  结构化动作空间
T  游戏模拟推进
R  奖励函数
Ω  观测生成函数
γ  折扣因子
H  最大 episode 长度
```

对第 `i` 个决策点：

```text
o_i = Ω(s_i, team_id)
a_i ~ π(a | o_i, mask_i)
s_(i+1) = T(s_i, a_i, Δticks)
r_i = R(s_i, s_(i+1), team_id)
```

### 2.1 State 与 Observation

- `State` 是游戏引擎内部的完整状态，只能由游戏线程读取。
- `Observation` 是受控队伍可以合法获取的信息。
- 不允许把 `State` 直接序列化给模型。
- 观测必须经过可见性过滤、坐标归一化和实体掩码处理。

### 2.2 Agent 边界

第一版采用“队伍级单智能体”：

```text
一个受控队伍 = 一个 agent
一个 agent 可以控制该队伍的多个单位或单位组
敌方队伍由原生 AI、规则脚本或另一个策略控制
```

后续自博弈可以扩展为：

```text
Agent 0：受控队伍 0
Agent 1：受控队伍 1
共享策略或独立策略
```

第一版不允许一个策略同时读取双方私有信息。

## 3. 坐标、地图和时间

### 3.1 世界坐标

游戏状态中的位置必须使用游戏世界坐标，不使用屏幕坐标。

每个位置记录：

```text
x: float
y: float
```

规范：

- 坐标原点、轴向和单位由游戏引擎决定，并记录在 `game_adapter_manifest` 中。
- 观测编码可以归一化到 `[0, 1]`，但必须保留地图尺寸以便反变换。
- 模型动作中的位置必须由 Bridge 转换回游戏世界坐标。
- 移动目标的坐标必须落在合法位置或地图边界内。
- 屏幕分辨率、窗口大小和客户端缩放不得影响训练观测。

### 3.2 地图网格

第一版局部地图建议使用固定大小：

```text
grid_size: 64 × 64 或 96 × 96
channels:
  terrain
  passable
  resource
  visibility
  own_occupancy
  visible_enemy_occupancy
  neutral_occupancy
  fog_memory
```

每个通道必须声明：

```text
name
shape
dtype
value_range
normalization
missing_value
```

地图窗口以受控队伍的某个锚点为中心：

- 基地。
- 主力单位组。
- 最近战斗区域。
- 或以上多个窗口的组合。

具体锚点策略必须写入场景配置，不能在训练和推理时改变。

### 3.3 时间单位

所有游戏逻辑使用 tick：

```text
tick: int，单调递增
simulation_tick_hz: 游戏固定模拟频率，待实测登记
decision_interval_ticks: 两次决策之间的固定 tick 数
action_repeat_ticks: 当前动作至少保持的 tick 数
max_ticks: episode 的最大 tick 数
```

第一版建议：

```text
decision_interval_ticks = 12
action_repeat_ticks = 12
```

约束：

```text
1 <= action_repeat_ticks <= decision_interval_ticks
0 < decision_interval_ticks
max_ticks > decision_interval_ticks
```

### 3.4 Tick 与墙钟时间

- 训练和评估不得用墙钟时间决定 episode 是否结束。
- 训练和评估不得用渲染帧数代替 tick。
- 推理服务可以记录毫秒延迟，但动作截止点必须由 tick 定义。
- 如果推理超时，安全层必须执行已定义的默认动作。

### 3.5 lockstep 与 realtime

#### lockstep

用于训练和固定评估：

```text
推进到决策 tick
  → 停止推进
  → 生成观测
  → 等待动作或超时兜底
  → 校验动作
  → 再推进固定 action_repeat_ticks
```

要求：

- 游戏不会在模型推理期间继续推进。
- 每次 step 的状态转移边界固定。
- 动作到达延迟不影响训练轨迹。
- 超时只用于防止环境挂死，不应用于正常训练路径。

#### realtime

用于推理、演示和内网人机评估：

```text
游戏持续运行
  → 到达决策 tick
  → 发送观测
  → 策略在截止 tick 前返回动作
  → 安全层过滤
  → 在允许的 tick 执行
  → 超时则使用默认动作
```

要求：

- 游戏线程不得等待网络或模型。
- 动作带有 `decision_tick` 和 `deadline_tick`。
- 超过 `deadline_tick` 的动作必须拒绝。
- 拒绝后必须执行安全默认动作或保持当前命令。

## 4. Episode 状态机

```text
CREATED
  → STARTING
  → WAITING_FIRST_OBS
  → RUNNING
  → TERMINATING
  → COMPLETED
```

异常路径：

```text
任意阶段
  → FAILED
  → CLEANUP
  → COMPLETED
```

### 4.1 状态字段

```text
episode_id: string
match_id: string
state: enum
seed: int
map_id: string
scenario_id: string
controlled_team: int
created_at: timestamp
started_at: timestamp
ended_at: timestamp
failure_reason: string | null
```

### 4.2 状态迁移约束

- `RUNNING` 之后不能回到 `STARTING`。
- `COMPLETED` 之后不能接受新动作。
- `FAILED` 必须进入 `CLEANUP`。
- `CLEANUP` 必须停止游戏进程、关闭端口并刷新日志。
- 所有 Bridge 消息必须校验 `episode_id`，不匹配则拒绝。

## 5. 观测空间

### 5.1 顶层结构

```text
Observation
  ├── meta
  ├── global
  ├── own_entities
  ├── visible_enemy_entities
  ├── remembered_enemies
  ├── local_maps
  └── masks
```

### 5.2 meta

```text
episode_id
tick
controlled_team
observation_schema_version
visibility_revision
game_time
```

### 5.3 global

```text
funds
income
expense
population
population_cap
unit_count
building_count
army_value
visible_enemy_value
kills
losses
game_phase
```

所有数值必须声明：

- 原始单位。
- 是否归一化。
- 归一化方法。
- 缺失值。
- 取值范围。

### 5.4 实体

本队实体：

```text
entity_id
entity_type_id
team_id
x
y
hp
max_hp
shield
facing
velocity
is_building
build_progress
production_queue_length
order_type
attack_target_id
attack_cooldown
carried_resource
is_selected
is_alive
```

可见敌人：

```text
entity_id
entity_type_id
team_id
x
y
hp
max_hp
shield
facing
velocity
is_building
build_progress
is_visible
last_seen_tick
```

记忆中的敌人：

```text
entity_id
entity_type_id
x
y
last_seen_tick
confidence
is_visible = false
```

规范：

- `entity_id` 在同一个 episode 内必须稳定。
- 实体列表使用固定最大长度加 `entity_mask`。
- 空缺槽位必须使用固定值填充。
- 实体排序必须稳定，不能依赖 Python 字典或 Java 集合的迭代顺序。
- `entity_type_id` 必须来自固定类型表，不能把显示名称直接作为 ID。
- 死亡实体必须通过 `is_alive` 或实体掩码移除。

### 5.5 局部地图

局部地图的每个格子记录：

```text
terrain_height
passable
resource_density
visibility
own_occupancy
visible_enemy_occupancy
neutral_occupancy
fog_memory
```

地图必须满足：

- 形状固定。
- 通道顺序固定。
- 值域固定。
- 缺失值固定。
- 训练和推理使用同一套归一化参数。

### 5.6 观测历史

第一版有两种可选方案：

1. `frame_stack`：保存最近 N 个决策观测。
2. `recurrent_state`：策略网络携带 GRU/LSTM 状态。

方案必须写入训练配置和 checkpoint manifest。评估和推理必须使用相同方案。

如果没有历史信息，必须明确标记为 `memoryless`，并且不能宣称模型具备长期记忆能力。

## 6. 动作空间

### 6.1 第一版动作

```text
MOVE_GROUP(unit_group, x, y)
ATTACK_MOVE(unit_group, x, y)
ATTACK_TARGET(unit_group, target_entity_id)
STOP(unit_group)
HOLD(unit_group)
```

### 6.2 单位组

第一版推荐：

- 固定编号的 4～8 个单位组。
- 每个单位组由场景配置生成。
- 一个单位组最多包含固定数量单位。
- 单位组为空时，`unit_group_mask=false`。

后续可以加入：

```text
BUILD(builder_group, building_type, x, y)
PRODUCE(factory, unit_type, count)
CANCEL_PRODUCTION(factory)
SET_RALLY(factory, x, y)
REPAIR(builder_group, target_entity_id)
```

### 6.3 动作组合

动作采用分解头：

```text
action_type
unit_group
target_entity
target_grid
count
```

每个头都必须有掩码：

```text
action_mask
unit_group_mask
target_mask
position_mask
count_mask
```

### 6.4 动作合法性

动作必须经过两层校验：

1. 策略采样时使用动作掩码。
2. 执行前根据最新状态重新校验。

以下情况必须拒绝：

- 单位不存在或已死亡。
- 单位不属于受控队伍。
- 目标不可见或已死亡。
- 目标位置不可通行。
- 资源不足。
- 建筑未完成。
- 生产队列已满。
- 动作超过频率限制。
- 动作来自过期 tick。

### 6.5 动作回执

每个动作必须返回：

```text
decision_id
episode_id
accepted
executed_at_tick
rejected_reason
```

如果动作在游戏线程执行失败，下一帧观测必须能反映失败结果。

## 7. 奖励

### 7.1 奖励分解

奖励必须按分量返回：

```text
reward =
    terminal_reward
  + combat_reward
  + economy_reward
  + map_reward
  + penalty
```

第一版 micro 场景建议只启用：

```text
terminal_reward
damage_reward
kill_reward
loss_penalty
invalid_action_penalty
```

### 7.2 终止奖励

```text
胜利：+1.0
失败：-1.0
平局：0.0
超时：0.0 或配置化小惩罚
```

### 7.3 奖励归一化

- 单位价值必须按场景基准价值归一化。
- 资源奖励必须按单位时间收入归一化。
- 奖励裁剪范围必须写入配置。
- 不能用未归一化的绝对值直接训练。
- 中间奖励的总量不应长期压过终局奖励。

### 7.4 奖励审计

每次 episode 必须记录：

```text
reward_total
reward_terminal
reward_combat
reward_economy
reward_map
reward_penalty
action_count
invalid_action_count
```

必须保留至少一个规则脚本作为奖励漏洞检测基线。

## 8. 重置语义

### 8.1 首版硬重置

首版采用进程级硬重置：

```text
停止旧进程
  → 清理端口和运行目录
  → 启动新进程
  → 加载场景
  → 等待第一帧观测
  → 返回 reset observation
```

硬重置必须验证：

- 旧进程已退出。
- 旧端口已释放。
- 旧临时目录不再被引用。
- 新 episode 的 ID 和 seed 不同或明确记录。
- 没有旧单位、资源或生产队列残留。

### 8.2 软重置

只有在硬重置测试通过、且 RWPP 提供可靠重置能力后，才允许软重置。

软重置必须通过以下测试：

- 连续 100 次 reset 后单位数量一致。
- 资源、生产队列和冷却状态一致。
- 单位 ID 不冲突。
- 迷雾状态一致。
- 随机数状态可恢复或重新播种。

### 8.3 reset 返回

```python
observation, info = env.reset(seed=seed, options=options)
```

`info` 至少包含：

```text
episode_id
match_id
seed
map_id
scenario_id
game_version
adapter_version
observation_schema_version
reset_mode
```

## 9. 终止与截断

### 9.1 terminated

以下情况必须是 `terminated=True`：

- 受控队伍获胜。
- 受控队伍失败。
- 场景定义的胜负条件满足。
- 游戏引擎进入不可恢复的结束状态。

### 9.2 truncated

以下情况通常是 `truncated=True`：

- 达到 `max_ticks`。
- 达到场景时限。
- 人为终止评估。
- 训练预算耗尽。

### 9.3 故障

以下情况不得伪装成普通 terminated/truncated：

- 游戏进程崩溃。
- Bridge 断开。
- 动作协议错误。
- 观测 schema 错误。
- 推理服务不可用且无安全兜底。
- 地图加载失败。

这些情况必须通过 `info["failure"]` 或异常路径报告，并终止当前 rollout。

### 9.4 GAE 规则

```text
terminated=True
  → 不 bootstrap

truncated=True
  → 按配置 bootstrap

failure=True
  → 截断 rollout，不参与跨边界 GAE
```

## 10. 战争迷雾与可见性

### 10.1 可见性状态

```text
VISIBLE
EXPLORED_NOT_VISIBLE
NEVER_SEEN
DEAD_LAST_SEEN
```

### 10.2 观测规则

- 当前可见敌人可以包含完整公开属性。
- 曾经可见但当前不可见的敌人只能包含最后可见位置和 `last_seen_tick`。
- 从未见过的敌人不得出现。
- 不能通过实体数量、资源变化或动作回执反推出不可见敌人。
- 观测中的地图占用只能包含本队可见或已探索的信息。

### 10.3 迷雾审计

每个 episode 必须记录：

```text
visible_enemy_count
remembered_enemy_count
hidden_enemy_count
hidden_enemy_leak_count
visibility_revision
fog_audit_result
```

测试中必须故意放置不可见敌人，确认它们不会进入策略输入。

## 13. 环境验收

### 13.1 最小验收

- [ ] 能连续运行 100 局。
- [ ] 每局都有唯一 `episode_id`。
- [ ] tick 单调递增。
- [ ] reset 后无旧状态残留。
- [ ] 相同种子和动作序列可复现到约定的确定性等级。
- [ ] 观测 schema 通过校验。
- [ ] 动作回执可追踪。
- [ ] 迷雾外敌人不泄漏。
- [ ] 截断和终止区分正确。
- [ ] 故障 episode 不进入正常训练统计。

### 13.2 训练前验收

- [ ] 随机合法策略可以稳定运行。
- [ ] 动作掩码与执行前校验一致。
- [ ] episode 边界处理符合 GAE 规则。
- [ ] 训练、评估和推理使用同一套观测编码。
- [ ] 模型 manifest 能阻止不兼容 checkpoint 加载。

### 13.3 演示前验收

- [ ] 推理使用 realtime 模式。
- [ ] 推理超时不会阻塞游戏。
- [ ] 安全默认动作有效。
- [ ] 急停开关可用。
- [ ] 演示不使用全图信息。
- [ ] 对局结束后进程和端口全部释放。

## 14. 尚未验证、不得默认成立的事项

以下内容必须在 RWPP 实测后更新本文档：

1. 当前游戏版本是否兼容 RWPP。
2. 无头服务端是否支持可靠的 lockstep。
3. 是否能控制固定 tick 推进。
4. 是否支持可靠的软重置。
5. 单位 ID 是否在 episode 内稳定。
6. 迷雾查询是否准确。
7. 多实例是否互相隔离。
8. 原生 AI 在无头服务端是否按预期工作。
9. 地图和模组是否能稳定加载。
10. 浮点和线程调度是否影响复现。

在这些事项未验证前，相关能力只能标记为“设计中”，不能写入对外承诺。
