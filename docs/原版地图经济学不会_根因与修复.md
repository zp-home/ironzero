# 原版地图经济学不会：根因与修复

> 结论先行：**不是训练算法的问题，是 `build_extractor` 这一整类动作在原版图上被
> 永久屏蔽了 —— 智能体连「造矿场」这个动作都表达不出来，练多久都不可能学会。**
> 已修复，并用真机端到端跑通「矿场 → 工厂 → 出战斗单位」全链条。

## 0. 一句话

掩码（`build_masks`）问引擎「你的建造菜单里有什么」，引擎回答
`["landFactory"]`；但同一台建造者**实际接受** `extractor` 的建造令。
掩码信了菜单，于是把 `build_extractor` 关上；引擎又明明会执行。
两边问的不是同一个问题。

## 1. 症状

用户在 Web UI 选**原版地图** `[p2]Lake (2p)`、2v2、`scratch` 从零训练 500 轮，
80 多轮后：

| 指标 | 实测值（`runs/platform/rwpp-ppo-ppo-d9a6b6db/live.jsonl`，81 个 update） |
|---|---|
| `win_rate` | 恒 `0.0` |
| `timeout_rate` | 恒 `1.0` |
| `kills` / `losses` | 恒 `0.0000` / `0.0000` |
| `bonus_produce` | 恒 `0.0000` |
| `bonus_build` | 仅 19/81 轮非零，均值 `0.0092` |
| `terminal` | 恒 `0.0000` |
| `potential` | 恒负，均值 `−0.5077` |
| 拒绝主因 | `BUILD_UNAVAILABLE=466` |

`income=0.0000`、`bonus_produce=0.0000`、`bonus_build≈0` 三条同时为 0，
说明经济链**一步都没走通**。

## 2. 根因：菜单和调度器问的不是同一个问题

### 2.1 两边各自在做什么

掩码侧（`src/ironzero/observation/masks.py`）：

```python
_KIND_REQUIRED_BUILDABLE = {
    "build_extractor": "extractor",     # 需要字面量 "extractor"
    "build_structure": "landFactory",   # 需要字面量 "landFactory"
}
```

桥接侧（`IronZeroBridge.buildersJson`，修复前）只探一个**写死的四元素列表**：

```java
private static final UnitType[] BUILDABLE_PROBE = {
    UnitType.extractor, UnitType.landFactory, UnitType.turret, UnitType.tank,
};
// 用 unit.canQueueAction(candidate, false) 过滤
```

### 2.2 实测矛盾（同一 jar、同一张图、同一条建造者、每样一条指令）

见 `.runtime/buildnames.json`：

| 桥报的 `can_build` | 实际下的指令 `structure_type=` | 回执 |
|---|---|---|
| `["landFactory"]` | `extractor` | **accepted** |
| | `extractorT1` | **accepted** |
| | `turret` | **accepted** |
| | `landFactory` | **accepted** |
| | `tank` | rejected `BUILD_UNAVAILABLE` |

`canQueueAction()` 回答的是「这个单位在**建造菜单 UI** 里有没有这一项」，
而 `buildWithBuilders()` 真正调度走的是 `getSpecialAction()` +
`isValidNewWaypoint()`。**两者不等价**，而掩码用的是前者的答案。

后果：`build_extractor` 在整局里恒为 `False`，策略**永远无法采样**这个动作。
不是「学得慢」，是「动作空间里这个动作不存在」。

## 3. 修复

`src/ironzero_bridge/java/ironzero/IronZeroBridge.java`：

1. **删掉固定列表探针**，`buildersJson()` 改为调用新的 `buildableNamesFor()`。
2. `buildableNamesFor()` 用**注册表扫描**（`UnitType.values()` +
   `getSpecialAction()`），与工厂菜单 `producibleNamesFor()` 同一套逻辑，
   也与 `buildWithBuilders()` 的调度同一套判定 —— 报告的菜单与实际可调度集合
   **按构造一致**。
3. 扫描之外再显式探 `CANONICAL_BUILD_NAMES`（`extractor` / `landFactory` /
   `turret`），经 `resolveUnitType()` 解析。原因：原版图上引擎内部名是
   `extractorT1`，注册表扫描拿不到字面量 `extractor`，而掩码要的正是那个字面量。

可负担性**刻意没有**并进菜单：掩码已经按 `funds` 单独把关，菜单随余额跳动会让
观测变成非平稳的。

## 4. 验证

### 4.1 掩码可达性（真机，`.runtime/econ_gate.json`）

| 仍关闭 | `build_extractor, produce_unit, upgrade_building` | `produce_unit, upgrade_building`（成因不同，见 §5） |

### 4.2 端到端经济链（真机，`.runtime/e2e_economy.json`）

一单一单发、中间不发任何指令（保证在建工程不被新指令打断）：

| tick | 事件 | 回执 |
|---:|---|---|
| 2 | `build_extractor` slot 0 | accepted |
| 141 | **矿场建成**（`extractorT1` 出现） | — |
| 142 | `build_structure landFactory` | accepted |
| 491 | **工厂建成**，菜单 `["builder","hoverTank"]` | — |
| 493 | `produce_unit hoverTank` | accepted |

「矿场 → 工厂 → 出战斗单位」在**原版 Lake 图**上完整跑通。
这正是用户要的「会生产、会建筑」，此前每一步都被掩码掐死。

### 4.3 回归测试

`tests/test_rwpp_economy_contract.py` 新增 2 条：

  `buildersJson` 不得再用 `BUILDABLE_PROBE`，且扫描必须走 `getSpecialAction`、

## 5. 还没解决的两件事（如实说明）

### 5.1 `produce_unit` / `upgrade_building` 仍被关闭

它们在**开局**关闭是正确的（开局没有工厂、没有可升级建筑），但要注意一个
时序问题：Lake 上工厂要 ~490 tick 才建成，而 `episode_ticks=4800` 里
还要再等 ~1530 tick 才下第一个单位。也就是说**一局内只有约 2 次「造兵」窗口**，
样本极稀疏。想让它真正学会，需要：

* 加长 `episode_ticks`（Lake 建议 ≥8000），或
* 用 `warmstart` 预热，不要让策略从零去撞这个稀疏奖励。

### 5.2 原版图上「打赢」仍然困难

`docs/内置AI不进攻_根因与修复.md` 已查明：`--unlock-ai` 会让引擎
`aggressiveMode=true`，而那个标志的含义是「**不建造、不防守**」。所以：

| 配置 | Lake 上的结果 |
|---|---|
| `--unlock-ai` | 对面只会造 builder/scout，2 万 tick 内打不出胜负 |
| 不加 `--unlock-ai`（用户当前配置） | 对面正常发展（最难时 30+ 种单位），但也很少主动推过来 |

用户当前跑的是**后者**（`unlockAi=false`），所以对面会发育、会造兵，这对学经济
是**正确**的方向；只是同时需要更长的 episode 才能等到接战。

**建议**：原版图训练用 `units_per_team=2`、`episode_ticks≥8000`、
`enemy_ai_difficulty=2`（实测难度 2 时对面最近距离 469 px，难度 3 时 102 px，
能真正压过来）。先解决「动作能表达」，再谈「打得好不好」——这一步已经完成。
