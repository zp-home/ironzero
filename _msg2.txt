fix(bridge): movement and attack orders must never include the builder

A numbered unit group selects units by id % GROUP_COUNT, so the builder lands in
whatever group its own id names and cannot be excluded by addressing a different
group. The Python curriculum already filtered builders when choosing which group
to march, but that only decides which group -- the order still reached the builder
through the id-modulo rule. The broadcast slot was worse: it selected every living
friendly unit, builder included.

Measured with a noop policy (so the curriculum is the only actor) on Lake at
difficulty 1, .runtime/economy_over_time.json: the builder's live order_type was
attack_move at ticks 9001 and 12001, and over 60000 ticks (3x the normal episode)
the economy produced exactly one extractor and then lost it -- income went
18 -> 26 -> back to 18 and never recovered. A builder that marches with the army
cannot expand, so income is frozen at the base rate and the army can never
out-produce a difficulty-1 opponent that fields 30-38 units.

Fix: addOwnOrderableUnits gains an excludeBuilders parameter, applied to
move_group / attack_move (army orders). Build and produce orders are untouched.

Verified with the same probe after the change: income 18 -> 26 -> 34 -> 42 and
occupied pools 1 -> 2 -> 3 across one episode, i.e. the economy now compounds
instead of collapsing back to the base rate.
