fix(rwpp): command centre is not a combat factory; produce orders name their target

Three defects in the production path, each measured with a probe under scripts/.

1. The command centre counted as a combat factory.
   ``combat_factories`` accepted any factory whose menu contained a non-builder
   entry, and the command centre's menu is ``[builder, scout]``. Because
   ``produce_options`` walks factories in payload order, its first entry was
   ``(23, scout)``, so every production order was "make a scout at the base".
   Measured at the end of a full episode on Lake at difficulty 1: three
   ``landFactory`` buildings stood idle for 19000 ticks while the army was six
   ``scout`` against an enemy holding tanks, artillery and gunships.
   Fix: a factory qualifies only when its menu contains something ranked above
   scout, and the command centre never qualifies.

2. Unit choice was absolute strength, which emptied the army.
   Preferring the strongest unit picked ``artillery`` (900 credits). The factory
   then waited for a bank it never saw: measured end state was *zero* mobile units
   with income at 42 and three factories idle. Fix: rank by value per credit, so a
   350-credit tank that gets built beats a 900-credit artillery that does not.

3. Production went through an index that is not stable between decisions.
   ``produce_unit`` was encoded as a target-head index into
   ``produce_options(state)``, a list rebuilt from the live observation. A busy or
   under-construction factory reports a shorter menu, so the same index names a
   different (factory, unit) pair one decision later. Measured: 13 entries at step
   83 and 6 at step 85, and the queue ended up holding ``c_tank`` -- absent from
   that factory's menu -- at ``progress = -1.0`` for the rest of the episode.
   Because ``production_queue_depth`` counts the wedged queue, the stage then read
   ``queue_full`` on 771 of 900 decisions.
   Fix: the curriculum now emits the concrete form the bridge already accepts,
   ``{"kind": "produce_unit", "factory_entity_id": N, "unit_type": "tank"}``, via a
   new ``_send_direct_order`` helper, and picks the unit from that factory's own
   menu, filtered by affordability read from the observation.

Also: ``produceUnit`` now resolves the unit type against the factory's own menu by
exact name (``exactProducibleType``) instead of trusting the engine's fuzzy
``UnitType.findUnitType``, and calls the engine's real production entry point
``Factory.executeSpecialAction`` -> ``FactoryBuildQueue.queueOrCancel`` instead of
building a command whose actionId the dispatcher does not turn into a queue entry.

Verified: economy now compounds -- income 18 -> 26 -> 34 -> 42 and occupied pools
1 -> 2 -> 3 within one episode, against a hard ceiling of 26 (one extractor) before
these fixes. 113 core tests pass.

Still not achieved: the factory queue is accepted and stays at ``progress = -1.0``,
so the army is still zero at episode end and the difficulty-1 win rate is 0%.
