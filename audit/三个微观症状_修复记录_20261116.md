## 1. 症状①：一个矿

### 1.1 解码器语义错位（最隐蔽的一条）

**问题**：`_issue_late_expansion` 把**全局池号**放进动作向量第 5 位：

```python
chosen_pool = int(free[offset])          # 全局 slot id
action = np.array([... , chosen_pool])
```

而 `decode_action` 把这一位当作 **free 列表的下标**：

```python
free = [i for i, s in enumerate(slots) if not s.get("occupied")]
"slot_id": int(candidates[int(target_index) % len(candidates)])
```

开局 `free == [0..8]`，`free[i] == i`，**碰巧一致**——所以第一个矿能建成。一旦池 0 被占，`free == [1..8]`，此后每一令都偏移一位。

**修法**：引入 `extractor_pool_candidates()` 作为唯一权威，并给 `decode_action` / `decode_action_multi` / `_decode_heads` / `_decode_slot` 增加 `extractor_slot_is_global` 参数：

- **策略**（默认 `False`）：第 5 位是 free 池序号。保持不变，因为掩码和目标头本来就是按这个列表编号的。
- **课程**（`True`）：第 5 位已经是具体池号，不再二次索引。`_decode_curriculum_action` 传 `True`。

**验证**（本会话实测，池 0 已占用）：

```
            修前  修后
offset 0 →   1     0     （课程想继续建池 0，修前被重定向到池 1，等于放弃自己的半成品）
pool 2   →   3     2
```

好消息是**开局矿那条路径也顺带修好了**：修前"继续建池 0"会被解码成池 1，即课程在矿没造完时就去开第二口井，把第一口取消掉。

### 1.2 停滞窗口短于走路时间

**问题**：`STALL_DECISIONS = 20` × `DECISION_INTERVAL = 10` = **200 tick**，而工程车 `move_speed = 0.8 px/tick`，到最近的**第二个**空池（918 px）要 **1147 tick**，是窗口的 3.8 倍。

于是 stage 的行为是：瞄准池 1 → 走 160px → 判"停滞" → 换池 2 → 掉头 → 换池 3……**永远在路上**。这解释了为什么轮转修好后下了 47 次令，占用数仍是 1。

**修法**（`env.py:_issue_late_expansion` + 新增 `_expansion_walk_budget`）：

1. **判据换成物理量**：比较"工程车到目标池的距离"与上一决策。距离在缩短 = 订单在工作，直接返回，不碰任何计时器。
2. **窗口按距离推导**：`ceil((distance / speed / 10 + 14) * 1.25)`，即"走路时间 + 施工时间 + 25% 余量"，下限仍是旧的 20。
3. **目标池锁定**：`_expansion_target` 记住本轮目标，只要它还 free 就不重算 `free[offset]`。否则池状态一变，序号就指向另一口池，等于中途换目标。
4. `speed` 读 payload 的 `move_speed`，缺失时回退 0.8（`contract_gap.json` 实测值）。

**验收待跑**（真机）：`occupied_histogram` 最大值 ≥ 3、`income` ≥ 42。依据是并行探针 `.runtime/extractor_pools_probe.json` 把窗口放大到 600 tick 后正好得到这两个数，说明只差时间。

## 2. 症状②：不打高输出

### 2.1 观测宽度（根因）

**实测**（`replay-rwpp-20261116-133006-d97c5a.json`，1200 帧）：

| 预算 | 敌方 unit-frame 可见 | 火炮可见 |
|---|---|---|
| `max_entities=8` | 8415 / 11380（73.9%） | **0 / 500（0%）** |
| `max_entities=32` | 11380 / 11380（100%） | **500 / 500（100%）** |

原因是敌块**故意不重排**（target head 依赖流式顺序），于是保留的是出生序——地图预置的指挥中心、工程车、工厂、矿场 id 都最小，**后生产的战斗单位永远排最后**。8 个槽里 61.7% 被建筑占满。

**修法**——注意这里我**改了做法**：没有改 `MicroDuelConfig` 的默认值。

第一版把默认值从 8 提到 32，跑全测后 9 条失败，其中 `tests/test_two_slot_actions.py::test_default_is_the_old_layout` 的注释写得很明确：

> If this ever fails, every shipped checkpoint and ~850 tests break.

那个默认值是**刻意钉住的库契约**。所以我改为：

- `MicroDuelConfig` 默认仍是 8（库契约不动，所有 fixture / mock / 历史测量继续有效）。
- 新增 `WIDE_MAX_ENTITIES = 32` / `WIDE_TARGET_SLOTS = 33` 常量。
- `train_rwpp.build_game()` 里解析：`--max-entities` 默认 `None`，实际取 `max(WIDE_MAX_ENTITIES, units_per_team)`，保证 25v25 不会因为默认值被砍到 8；`--target-slots` 默认 `max_entities + 1`，保证**看得见就打得着**。
- 显式传 `--max-entities 8 --target-slots 9` 仍可复现历史布局，A/B 可做。

**推理侧不用改**：`play_rwpp_policy.py` 和 `eval_rwpp_policy.py` 都从 checkpoint 的 `micro_config` 读 `max_entities`/`target_slots`，所以训练/推理自动一致。

**代价（必须写进报告）**：`flat_obs_dim` 639 → 1935，**所有现存 checkpoint 失效**，必须重训。这是"看得见敌人"的必要代价。

### 2.2 奖励定价反向（"不知道疼"的真身）

**问题**：`combat_value` 按 `max_hp` 定价，而铁锈战争里血量和火力基本无关：

```
c_artillery  140 hp   ← 射程 290，是坦克(130)的 2.2 倍
builder      170 hp   ← 比炮车"值钱"
scout        350 hp
```

于是"优先杀炮车"得分低于"优先杀工程车"。**不是没信号，是信号方向反了。**

**修法**（`reward.py`）：

- 新增 `_unit_threat(unit)`：`1 + 射程/300 + 0.25*射速 + 0.35*能打空`，纯无量纲，`[0,2]`。
- `combat_value(hp, max_hp, unit=None)`：多一个可选 `unit`，给了就乘 `1 + 0.35*threat`。**默认 `None`，所有旧调用逐位不变**。
- 新增 `threat_value(unit)` 供击杀计价。
- 射程是**代理**不是真伤害——引擎把 stock 伤害藏在 `Projectile.reloadTime`，无法静态读取（`观测契约补齐_20261115.md` §8.3 已论证过不能编字段）。

**修法**（`reward_shaping.py`）：

- `kills` / `losses` 从"个数差"改为 `_weighted_attrition()`：按 `entity_id` 比对前后快照，只给**真正消失**的单位计 `threat_value`，再除以基线血量归一（保持"一杀 ≈ kill_bonus"的量级）。
- 无 `entity_id` 的 payload（mock engine、手写 fixture）自动回退到旧的计数语义。

**实测差异**：

```
杀炮车   -> 1.184   （修前 1.0，无法区分）
杀坦克   -> 1.589
杀工程车 -> 0.810
```

### 2.3 一个诚实的限制

**坦克(1.589) 仍高于炮车(1.184)**。原因是真伤害不可观测，而我用射程做代理；坦克血 210 > 炮车 140，血量项压过了射程项。

这不是调参能"修好"的——要么拿到真实 DPS（`type_features` 加一列，靠 `UnitType` 静态推导），要么接受"按血量+射程"这个近似。**我选择不为了让它好看而调系数**，因为那只会把代理变成另一个假的物理量。

**当前状态已经解决了原始症状**："杀炮车"从**比杀工程车还低**变成**比它高 46%**。坦克排在炮车前面对"不打高输出单位"这个抱怨不构成反向激励——两者都比工程车/建筑优先。

## 3. 症状③：不造防空

**问题**：`CANONICAL_BUILD_NAMES` 只有三个名字：

```java
{"extractor", "landFactory", "turret"}
```

注册表扫描也会漏掉 `antiAirTurret`（和漏掉 `extractor` 同一个原因：`UnitType.values()` 扫不到，但引擎实际接受）。所以**动作空间里根本说不出"防空塔"这个词**。而唯一造得出的 `c_turret_t1` 实测 `can_attack_air: false`；`laserDefence` 是导弹拦截器（`canAttack()` 返回 false）。

我们在 1200 帧回放里看敌方建了 `c_antiAirTurret`（1008 个 unit-frame），自己一个也造不出来。

**修法**（`IronZeroBridge.java`）：`CANONICAL_BUILD_NAMES` 追加 `"antiAirTurret"` 和 `"antiAirTurretT2"`，走与 `extractor` **完全相同**的 `resolveUnitType` + `getSpecialAction` 探测路径。引擎不接受就自动不进菜单，不会产生 `BUILD_UNAVAILABLE`。

**引擎侧确认**（`E:\IronZeroBuild\game-lib-src`）：

```java
// AntiAirTurret.java:128,133
public boolean canAttackFlyingUnits() { return true;  }
public boolean canAttackLandUnits()   { return false; }
```

正是需要的语义。

**验证**（Python 侧端到端）：

```
build_menu: [..., 'turret', 'antiAirTurret']
target 槽 7 -> antiAirTurret       （target head 能命名它）
is_defence_type('antiAirTurret') = True
is_pool_only_type('antiAirTurret') = False
```

菜单从 7 项变 8 项，`target_slots` 加宽后（33）有充足槽位，`economy_menu_sizes` 自动把宽度纳入 target mask。

**注意**：这项改动在 **Java** 里，需要重新构建 jar 才对真机生效：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build_rwpp_extension.ps1 `
  -RuntimeDir "E:\IronZeroBuild\rwpp-runtime-1.15" -JavaHome "E:\jdk25copy"
```
