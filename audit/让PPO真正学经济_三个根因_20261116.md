这个质疑是对的，而且我确实在做错的事。本轮之前我在调 `economy_credit_reserve`、`economy_max_factories`、`economy_production_queue_depth` 这类参数 —— **全部作用在课程（scripted stages）上，对 PPO 一点影响都没有**。

### 先证明这一点

`.runtime/policy_freedom.py` 用一个"后期富裕状态"（5 工厂、6 矿场、20 兵、2 万资金）渲染掩码：

```
economy slot kinds   ['build_extractor', 'build_structure', 'produce_unit', 'upgrade_building', 'noop']
tactical slot kinds  ['move_group', 'attack_move', 'attack_target', 'hold', 'stop', 'noop']

factory count cap      NOT MASKED
army size cap          NOT MASKED
credit reserve         NOT MASKED

verdict: POLICY IS UNCONSTRAINED by our caps
```

**结论**：`curriculum_mode="mask"` 下掩码只编码"引擎会不会接受"，不含任何配额或预算。我调的那些上限只约束课程。

## 一、真正的根因 #1：采样结构与局长度不匹配（最致命）

这是本轮最重要的发现，而且是我自己造成的。

**实测一局需要 2006 个决策**（`.runtime/episode_completion.py`）：

```
configured episode_ticks: 20056
expected decisions at DECISION_INTERVAL=10: 2005
episode 0 seed 88000: decisions=2006 result=timeout tick=20056
episode 1 seed 88001: decisions=2006 result=timeout tick=20056
```

而我之前所有训练都用 `--rollout-steps 1100` —— **不到一局的一半**。

### 后果

每个 rollout 都被拦腰截断，PPO 几乎看不到终局。表现是 `total_episodes` 在 19 个 update 后只涨到 20，而按 6 envs × 19 updates 应该有 ~114 局。

**这解释了为什么 PPO 学不会经济**：
- 一局 2006 决策，"建矿场是对的"要等约 1900 个决策才由终局兑现
- 如果 rollout 只有 1100 步，终局根本不在采样窗口内
- PPO 只在训练"半局游戏"，永远不知道半局之前的决策是好是坏

### 修复与验证

`--rollout-steps 2100`（> 一局）：

```
upd   eps  rollWin  rollRet
  1     4    0.00    0.571
  2     8    0.00    0.327
  3    12    0.00    0.253
  4    16   0.0625   0.468     <- 第一次出现胜局
  5    20    0.05    0.256
  6    20    0.05    0.223
```

**每个 update 完成 4 局**（之前是 0），并且出现了 `win_rate 0.25` 的时刻。

## 二、真正的根因 #2：经济奖励小到学不到

`.runtime/check_growth_run.py` 与 `reward_shaping.py` 的实际数值：

| 事件 | 旧奖励 | 对比终局 |
|---|---|---|
| 建成一座矿场 | `extractor_reward * delta / 10` = **0.04** | 终局 ±1.0 → **25:1** |
| 造一个侦察兵 | `bonus_produce` = 0.10 | |
| 赢一局 | ±1.0 | |

一个 700 资金的矿场（永久 +8 credits/s）只值 **0.04**，而两个侦察兵值 0.20。PPO 当然选择造侦察兵 —— 它在优化奖励，而奖励在告诉它"造兵比建经济好"。

### 修复：`income_growth`

```python
"income_growth": (
    economy_growth_bonus * (income_delta / base_income_reference)
    if income_delta > 0.0 else 0.0
),
```

- `economy_growth_bonus = 0.5`，`base_income_reference = 18.0`（地图基础收入）
- 第一座矿场：18 → 26，`+8/18 = +44%`，奖励 **0.22**（半个胜局）
- 这是**速率变化**而非速率，所以坐着不动无法刷分
- 刻意低于 1.0，塑造经济但不替代目标

**关键：这是教学，不是脚本**。它只说"收入涨了是好事"，至于建几个矿场、哪些、是否改升级、何时停止扩张，全部留给 PPO。

### 验证奖励真的在发放

```
reward_components keys seen (and how many updates each appears in):
  ...
  income_growth     6
```

## 三、真正的根因 #3：矿场只建 1 个（bug，已定位未修完）

`.runtime/income_breakdown.py`，Lake 难度 1，9 个矿池：

```
occupied pools:      0 -> 15 decisions
                     1 -> 1991 decisions     <- 整局只有 1 个
free pools:          8 free -> 1991 decisions
build_extractor dispatched:  33 次
extractor tiers:     tech_level 1: 1991
                     ever upgraded past T1: False

income vs extractor count:
  0 extractors -> 18.0
  1 extractor  -> 26.0
```

**33 次 `build_extractor` 指令，只建成 1 个矿场，8 个池子整局空闲。**

这与工厂的 bug 完全同构：某个池子被引擎静默丢弃 → 占用数不变 → 阶段以为"还没成功" → 永远瞄准同一个死池子。
