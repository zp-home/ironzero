# 三个微观症状的根因与方案：只建一个矿、不打高输出、不造防空

日期：2026-11-16
范围：`src/ironzero/`（obs / mask / decoding / reward / env）、`src/ironzero_bridge/java/ironzero/IronZeroBridge.java`、`runs/`、`.runtime/` 实测产物
问题提出：用户推理实跑后报告三条

> 1. 只建造了一个资源提取器
> 2. 攻击的时候不会攻击敌方高输出单位
> 3. 对方建造空军了，咱们一直没有防空

用户同时要求先回答：根因是**桥传输信息不全**、还是**压根不知道疼**（奖励无信号）、还是**课程写得比较死**；并明确要求**不要过多干预课程**。

---

## 0. 结论先行

三条症状**都真实存在且可复现**，但根因不在同一个地方，而且**不是"课程不够聪明"**：

| 症状 | 主导根因 | 次要根因 | 与课程的关系 |
|---|---|---|---|
| ① 只建一个矿 | **三层同时坏**：(a) 停滞窗口 200 tick 短于走路 1147 tick（3.8 倍）；(b) 动作向量放全局池号、解码器按 free 下标解，pool 0 占了之后**每令都错位**；(c) 掩码漏保护 `build_extractor` | 轮转已实现（33→47 次令）但 `occupied_histogram` 仍是 `{"0":15,"1":1991}` | **是课程 bug**，但修法是**换判据 + 对齐语义**，不是加阶段 |
| ② 不打高输出 | **观测契约截断**：敌块 8 槽、按出生序、61.7% 被建筑占满，最高 DPS 单位**100% 看不见** | 奖励里 kill 是**无差别计数**，唯一稠密势函数按 max_hp 定价，把火炮（140hp）**定得比工程车（170hp）还低** | 与课程无关 |
| ③ 不造防空 | **动作空间表达不了**：桥的建造菜单里没有任何防空项，唯一可造的 `c_turret_t1` 实测 `can_attack_air: false` | 观测里没有"敌方有空军"的全局特征；`defence_bonus` 不区分防空与地面炮 | 与课程无关 |

一句话回答用户的三个猜测：

> **三条症状各自对应一个不同的病**，没有一个能靠"改课程"解决：
> ① 是**课程自己的算错**（窗口短于走路时间），修法是把判据换成物理量，**不是加阶段**；
> ②③ 是**桥+观测+奖励的表达能力不足**（菜单漏项、槽位截断、定价反向），课程连碰都碰不到这一层。

**总方针**：把课程降级为纯合法性掩码（已有 `curriculum_mode="mask"`），把缺失的能力补到**桥的菜单 / 观测宽度 / 奖励定价**里，而不是补到课程里。这样既满足"不要过多干预课程"，又让 PPO 真正有牌可打。

> **关于"是不是课程写得太死"这个具体疑问，答案是：不是"死"，是"算错了"**。课程并没有限制 PPO 的宏观决策——`.runtime/policy_freedom.py` 实测证明掩码里不含任何配额或预算，`economy_max_*` 那组参数只约束 stage、不约束策略。真正的问题是 `_issue_late_expansion` 用"20 个决策内占用数没变"当作"这个池子死了"，而 20 个决策只够工程车走 160px——**它把"还在路上"判成了"引擎拒绝"**。

## 1. 症状①：为什么只造得出一个资源提取器

### 1.1 实测证据

`.runtime/income_breakdown.json`（`curriculum_mode="orders"`，seed 88000，2006 决策，Lake 9 个资源池）：

```
dispatched.build_extractor = 33        ← 下了 33 次建造令
occupied_histogram       = {"0": 15, "1": 1991}   ← 1991 个决策里始终只有 1 个池被占
income_by_extractors     = {"0": [18.0], "1": [26.0]}   ← 收入从 18 涨到 26 之后再也不动
```

下了 33 次令，占用数一次没变。**每一次令都在取消上一次的施工。**

> **重要时序说明**：本节分析期间（13:57）工作区被并发修改，`env.py` 的池轮转**已被实现**（新增 `self._expansion_pool_offset += 1`，`env.py:1764-1766`；回执 `slot_id` 改为真实选中的池，`env.py:1771`）。修改前后各跑了一次 `income_breakdown.py`：
>
> | | 修改前 | 修改后 |
> |---|---|---|
> | `dispatched.build_extractor` | 33 | **47** |
> | `occupied_histogram` | `{"0":15,"1":1991}` | `{"0":15,"1":1991}`（**没变**） |
>
> **轮转生效了（33→47），但占用数依然是 1。** 这才是症状①的真正根因——见 §1.2。

### 1.2 根因一（决定性）：重试窗口按"决策数"计，而物理上根本走不到

轮转修好之后，扩张 stage 会把候选池依次试一遍（`free[1]`, `free[2]`, …）。但它的判据是"20 个决策内占用数没变就换下一个池"，而 `STALL_DECISIONS = 20`（`env.py:63`）× `DECISION_INTERVAL = 10`（`IronZeroBridge.java:79`）= **200 tick**。

用真机实测数据算一遍（工程车实际坐标 `(990, 2070)`，来自 `replay-rwpp-20261116-133006-d97c5a.json` 首帧；池坐标来自 `.runtime/ai_orders_probe.json`；工程车 `move_speed = 0.8` px/tick，来自 `.runtime/contract_gap.json`）：

```
stall window = 20 decisions x 10 ticks = 200 ticks

pool  toBuilder  @0.8px/tick   verdict
 0        181        226        reachable (开局用)
 1        918       1147        NEVER arrives in window (3.8x)
 2        875       1093        NEVER arrives in window (3.6x)
 3       1163       1453        NEVER arrives in window (4.8x)
 4       1392       1740        NEVER arrives in window (5.8x)
 5       1488       1860        NEVER arrives in window (6.2x)
 6       1686       2107        NEVER arrives in window (7.0x)
 7       1754       2193        NEVER arrives in window (7.3x)
 8       2083       2603        NEVER arrives in window (8.7x)
```

**开局矿用掉 pool 0 之后，`free = [1..8]`，最近的 pool 1 也要走 918px / 1147 tick，是窗口的 3.8 倍。**

所以 stage 的真实行为是一个**自我挫败的循环**：

```
瞄准 pool 1 → 工程车往东北走 → 200 tick 后判定"停滞" → 轮转到 pool 2
          → 工程车掉头往西南走 → 200 tick 后判定"停滞" → 轮转到 pool 3
          → ... → 走遍 8 个池，每个都只走了约 160px（200tick × 0.8px/tick）
          → 工程车在自家基地附近来回摆动，一个矿也建不成
```

### 1.2b 决定性反证：把窗口从 200 tick 放大到 600 tick，矿就建出来了

本会话期间（14:04）一个并行探针 `.runtime/extractor_pools_probe.json` 恰好做了这个实验：同一张图、同一难度，把每个池的间隔从 2 秒放大到 **600 tick**（约 10 秒游戏时间），其余不变。

```
settle_ticks = 600
occupied_max = 3          ← 三个矿
income_final = 42.0       ← 收入 26 → 42

pools_final occupied:
   pool 0  owner=0  level 1
   pool 2  owner=0  level 1
   pool 3  owner=0  level 1
```

**只改窗口，`occupied` 从恒 1 变成 3，`income` 从 26 变成 42。** 这是对 §1.2 的直接证明：问题不是"引擎拒绝"，不是"池子是死的"，**就是时间不够**。

同时它也暴露了第二层事实：**pool 1 在 600 tick 内工程车纹丝不动**（`distance_before = distance_after = 893.9`，四帧 `walk_samples` 坐标完全相同 `(1091.5, 2069.8)`）。而 pool 2 的工程车确实走了（894 → 471）。所以：

1. **不是所有空池都可建**。pool 1 位于 (1250,1190)，工程车完全不响应——要么被地形挡住，要么该点非法。**轮转是必要的**（不能死守一口池），但**不能靠"占用数 20 决策没变"来判断是哪一种**。
2. **必须区分三种"没变化"**：还在走路 / 到了但引擎拒绝 / 命令根本没被受理（`receipts` 全过程为空，说明这条路径连回执都不产生）。

**这正好是 §1.3 说的"可观测量替错了"的实证**：`occupied` 这一个数同时对应三种完全不同的状态，而 stage 把它们当成同一种（"换个池试试"）。

所以 stage 的真实行为是一个**自我挫败的循环**：

```
瞄准 pool 1 → 工程车往东北走 → 200 tick 后判定"停滞" → 轮转到 pool 2
          → 工程车掉头往西南走 → 200 tick 后判定"停滞" → 轮转到 pool 3
          → ... → 走遍 8 个池，每个都只走了约 160px（200tick × 0.8px/tick）
          → 工程车在自家基地附近来回摆动，一个矿也建不成
```

这**完全解释**了 `occupied_histogram` 恒为 1，也解释了为什么下 47 次令比下 33 次令更糟——**轮转把一个"永远够不到"的问题变成了"永远在走、永远到不了"**。

### 1.3 根因二：把"走路耗时"误判成"引擎拒绝"

上面那个循环的成因，是判据选错了可观测量。stage 的注释（`env.py:1733-1742`）自己承认困难：

> "A progress gate ... is **not** enough here, and the reason is specific to this stage: it aims at a *free pool*, and a pool the builder has been sent to but whose hull the bridge has not streamed yet still reads as free. There is therefore no half-built entity to watch."

所以它退化成"用占用数变化当成功信号"。但"占用数没变"至少对应**四种**完全不同的状态（§1.2b 的探针把后三种都观测到了）：

| 状态 | 探针观测到的样子 | 正确响应 |
|---|---|---|
| 工程车还在走路 | pool 2：`distance 975 → 471`（在缩短） | **继续等** |
| 到了，引擎拒绝 | pool 1：位置完全不动（`893.9` 四帧不变） | 换池 |
| 命令没被受理 | 全过程 `receipts = []` | 修命令格式，不是换池 |
| 正在施工 | `build_progress` 在涨 | 继续等 |

代码把它们全当成第一种的反面（"换池"），于是**把"正在走路"也当成"池子是死的"**。这是典型的"可观测量替错了物理量"：`occupied` 描述的是**结果**，而需要判断的是**过程**。

正确的可观测量是存在的，只是没用：**工程车到目标池的距离**。（桥已经报了工程车坐标，池也报了坐标——两者都在 payload 里，§1.2b 的探针正是靠这两项得出结论的。）

### 1.4 根因三（13:57 修改后仍存在）：动作向量与解码器对 target head 的语义不一致

`_issue_late_expansion` 把**池的全局编号**放进动作向量的最后一位：

```python
# env.py:1711-1720
offset = int(getattr(self, "_expansion_pool_offset", 0)) % max(1, len(free))
chosen_pool = int(free[offset])          # ← 全局 slot id
action = np.array([... , chosen_pool], dtype=np.int64)
```

而 `decode_action` 把这一位当作 **`free` 列表的下标**：

```python
# decoding.py:179-196
free = [index for index, slot in enumerate(slots) if not slot.get("occupied")]
"slot_id": int(candidates[int(target_index) % len(candidates)])
```

**开局时 `free == [0,1,...,8]`，`free[i] == i`，两者碰巧一致，所以第一个矿能建成。一旦 pool 0 被占用，`free == [1..8]`，`free[i] == i+1`，从此每一令都偏移。**

本会话实测（真实 `decode_action`，pool 0 已占用）：

```
free = [1, 2, 3, 4, 5, 6, 7, 8]

offset -> chosen_pool -> decoder actually names
  0 -> 1 -> slot_id=2   MISMATCH
  1 -> 2 -> slot_id=3   MISMATCH
  2 -> 3 -> slot_id=4   MISMATCH
  3 -> 4 -> slot_id=5   MISMATCH
  4 -> 5 -> slot_id=6   MISMATCH
```

两点后果：

1. **回执撒谎**：`env.py:1771` 记录的 `slot_id` 是 `chosen_pool`（课程序列里的意图），而真正下发的是解码后的另一口池。所有依赖回执的诊断都会指向错误的池。
2. **这不是"随便一口空池也一样"可以糊过去的问题**：`free` 随占用状态不断变化，`free[free[offset]]` 的映射不稳定，轮转顺序被打乱；而 stage 的滞停记账（`_expansion_occupied`、`_expansion_ordered_at`）全部基于"我瞄准的是 `chosen_pool`"这个错误前提。

这正是 `menus.py` 模块 docstring 里钉死的那条不变式的反面：

> "If the two derived their own menus they would disagree, and the disagreement is exactly the class of bug that made the real game unplayable"

**修法（一行）**：动作向量里放 `offset`（free 列表下标）而不是 `free[offset]`（全局 id），或者让解码器直接接受全局 id。**两种都行，但不能一边放全局 id 一边按列表下标解。**

### 1.5 根因四：`build_extractor` 不受施工保护

`masks.py:210-234` 定义了 `construction_guard`（"有建筑没造完时，关掉会重定向工程车的指令"），但只有 `build_structure` 被关了：

```python
# masks.py:309-320
if construction_guard and kind == "build_structure":
    kind_mask[index] = False
if construction_guard and kind in {"move_group", "attack_move", "stop", "hold"}:
    ...
```

**`build_extractor` 不在任何一条里。** 实测确认（本会话构造真实晚期状态跑 `build_masks_multi`）：

```
extractor UNDER CONSTRUCTION
  econ kinds open : ['build_extractor', 'noop']
  build_extractor : OPEN   <-- 可以取消自己正在施工的矿场
  build_structure : closed (construction_guard)
```

在 `orders` 模式里，课程每 20 决策重发一次；在 `mask` 模式里，**策略可以每决策重采样一次**，把施工进度打回 0。后者正是当前最新两个 run 用的模式。这条与 §1.2 的窗口问题是**两个独立的杀伤源**，都会让矿建不成。

### 1.6 为什么"还是有一个"能建成

`_issue_opening_extractor` 用的是**另一套**正确判据（`build_progress` 进度门 + 移动平均），并且它瞄准的 pool 0 距工程车只有 181px（226 tick @ 0.8px/tick），**勉强落在窗口内**——这就是为什么开局那个矿能成，而第二个永远不成。其余全部来自 `_issue_late_expansion`，它踩中了 §1.2（窗口不够）+ §1.3（走路误判成拒绝）+ §1.5（无施工保护）三条。

**结论①：这不是"PPO 学不会扩张经济"，是扩张 stage 的**判据物理上不成立**。** 用户看到的是"只建一个矿"，代码里发生的是"工程车在基地附近来回摆动，一个也没建成"。

## 2. 症状②：为什么不打敌方高输出单位

### 2.1 先说结论：不是"不想打"，是"看不到"

取最新真机回放 `runs/platform/real-rwpp-20261116-133006-d97c5a/replays/replay-rwpp-20261116-133006-d97c5a.json`（1200 帧，11991 tick），按当前观测契约（`max_entities=8`）逐帧模拟敌块保留情况：

```
frames 1200
enemy unit-frames visible 8415   dropped 2965   drop rate 26.1%
of the VISIBLE enemy slots, 61.7% are buildings
artillery: visible unit-frames 0,    dropped 500      ← 100% 看不见
```

再看具体一帧（tick 10991，敌方 16 个单位）的流式顺序：

| 槽 | id | 类型 | 是否可见 |
|---|---|---|---|
| 0 | 21 | commandCenter | ✅ |
| 1 | 22 | builder | ✅ |
| 2 | 25 | extractorT2 | ✅ |
| 3 | 26 | builder | ✅ |
| 4 | 27 | landFactory | ✅ |
| 5 | 28 | c_antiAirTurret | ✅ |
| 6 | 29 | scout | ✅ |
| 7 | 64 | airFactory | ✅ |
| 8 | 65 | scout | ❌ **丢弃** |
| 9 | 76 | **c_artillery** | ❌ **丢弃** |
| 10–15 | 77–82 | builder / extractorT1 ×2 / landFactory / builder | ❌ 丢弃 |

**敌方最高输出的地面单位（`c_artillery`，射程 290px，是坦克 130px 的 2.2 倍）在它存在的 500 个 unit-frame 里，没有一个帧进入过策略的视野。** 策略想打它也无从下手：`attack_target` 的 target head 只能索引它看得见的前 8 个敌人。

### 2.2 机制细节：为什么是"排到后面的被丢掉"

`encoding.py:138-150`：

```python
# --- enemy entity block ---
# Deliberately *not* reordered: the target head indexes this list, and the
# bridge streams entities in stable spawn order.
for slot in range(cfg.max_entities):
    if slot < len(enemies):
        feats = _entity_features(enemies[slot], ...)
```

敌块**故意不打乱**（因为 target head 用下标索引它），所以保留的是"引擎 `Unit.unitList` 的出生序"。而 AI 的地图预置建筑 + 工程车 id 最小（21/22/25/26/27/28），**后生产的战斗单位（id 65/76+）永远排在最后**——即"越晚出生、越新的兵，越看不见"。

`prioritise_own` 对己方块做了优先级排序（`features.py`：工厂 > 建筑 > 工程车 > 战斗单位），**但对敌块没有对应处理**，理由是"会破坏 target 映射"。这个理由是成立的，但结论应该是"加宽槽位"，而不是"接受截断"。

### 2.3 根因二：奖励对"打谁"完全无差别

```python
# reward_shaping.py:486
"kills": float(game.kill_bonus) * max(0, previous_enemy_alive - enemy_alive),
```

**按个数计，不看类型。** 杀一门火炮和杀一个工程车都是 +0.25。

唯一带类型信息的稠密项是 `combat_value`，但它按 `max_hp` 定价：

```python
# reward.py
COMBAT_ALIVE_WEIGHT = 0.85
def combat_value(hp, max_hp):
    return max_hp * (0.85 + 0.15 * hp/max_hp)
```

用真机实测血量算一遍：

```
c_artillery      hp=140   combat_value= 140.00
builder          hp=170   combat_value= 170.00      ← 工程车比火炮"值钱"
c_tank           hp=210   combat_value= 210.00
scout            hp=350   combat_value= 350.00
extractorT1      hp=800   combat_value= 800.00
```

**在这套奖励下，"优先杀火炮"比"优先杀工程车"得分更低。** 不是"没有信号"，是**信号方向反了**。

### 2.4 根因三：观测里根本没有"输出"这个量

`features.py` 的 17 列身份特征里有 `can_attack`、`attack_range`、`shoot_delay`、`tech_level`、`can_attack_air`、`is_defence`、`shield`——**唯独没有 damage/DPS**。桥侧的说明（`观测契约补齐_20261115.md` §8.3）已经明确：

> `getTurretDamage` 对 stock 坦克返回 0。引擎把 stock 单位的伤害藏在 `Projectile.reloadTime` 里……我**没有**发一个假的"伤害=0"字段（那会让 policy 以为坦克不痛），所以**伤害依然不可观测**。

所以即使加宽槽位，网络也**无法**从特征里算出"哪个敌人输出高"。它只能从 `attack_range` 反推（火炮 290 > 坦克 130 > 侦察 110），而射程 ≠ 输出。

### 2.5 结论②

症状②是**三重叠加**，且**每一重都必须修**：

1. **槽位不够** → 目标根本不在视野里（100% 丢失）。
2. **奖励无类型** → 即使看得见，也没有梯度指向它（而且 max_hp 定价反向）。
3. **无 damage 特征** → 即使有梯度，也要靠终局回报反向推断约 2000 个决策，样本效率上不可行。

## 3. 症状③：对方有空军，我们一直没有防空

### 3.1 桥的能力菜单里没有任何防空项

`IronZeroBridge.buildableNamesFor`（L1050-1118）报出的建造菜单，实测于 `[p2]Lake (2p)`（`.runtime/q1_build_menu.json` + `q3_factory_menu.json`）：

```
reported can_build = landFactory, airFactory, seaFactory,
                     laserDefence, repairbay, experimentalLandFactory,
                     extractor, turret
```

Python 侧最终可选的 `build_menu`（去掉 pool-only 的 `extractor`）= **7 项**：

```
['landFactory', 'airFactory', 'seaFactory', 'laserDefence',
 'repairbay', 'experimentalLandFactory', 'turret']
```

**没有 `antiAirTurret`。** 而敌方 AI 在同一张图上实际建了 `c_antiAirTurret`（上面 1200 帧回放里出现 1008 个 unit-frame）。也就是说：**敌人有这个建筑，我们的动作空间说不出它的名字。**

为什么漏了？两条路径都过不去：

1. **注册表扫描**：`UnitType.antiAirTurret` 确实在 `UnitType.values()` 里（`E:\IronZeroBuild\game-lib-src\...\UnitType.java:29`），但 `builder.getSpecialAction(antiAirTurret, false)` 返回 null → 被 `continue` 跳过。
2. **规范名补探**：`CANONICAL_BUILD_NAMES` 只有三个名字：

```java
// IronZeroBridge.java:212-216
private static final String[] CANONICAL_BUILD_NAMES = {
    "extractor",
    "landFactory",
    "turret",
};
```

`extractor` 当初就是这么补进去的（注释 L1088-1098 记录得非常清楚：注册表扫描漏了 `extractor`，但**同一个 builder 实际接受它**）。**防空从来没被补进这个数组，所以"引擎到底接不接受 antiAirTurret"这个问题，从来没有人问过。**

### 3.2 唯一造得出来的防御建筑打不到空

`turret` 造出来是 `c_turret_t1`，实测（`.runtime/q2_turret.json`）：

```json
{"unit_type":"c_turret_t1", "hp":700.0, "is_defence":true,
 "can_attack":true, "can_attack_air":false, "attack_range":165.0}
```

`can_attack_air: false`。而 `laserDefence` 是**导弹拦截器**，`canAttack()` 返回 false（`masks.py` / `menus.py:99-104` 有实测引用），也不打飞机。

**所以在当前动作空间里，我们这一侧不存在任何能打飞机的选项。** 用户看到的"对方造空军了我们一直没有防空"，在代码层面不是"没学会"，是**"没有这个选项"**。

### 3.3 次要根因：观测里看不出"敌方有空军"

- 每单位有 `is_air_unit` / `can_attack_air`（`IronZeroBridge.java:1477, 1541`），但**敌块只有 8 槽且 61.7% 被建筑占满**——空军能不能挤进前 8 取决于出生序，属于运气。
- `global_state` 15 维里**没有任何**"敌方空中单位数 / 我方防空能力"的汇总特征（`encoding.py:88-112`）。策略要自己从 8 个槽里"数"，而这些槽大半是建筑。
- 奖励里 `defence_bonus`（0.10）对**任何**防御建筑一视同仁（`config.py:292-299`），空中威胁造成的损失与地面威胁等价（`losses` 按个数）。

### 3.4 结论③

症状③的**阻断性根因是动作空间**（约 70%），**观测汇总缺失**（约 20%）和**奖励不区分威胁类型**（约 10%）是次要的。修动作空间是**单点、可验证、低风险**的改动。

## 5. 方案：六条工作流

设计原则：
1. **不新增课程阶段**；课程只保留"合法性掩码"职责（`curriculum_mode="mask"`，已实现）。
2. 每一条都必须有**真机可验证的通过标准**，不接受单测代替（`观测契约补齐_20261115.md` §3.7 的教训：契约层 bug 只能用协议层手段验证）。
3. 改动**追加在尾部**（观测列、掩码键），保护已有 checkpoint 的平移映射。

### A. 观测宽度：把 8 槽换成"跟得上敌人"的槽（P0，解锁 ②③）

**改动**
- `micro_config.py:117-118`：`max_entities` / `target_slots` 默认值从 8 / 9 提到 **32 / 33**。
  - 依据：本次回放敌方峰值 16，`runs/platform/twoslot-mask-long/eval_report.json` 记录 `enemy_alive` 峰值 **41**。32 覆盖 78%，或按 `--max-entities 48` 做一次上限扫描。
- `train_rwpp.py:79-84`：`--max-entities` 与 `--units-per-team` 解耦，并在 reset 时**断言** `len(visible_enemy_entities) <= max_entities`，超出时**计数并上报**（`info["truncated_enemies"]`），不允许静默截断。
- 新增 `pipeline` 度量：每局记录 `enemy_unit_frames` / `enemy_dropped` / `enemy_dropped_types`，写进 `eval_report.json`。

**验收**
- 同一张图、同一 AI 难度，`enemy_dropped / enemy_unit_frames` **从 26.1% 降到 < 2%**。
- `c_artillery` 在其存在帧中的**可见率 ≥ 95%**（当前 0%）。
- 观测维度变化需同步 checkpoint 迁移测试（`tests/test_checkpoint_stride_migration.py` 已有机制，追加一条 32 槽用例）。

**不做的事**：不改变敌块排序（target head 依赖流式顺序）。宽度是唯一不破坏语义的解法。

### B. 建造菜单补全防空（P0，解锁 ③）

**改动**
- `IronZeroBridge.java:212-216` 的 `CANONICAL_BUILD_NAMES` 追加 `"antiAirTurret"`（以及 T2 变体，若 `UnitType` 里存在）。
- 用与 `extractor` **完全相同**的解析路径（`resolveUnitType` + `getSpecialAction`），所以：引擎不接受就自动不进菜单，不会造成 `BUILD_UNAVAILABLE`。
- `menus.py:118-121` 的 `is_defence_type` 标记已含 `"antiair"`，无需改动；但需补一条**防空专有判据**（见 D）。

**先做的一次性探测（半小时，必须先跑）**

用现有探针骨架（`q1_build_menu.py` 同构）回答一个从未被问过的问题：

```
structure_type ∈ {antiAirTurret, antiAirTurretT2, aaTurret}
for each: 下一条 build_structure 令，等 400 tick
期望：accepted=true，出现实体且 can_attack_air=true
```

**验收**
- 真机 `build_menu` 包含防空项；造出的实体 `can_attack_air: true`。
- `menus.is_defence_type` 对防空名返回真（当前 `turret` 分支已覆盖，但要加显式断言）。
- 回归：不破坏现有 7 项菜单的顺序（target head 下标稳定性）。

### C. 奖励：把"打谁"从无差别计数改成威胁加权（P1，解锁 ②）

**改动**
1. 新增 `threat_value(unit)`（放 `rwpp/reward.py`，与 `combat_value` 并列）：
   ```
   threat = w_out * output(unit) + w_range * range_norm(unit)
          + w_air * can_attack_air(unit) * air_multiplier
   其中 output = 有 damage 字段就用，没有就用 attack_range 与 shoot_delay 的组合代理，
        并显式标注 "proxy" 供后续替换（见 E）
   ```
2. `reward_shaping.py:486` 的 `kills` 改为 `kill_bonus * Σ threat_value(被击杀单位)`，**保留旧 term 名与 `episode_components` 键**，只是内部从计数改成加权求和。
3. `losses`（L487）对称：按 `threat_value` 加权，"丢一门火炮"比"丢一个工程车"更痛。
4. `combat_value` / `combat_value_potential` 的定价从 `max_hp` 改为 `threat_value`。**保持 potential-based 形式**（`γΦ(s')-Φ(s)`），所以策略不变性不被破坏。
5. 新增 `defence_bonus` 分支：防空建筑按 `denied_threat` 定价（它挡住的空中威胁价值），而不是与地面炮同一个 0.10。

**验收**
- 单元级：给定真实血量表，`threat_value(c_artillery) > threat_value(builder)` **必须成立**（当前反了）。
- 差分实验：用同一个脚本策略跑两组（"优先集火火炮" vs "优先集火工程车"），**累计 reward 差 ≥ 1.5×**。这一条是"知道疼"的直接证明。
- 不改变终局权重：`win_reward` / `timeout_penalty` 数值不动。

### D. 掩码：施工保护补齐 + 防空可见性（P0，解锁 ①③）

**改动**
1. `masks.py:309-320`：把 `build_extractor` 加入 `construction_guard` 的关闭集合。
   - 现状实测：矿场施工中 `build_extractor` **仍然开放**，策略可自毁进度。
   - 注意与 `curriculum_owns_build_kinds` 的既有联动（`config.py:698-700`）：mask 模式下课程不发令，所以必须保留"先建第一个矿"的可行性。正确做法是：**只在一个矿/工厂正在施工时关闭 `build_extractor`，而不是永久关闭**。
2. `encoding.py`：`global_state` **尾部追加 2 维**（保持旧列偏移不变）：
   ```
   13. enemy_air_count / 8
   14. own_can_attack_air_count / 8
   ```
   `global_dim: 15 → 17`。旧 checkpoint 由既有迁移逻辑补零。
3. `masks.py:447-455`：`economy_menu_sizes` 已把 `build_menu` 长度纳入 target head 宽度；确认加宽后**防空项的下标能被 target head 表达**。

**验收**
- 矿场施工中 `build_extractor` 关闭；施工完成后重新开放。单测 + 真机各一条。
- `global_dim` 变更后旧 checkpoint 能加载且不报形状错。
- `target_mask` 中防空项的槽位可采样并被解码成该名字（"掩码开放"与"解码可命名"是同一个陈述——这是 `menus.py` 文档里钉死的不变式）。

### E. 让"输出"变得可观测（P1，②③ 的长期解）

引擎限制是真实的（`观测契约补齐_20261115.md` §8.3）：stock 单位的伤害藏在 `Projectile.reloadTime` 里，而同一个字段在冷却时是"装填时间"。所以**不要在桥里编一个 `damage` 字段**。

三条可行路径，按成本排序：

1. **类型级静态表（推荐）**：启动时遍历 `UnitType` + 其 ammo/projectile 定义，算出**每单位类型**的 `dps_proxy`，缓存一次，作为实体特征追加列（第 18 列，`type_features: 17 → 18`）。不是每帧扫描，成本可忽略。若某类型算不出来，该列写 `0.0` **并在 `info` 里列出无法定价的类型**——绝不静默当 0。
2. **运行时反推**：遍历 `Projectile.allProjectiles` 反推伤害。成本高（每帧扫描），对未开火单位无解。**不建议**。
3. **接受不可观测**：在文档里明确"输出只能从 `attack_range` + `shoot_delay` 代理"，并让 `threat_value` 用代理（C 的第 1 条已留口子）。

**验收**：路径 1 落地后，`threat_value(c_artillery) > threat_value(c_tank) > threat_value(builder)` 由实测 dps 支撑，且 `info` 中"无法定价类型"列表为空（Lake 全类型可定价）。

### F. 把扩张 stage 的判据换成物理量（P0，解锁 ①）

**先说清楚为什么"已经是课程 bug"却不算"干预课程"**：这一条修的是**一个算错的判据**，不是**加一层策略**。修完之后课程对 PPO 的自由度**一点没变**（`policy_freedom.py` 已证明掩码不含配额），只是它不再把自己撞死在墙上。这与"给课程加阶段、加阈值"是两件不同性质的事。

**已发生（13:57 并发修改，需复核而非重做）**
- `env.py:1764-1766` 已实现 `_expansion_pool_offset += 1`（stall 时轮转）。
- `env.py:1771` 回执 `slot_id` 已改成真实选中的池。
- 效果：`build_extractor` 33 → 47 次。**但 `occupied_histogram` 仍是 `{"0":15,"1":1991}`。**

**仍必须改的核心**

**(a) 对齐 target head 语义（1 行，最先做）**

动作向量放 `offset`（free 列表下标）而不是 `free[offset]`（全局 id），**或者**让解码器接受全局 id。二者选一，但不能一边放全局 id 一边按列表下标解。修完后 `decode_action` 命中的必须是 `chosen_pool` 本身。

**(b) 把停滞判据从"决策数"换成"工程车是否在接近池"**

```python
# 概念示意，不是最终代码
距离_now  = hypot(builder.x - pool.x, builder.y - pool.y)
距离_prev = getattr(self, "_expansion_builder_distance", None)

if 距离_prev is None or 距离_now < 距离_prev - 1.0:
    # 在接近：一切正常，继续等。不要按决策数计时。
    self._expansion_builder_distance = 距离_now
    self._expansion_stalled = 0
    return []
# 距离不再缩小：可能到岸了在造，也可能被卡住
self._expansion_stalled += 1
if self._expansion_stalled < STALL_DECISIONS:
    return []
# 真正停滞了，才考虑换池
```

关键点：

1. **窗口必须容纳走路时间**。`STALL_DECISIONS` 的本质是"容忍多久没进展"，而"没进展"的定义必须排除"正在赶路"。合理值：`ceil(距离 / move_speed / 10) + 施工tick/10`。上表已给出每口池的走路 tick（最近 1147，最远 2603）。
2. **目标池一旦选定就锁定**，直到"建成"或"确认引擎拒绝"才允许换。**当前每次 stall 都换池，等价于让工程车永远在路上**——这是 33 次令变 47 次令却更糟的原因。
3. **回执要区分 `accepted` 与"施工中"**：`accepted: true` 不等于有进展（`ab_reissue.py` 已实测：`build_progress` 恒 0 而回执全 true）。
4. **`build_extractor` 加进 `construction_guard`**（见 D.1），否则 mask 模式下策略每决策都能把它打回 0。

**验收（真机，硬指标，必须两条模式都跑）**

| 指标 | 当前（auto/200tick） | 600 tick 探针实测 | 目标 |
|---|---|---|---|
| `occupied_histogram` 最大值 | 1 | **3** | **≥ 3** |
| `income` | 26.0 | **42.0** | **≥ 42.0** |
| `build_extractor` 下发次数 / 建成的矿 | 47 / 1 | — | **≤ 3 / 1**（不再空转） |
| 工程车最终位置 | 基地附近来回摆 | 停在 pool 3 旁 | **停在最后一个建成的矿旁** |

最后一条是最直接的证据：如果工程车还停在基地附近，说明它一次都没走到位。

**注意目标值不要写死成"6 个矿"**：§1.2b 的探针显示 9 个池里只有 pool 0 / 2 / 3 能建成（pool 1 的工程车完全不响应），**可达上限是地图性质，不是策略性质**。验收应该问"是否达到了该地图的可达上限"，而不是"是否建满了配置的 6 个"。

## 7. 依赖顺序与工作量

```
F2a（对齐 target head 语义 0.5h）── P0，1 行，最先做
   │
F2b（停滞判据换成距离 2h）───── P0，依赖 F2a（语义不对，距离记账也是错的）
   │
B（防空探测 0.5h）───────────── P0，独立，先跑，把猜测变事实
   │
D.1（掩码施工保护 1h）───────── P0，独立，可并行（F2b 的配套）
   │
A（观测宽度 4h）─────────────── P0，阻塞 ②③ 的验证
   │
D.2（global 补 2 维 1h）─────── P1，依赖 A
   │
C（威胁加权奖励 6h）─────────── P1，依赖 A（先看得见，加权才有意义）
   │
E（类型级 dps 表 8h）────────── P2，可延后，C 先用代理
   │
   └─→ 全量训练 + N≥20 评估（按 docs/训练问题日志.md §3 的验收清单）
```

**顺序理由**

1. **F2a 只要一行，却是一切的前提**：语义不对的话，轮转、滞停记账、回执诊断**三者全部建立在错误前提上**，后两项修了也会被掩盖。
2. **B 和 D.1 都是"半小时到一小时、独立、可用现有探针立刻验证"**，可以并行插在 F2b 期间。
3. **A 是 ② 和 C 的前置**：观测宽度不改，`threat_value` 加权了也覆盖不到火炮，"优先打高输出"的差分实验跑不出结论。
4. **E 放最后**：C 允许先用 `attack_range` + `shoot_delay` 代理；先让闭环成立，再提高精度。
