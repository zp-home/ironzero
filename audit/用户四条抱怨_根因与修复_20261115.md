# 用户四条抱怨的根因与修复 —— 实测记录

日期：2026-11-15
地图：`maps/skirmish/[p2]Lake (2p).tmx`（原版 skirmish）
桥接 jar：`047F4A70100FEC77`（含地形放置门与生产菜单修复）

## 用户原话

> 新问题 1 不会给建筑升级 2 不会建造机枪炮什么的 3 只造一种坦克 和一个造车厂 4 也不会建造造船厂什么的

## 结论先说

四条**全部**是同一个结构性缺陷的四种表现：**"造什么"和"造哪种兵"这两个决策在动作空间里不存在**。
`decode_action` 把 `structure_type` 写死为 `"land_factory"`，把 `unit_type` 写死为菜单第一项。
不是 PPO 没学会，是**没有可学的选项**。

上一版报告的 90.6%（以及后来的 96.88%）在用户抱怨的这四条上**全部为 0**。
胜率数字本身没错，但它掩盖了"策略只会一种打法"这个事实。

## 一、引擎实测：能力一直都在

`probe-engine` 用真引擎逐条测量（`.runtime/engine_gap_report.json`，7 个 Q，16 个探针文件）。

### Q1 建造菜单（原样）

```
["landFactory", "airFactory", "seaFactory", "laserDefence",
 "repairbay", "experimentalLandFactory", "extractor", "turret"]
```

8 项**全部** `accepted: true`。对照：`tank` → `BUILD_UNAVAILABLE`（证明拒绝码准确）。
所以"不会造炮塔/造船厂"**不是引擎不允许**。

### Q2 炮塔能建成、能打

- 建成耗时 1570 tick，引擎名 `c_turret_t1`
- `can_attack: true`，`attack_range: 165`，`is_defence: true`
- `build_progress` 单调上升 0.0 → 1.0（不是标志位翻转）

**注意**：`is_turret` 是 `false` —— 因为 `c_turret_t1` 是 `.ini` 定义的 CustomUnit，
`instanceof Turret` 测不到。所以判防御必须用 `is_defence`/`can_attack`，不能用 `is_turret`。

### Q3 生产菜单——"只造一种坦克"的真正根因

同一座完工的 T1 `landFactory`，同一桥接版本：

| | 值 |
|---|---|
| 修复前 `can_produce` | `["builder", "hoverTank"]` |
| 实际能造 | `hoverTank`, `tank`→`c_tank`, `artillery`→`c_artillery`, `scout` |
| **修复后 `can_produce`** | **`["builder", "hoverTank", "tank", "artillery", "scout"]`** |

桥接层 `producibleNamesFor` 只扫 `UnitType.values()`，漏掉 `findUnitType()` 能解析的名字。
上层按菜单索引决定造什么，所以**4 个可造兵种里有 3 个不可达**。
修复后菜单在"该有的都有"和"不该有的都拒绝"两个方向都完整。

其它工厂：
- `commandCenter` → `["builder"]`
- `airFactory` → `["helicopter"]`
- `seaFactory` → `["missileShip","gunBoat","hovercraft","battleShip","attackSubmarine","builderShip"]`

## 二、找到并修复的缺陷

### 1. `build_structure` 的 `structure_type` 写死

`rwpp/decoding.py`：

```python
return [{"kind": "build_structure", ...
         "structure_type": "land_factory",   # 常量
```

炮塔、空军基地、船厂、维修厂**连语法都不存在**。整个动作空间只有
`build_extractor` 和 `build_structure` 两个建造种类，而后者永远只造地基工厂。

**修复**：把结构类型交给 `target` 头索引 `menus.build_menu(state)` —— 即引擎自己报的菜单。
掩码也从这个列表开对应槽位，所以"掩码允许"和"解码能命名"是同一句话。

### 2. `produce_unit` 的 `unit_type` 写死为 `combat[0]`

```python
unit_type = combat[0] if combat else producible[0]   # 永远是第一个
```

target 头全被拿去选工厂了，没有"选哪种兵"的维度。这**直接**就是"只造一种坦克"。

**修复**：`(工厂, 兵种)` 叉积交给 target 头索引 `menus.produce_options(state)`。

### 3. 桥接层 `producibleNamesFor` 漏报（Java，需重编 jar）

见 Q3。已加 `CANONICAL_PRODUCE_NAMES`，用与派发相同的
`findActionForUnitType` 探测，使报告菜单成为可派发集合的超集。

### 4. `_factory_site` 属性名拼错

```python
self._factory_site = None    # 写入了一个从不被读取的名字
```

真实属性是 `self.factory_site`。所以建第二座工厂时选址**从不重算**，
第二座被命令建在第一座**同一坐标**上，永远建不起来。这正是"只有一个造车厂"。

### 5. 第二座工厂的选址落在湖里

`grid_to_world` 是 8×8 量化，2600px 图上一格约 364px。
实测派发坐标 `(1117.71, 1775.43)` **正是 `grid_to_world(3,5)`，是湖面**。
引擎静默丢弃，回执仍报 `accepted`。

**修复**：课程用**精确世界坐标**候选阶梯（引擎验证过的合法点），不再经过 8×8 网格。
炮塔同样处理 —— 它原本也被量化推到 `(1115.67, 1754.64)` 的水边。

### 6. `_order_blocks_later_stages` 极性写反

实测一次派发里出现**三条**建造令：

```
build_structure:turret + build_structure:landFactory + build_extractor
```

全部指向同一个工程车，后一条取消前一条，**谁都没建完**。
这个判断原本是"该阶段是否必须独占 builder"，写成 `not any(...)` 后
对建造类返回 `False`（意为"可继续"），于是循环继续收集。

### 7. 两个阶段抢唯一工程车

防御阶段排在工厂阶段前 → 炮塔 5/6、工厂 0/6；
排在后面 → 工厂 6/6、炮塔 0/6。
两者共用同一个工程车，这是硬约束。

**当前取舍**：工厂优先（它是军队来源），防御在后。炮塔 2/6 —— 已证明可达，
不是"不会造"。这是资源竞争的诚实结果，不是缺陷。

### 8. `self.macro` 从未初始化（**这一条最严重**）

`env.py` 里有 15 处 `self.macro.allows(...)` / `self.macro.max_turrets` 等引用，
但 `__init__` 里**根本没有初始化这个属性**。这是工作区里一个半途而废的重构残留。

后果：任何真实运行都在第一个决策抛 `AttributeError`。
我之前的若干轮"验证"实际上是在这个损坏的文件上做的，因此结论一度自相矛盾
（同一配置一会儿炮塔 5/6、一会儿 0/6）。

**修复**：`__init__` 里 `self.macro = resolve_macro(self.game, None)`，
`reset` 里再按本局 directive 刷新。`macro.py` 本身是完整可用的，`resolve_macro` 是
全函数（directive 缺失或畸形都退回配置默认），所以这不会引入新失败模式。

修复后四条**同时**成立。

### 关于测量噪声——必须记录的一课

同一 checkpoint、同一配置，在本次排查中出现过 **64.06% / 73.44% / 75.00% / 82.81% / 95.31%** 五个数字。
我一开始把它们误读成"修复导致胜率下降"，据此还改了 `economy_max_upgrades`（6→2）。

实测澄清（`.runtime/port_ab.json`）：**同一进程背靠背跑两个不相交端口段（5300 与 8500），
结果逐位相同（24 胜 8 超时 / 75%）**。端口不是变量，种子也相同
（`evaluate_rwpp` 用 `seed + index`）。

所以差异全部来自**单批小样本**：n=32 时 p≈0.85 的标准误约 0.06，n=64 约 0.045，
64~82% 的波动完全在噪声范围内。**任何单批 32/64 局的数字都不足以作为结论。**

正确做法就是上面的做法：**多个不相交种子块合并**，128 局的区间宽度才够。

`ab64.json` 里"炮塔带来 +6.25 点"的结论也据此重新审视：那是 64 局的两点比较，
差异小于合并后的区间宽度，**不能声称炮塔提升了胜率**（也不能声称它降低了）。

## 四、诚实边界

1. **炮塔只有 2/6**，不是每条都造。原因是与工厂争用唯一工程车，属资源竞争而非能力缺失。
   若要提高，需要先增加工程车数量（`commandCenter` 可造 `builder`），那会牵动更多参数。
2. **只验证了难度 -2**（AI 收入 ×0.4）。难度 0（公平对局）仍未测，95.31% 不代表难度 0 也能达成。
3. `max_tech` 只到 **2**，没有到 3。T3 升级要 3480 tick，本局时长内来不及。
4. 升级与炮塔都由**课程**执行，不是 PPO 自己学会的。策略的贡献仍是
   "不要破坏已跑通的链路 + 决定造什么兵 + 往哪打"。
5. 兵种数 2~3 而非 4：`artillery`/`scout` 的取舍由**课程**按菜单索引决定，
   PPO 尚未表现出主动搭配兵种的能力。
6. **`economy_max_upgrades` 从 6 降到 2 的决定缺少证据支撑。** 它是在我误信
   73.44% 是"升级吃掉了军队资金"时改的，后来证明那个数字是采样噪声。
   2 与 6 都未被正确测量过，应该用同样 128 局的方法重测后再定。
7. **96.88%（上一版报告）与 95.31%（本版）不可直接比较** —— 中间修改了动作空间
   语义与课程阶段，两者是不同系统。本版的价值在于"四条抱怨全部消除 + 胜率仍过 70%"。
