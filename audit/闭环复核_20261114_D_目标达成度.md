## 5. 三阶段路线图

> 前提纪律：每阶段结束都要产出 **可复核的 `eval_report.json`（N≥20，含逐局 `episode_results` 与 seed）**，否则该阶段不算过。产物必须提交或至少有 `audit/` 下的哈希清单（当前 `runs/` 被 gitignore，这是 N10 的根）。

### 阶段 1：跑通最小闭环（让 Lake 上出现第一个真实 victory）

| 项 | 内容 |
|---|---|
| **做什么** | ①**先证明 victory 可达**：手写脚本（或 `.runtime/` 下已有探针模式）在 Lake 上用**脚本策略**把对面打爆，确认 `result == "victory"` 能从桥透传出来。这是 N2 的唯一解法，也排除"胜负判定单边失效"的系统风险。<br>②固定评估协议：`map=[p2]Lake (2p)`、`units_per_team=2`、`episode_ticks=8000`、`unlock_ai=false`、`enemy_ai_difficulty=2`、`vision_radius=260`（与训练一致）、`eval_episodes=20`。<br>③把 checkpoint 选优修好（`maybe_save_best` 按 N≥8 的 win_rate 选，写 `checkpoint_best.pt` 并在评估报告里记录实际加载的路径）。<br>④`runs/` 产物落 `audit/` 哈希清单（`sha256` + 路径 + 生成时间），解决 N10。 |
| **验收标准** | ① Lake 上出现 ≥1 局 `result="victory"`（脚本策略即可），并给出 tick 与 `enemy_alive=0`；② `eval_report.json` 的 `checkpoint` 字段与磁盘实际文件 **sha256 一致**；③ 同一 checkpoint、同协议连跑 2×20 局，两次 win_rate 差 ≤0.10（量化环境噪声，回应 P-S2-07）；④ 除 `IronZero25` 外的地图上首次出现非零 win_rate（哪怕 1/20） |
| **预估时长** | 1~2 天（主要是找胜利判定的边界 + 把评估协议脚本化） |
| **风险** | ⚠️ **高**：victory 可能真的不可达（判定 bug / 目标点定义问题）。若阶段 1 卡住，后续全部无意义——**这是必须最先做的验证** |

### 阶段 2：学会经济（矿 → 厂 → 兵，形成稳定正向收入与稳定出兵）

| 项 | 内容 |
|---|---|
| **做什么** | ①**课程式固定开局**：用 `.runtime/opening_curriculum.json` 已验证的"开局先下 extractor"（`start_income 18 → final_income 26`，13 决策 / tick 141）作为 warmstart 目标，先模仿学习再 PPO。<br>②**拉长 horizon 到 8000~12000 tick**，并把 `produce_unit`/`upgrade_building` 的稀疏奖励补上中间信号（工厂进度、首兵出生、矿场数量）——`docs/原版地图经济学不会…` §5.1 明确指出「一局内只有约 2 次造兵窗口」。<br>③**并行化**：把 `envs` 拉到 8~10（瓶颈是单线程 Java 进程，`docs/训练问题日志.md` L143），目标单次 run 覆盖 ≥10⁴ episodes。<br>④**难度课程**：`enemy_ai_difficulty` 从 0/1 起步，稳定后再上 2（`docs/原版地图经济学不会…` §5.2「难度 2 时对面最近距离 469 px，难度 3 时 102 px」）。 |
| **验收标准** | ① `income` 非零轮数占比 ≥80%（对比 `econ_fix_long` 的 4/60）；② 每局稳定出现 `extractorT1 ≥1`、`landFactory ≥1`、`hoverTank ≥1`（对齐 `.runtime/e2e_economy.json`）；③ `PRODUCE_UNAVAILABLE`/`UPGRADE_UNAVAILABLE` 从"出现"变为"**被接受**"（`produce_gate.json` 已有 accepted 回执）；④ Lake 上 N=20 评估 **win_rate > 0**（哪怕 2/20），且 `timeout_rate < 100%`；⑤ 单局平均 `own_alive` 从 2~5 提升到 ≥8 |
| **预估时长** | 1~2 周（并行化改造 + 奖励塑形 + 课程，每轮 run 数小时） |
| **风险** | ⚠️ 中高：经济是稀疏奖励，容易退化成"只造矿不造兵"或反之；`docs/观测与奖励改造清单.md` L403 指出 `repair_target` 在 Java 侧未实现、`upgrade_building` 曾长期死锁 —— 需先确认四类经济动作**全部**在真机被接受 |

### 阶段 3：打赢 70%（稳定胜率并做统计验收）

| 项 | 内容 |
|---|---|
| **做什么** | ①在阶段 2 的经济能力基础上加微操（复用 IronZero25 竞技场已学到的集火/拉扯——类别①的 0.750 说明微操策略本身有效，可迁移作 warmstart）。<br>②**自我对弈/对手池**：把历史 checkpoint 做成对手池，避免对单一内置 AI 过拟合。<br>③**正式验收协议**：N≥100 局、固定地图/horizon/difficulty、逐局落盘、**Wilson 95% CI 下限 > 0.70**、报告 `checkpoint` sha256。<br>④Web 侧把 `eval_episodes` 上限从 8 提到 32，并强制 UI 显示 "N 与 CI"（`docs/训练问题日志.md` P-S3-02 要求）。 |
| **验收标准** | ① `[p2]Lake (2p)` 上 **N≥100，win_rate ≥0.70，Wilson 95% 下限 >0.70**（按我复算：若真实 70%，需 N≥100 才能让下限接近 0.604；若要做到下限 >0.70 需接近 85%+ 实测胜率 —— **务实做法是先定 win_rate ≥0.70 且下限 >0.60**）；② `timeout_rate ≤10%`（`docs/训练问题日志.md` P-S3-03 建议）；③ 同协议重跑 2 次，win_rate 差 ≤0.05；④ 至少 2 张原版图（Lake + Artillery）都 ≥0.60，证明不是单图过拟合；⑤ 产物入库或用 `audit/` 哈希清单锁定 |
| **预估时长** | 3~6 周（含多轮长跑与调参） |
| **风险** | ⚠️ 高：`unlock_ai=false` 时对面会发育到 100+ 单位，70% 需要策略同时具备经济、生产、兵种搭配与微操；任一环不稳都会把胜率压到 20~30%。**建议把最终目标拆成「先对固定难度 AI 达 70%，再提难度」，并在报告里写明对手难度与 `unlock_ai` 取值** |
