## 0. 一句话结论

**「点一次训练」的传输链路今天能通（宿主 8300 服务在 19:43:53 已启动，我实测 200），但用户在 Web 上仍得不到他说的那套闭环**：前端表单上有控件的 14 行参数**确实都透传到了宿主**，可**经济/建筑/生产这条主线的三个关键开关（`unlock_ai` / `win_mode` / `enemy_ai_difficulty`）用户根本设不了**；「数据采集」页的地图下拉是**假的**（不传 `map_path`，永远跑 Lake）；原版图上默认的「预热策略」会**静默套用 25v25 的 BC 权重**；而原版图上「双方血量比」指标**口径失效、恒为 100%/100%**——所以即使训练跑完，用户看到的曲线也不描述他想学的东西。

## 2. 逐题回答 task-3 的 6 个问题

### Q1 前端表单到底暴露了哪些训练参数

见 §1 表。要点：

1. **地图下拉确实含原版 `maps/skirmish`**：`feMaps.js:85-97` 把 `feInferMapList()`（`feMaps.js:15-18` 允许 `skirmish/challenge/testing/ironzero`）里除 IronZero* 之外的图放进「原版实机地图（遭遇战 / 战役挑战）」分组。我 GET `/api/maps` 实测返回 **89 张**，其中 `skirmish=48`、`ironzero=5`、`challenge=7`，`[p2]Lake (2p)` 在册（`relative=maps/skirmish/[p2]Lake (2p).tmx`，2600×2600）。
2. **`units_per_team` 在原版图上是写死的 2**（`model.js:41-47`，注释「stock skirmish maps start both sides with exactly one command center and one builder」）。用户无法在原版图上改默认部队量——但对原版遭遇战来说这恰恰是「默认部队」的正确含义，属于设计选择而非缺陷，**前提是「默认部队」= 地图自带部队**；若用户想要「25 辆坦克在原版图上」，UI 无路可走。
3. **`physics_ms` 被前端写死**：`ppoRun.js:223` 无条件发 16。注释解释了原因（trainer 默认值漂移过），但用户既看不到也改不了。
4. **风险点（半成品）**：`physics_ms`、`init_mode` 解析、`fePpoStartHint` 都是**未提交改动**（见 §5 的改动清单与半成品判定），逻辑本身自洽，但依赖宿主 /jobs 回报的 `init_mode`/`init_checkpoint`（`handler.py:136-139` 新增）——**只有在 8300 进程是改动后启动的才有这两个字段**。宿主 8300 当前进程（PID 23264）启动于 19:43:53，晚于源码 mtime（`launch.py` 17:02），所以字段在；但 README 自己就点名了这个坑（`scripts/rwpp_service/README.md:20-31`「改完 `.py` 不重启…前端会收到和源码对不上的 400」）。
