# 对局加速契约（2026-11-15）

> 本文件是本次「再快一点」改造的**唯一契约**。所有并行工作都必须严格按此实现，
> 不得自行改名字、改默认值或改范围。

## 0. 实测背景（先看数字，再改代码）

16 逻辑核 / RTX 4070，Lake 小图，`physics_ms=16` 固定仿真步长：

| 配置 | 6000 tick 墙钟 | tick/s | 相对真实时间 |
|---|---:|---:|---:|
| `frame_ms=16`（真实时间） | 100.4 s | 59.8 | 1× |
| `frame_ms=4` | 30.5 s | 196.8 | 3.3× |
| `frame_ms=2` | 15.4 s | 390.6 | 6.5× |
| `frame_ms=1`（当前「极速 16×」） | 9.35 s | 641.7 | **10.7×** |
| `frame_ms=0`（完全不 sleep） | 3.78 s | 1587 | **26.5×** |

结论一（免费，零保真损失）：**`frame_ms=1` 里 68% 的墙钟是 `Thread.sleep` 的唤醒开销**
（每帧 0.93 ms 固定唤醒 + 1 ms 预算，实测回归 `sleep_per_frame(N) ≈ 0.93 + 0.99N`）。
把 sleep 完全去掉是 **2.2–2.5×**，而且**不改仿真**——只要 `physics_ms>0` 把 delta 钉死，
`frame_ms` 就只剩 pacing 作用（`IronZeroBridge.java:382-383`）。

结论二（要开关，改保真）：引擎自己支持快进。`updateFrameInternal` 的 `var1` 被
`RWGameEngine.java:1203` 钳到 `3.0`，所以 `physics_ms` 只有 16→50 这一段有效（3×）；
再往上必须走引擎原生 `gameSpeed`（`updateAllGame` 里 `var1 *= gameSpeed`，
单机/非 replay 生效，官方 UI 允许到 64）。实测 IronZero25 竞技场：
`physics_ms=16` → 418 帧分出胜负 / 4.06 s；`physics_ms=50` → 133 帧 / 2.71 s。

结论三：`frame_ms` 的 0 目前被 `effective_frame_ms()` 钳到 1，理由写的是
「0 ms 会让引擎用零步长推进」——**那是 `physics_ms` 还不存在的年代**的诊断。
`physics_ms>0` 时该理由已不成立，钳位必须放宽（见 §2）。

## 1. 桥接新增参数（Java，Lead 负责）

| 参数 | 默认 | 范围 | 语义 |
|---|---|---|---|
| `--fast-forward N` | `1` | 1..32 | 地图加载完成后设 `engine.gameSpeed = N`。**每 tick 推进 N 倍游戏时间**，一局需要的 tick 数同比减少。默认 1 = 关闭，命令行不变。 |
| `--lockstep` | 关 | bool | 每个决策边界发完 `obs` 后**阻塞等客户端消息**（`step`/`shutdown`）再继续推进，最长等 `--lockstep-timeout-ms`。目的：引擎再快也不丢帧，控制周期恒为 `DECISION_INTERVAL=10` tick。 |
| `--lockstep-timeout-ms N` | `30000` | 1000..600000 | lockstep 等待上限；超时后**退回自由运行**并计数，最终日志打印 `lockstepTimeouts=N`。 |
| `--frame-ms 0` | — | 0..16 | 允许；`0` = 完全不 sleep（不得再被静默钳到 1）。 |

新增启动日志（一次）：
```
[ironzero] pacing: frameMs=<n> physicsMs=<n> physicsDelta=<f> lockstep=<bool> fastForward=<n>
```
结束日志追加：`fastForward=N lockstepTimeouts=K`。

## 2. Python 侧契约（Teammate B）

`src/ironzero/rwpp/config.py::RwppGameConfig` 新增三个字段（顺序追加在 `physics_ms` 之后）：

```python
fast_forward: int = 1          # -> --fast-forward，1 = 关闭
lockstep: bool = False         # -> --lockstep
lockstep_timeout_ms: int = 30000  # -> --lockstep-timeout-ms（仅 lockstep 且非默认时发）
```

`src/ironzero/rwpp/process.py`：

1. `effective_frame_ms(frame_ms: int, physics_ms: int = 0) -> int`
   - `physics_ms > 0` 且 `frame_ms <= 0` → 返回 **0**（合法，不 sleep）。
   - `physics_ms == 0` 且 `frame_ms <= 0` → 仍钳到 `1` 并打印既有警告
     （`frame_ms` 同时是 delta 的旧行为必须保留）。
   - 其余原样返回。
2. `_bridge_command()` 追加（**只在非默认时出现**，保证旧命令行逐字节不变）：
   - `fast_forward != 1` → `--fast-forward N`
   - `lockstep` → `--lockstep`，且 `lockstep_timeout_ms != 30000` 时再发 `--lockstep-timeout-ms N`
   - `--frame-ms` 传 `effective_frame_ms(game.frame_ms, game.physics_ms)`

`RwppGameConfig` 同时把默认 `frame_ms` 从 2 改成 **0**（不限速）：
`physics_ms=16` 已钉死仿真，0 只是不再空等。若 `physics_ms` 被显式设成 0，则
`effective_frame_ms` 会把它安全钳回 1，不需要额外判断。

`train_rwpp` / `evaluate_rwpp` CLI 新增：
`--fast-forward`（默认 1）、`--lockstep/--no-lockstep`（**训练/评估默认开**）、
`--lockstep-timeout-ms`（默认 30000）。三者都写进运行摘要 JSON
（`frame_ms/physics_ms` 旁边）。

脚本（`play_rwpp_policy.py`、`record_rwpp_replay.py`、`baseline_rwpp.py`、
`eval_rwpp_policy.py`、`bc_warmstart_rwpp.py`）：
新增同名参数；`record_rwpp_replay.py` 默认 `--lockstep` 关（它每 4 条 obs 才发一次
order，开 lockstep 会卡住），其余模型推理脚本默认开。

## 4. 验收（Lead 负责）

1. `python -m pytest tests -q` 全绿。
2. `scripts\build_rwpp_extension.ps1` 重建 jar 并同步到**两套**在用 runtime
   （`E:\IronZeroBuild\rwpp-runtime-1.15` 与 `C:\IronZero\rwpp-runtime-1.15`），
   jar 里能看到 `--fast-forward` / `--lockstep` / `--lockstep-timeout-ms`。
3. 真机计时：同一张图同一 tick 数，`frame_ms=0` 对比 `frame_ms=1` 提速 ≥2×
   （实测 2.2×，见 §0）。
4. **`fast_forward` 的验收必须分档写，不能统一要求 ≥1.8×。** 这一条原本写成
   「`fast_forward=2` 让分出胜负的墙钟下降 ≥1.8×」，是**错的**，已由实测推翻：
   `frame_ms=0` 时桥接已不受 sleep 限制，墙钟由**仿真本身**撑满而不是被 tick 数撑满，
   而且每帧成本随 ff 上升（实测 ff=1 423 µs/帧、ff=2 797 µs/帧、ff=4 1152 µs/帧），
   所以 tick 数掉 3.4× 只换来墙钟掉 1.5×。分档标准：

   | `frame_ms` | `fast_forward` 的墙钟收益 | 判据 |
   |---|---|---|
   | `0`（不限速） | 1.2–1.5×（被 sim 每帧成本吃掉） | 只要求 **frames（到分胜负的决策数）下降 ≥2×** |
   | `4` | ~17× | 墙钟下降 ≥2× 成立 |
   | `8` | ~7× | 墙钟下降 ≥2× 成立 |
   | `16`（真实时间） | ~5.7× | 墙钟下降 ≥2× 成立 |

   机理一句话：**`fast_forward` 缩短的是 tick 数，不是每 tick 的计算量。** 当墙钟里
   sleep 占大头（`frame_ms` 大）时收益接近线性；当墙钟已被仿真占满（`frame_ms=0`）时
   收益只剩「tick 数变少带来的固定开销减少」。所以两者是**互补**的两个旋钮，
   发布文案里不能把它们相乘成「26× × N」。
5. 回归：`frame_ms=0 + physics_ms=16` 的 tick→游戏时间换算与 `frame_ms=1` 完全一致
   （用 bridge 日志里的 `pacing:` 行与 replay 的 `tick/time` 斜率核对，
   实测三种 pacing 的 `game_s_per_tick` 都是 `0.01667`）。
6. `lockstep` 回归：`frame_ms=0 + lockstep` 下 `skipped_frames == 0` 且
   `ticks_per_step == 10`（实测 400 步 10.0 tick/步、0 跳帧；不开 lockstep 时
   同样 400 步只拿回 4001 tick 但 158 帧被丢、控制周期漂到 14 tick/步）。

## 5. 补充：`fast_forward` 与 `physics_ms` 并不正交（bridge-java 实测，2026-11-15）

原本假设 `--fast-forward` 只影响 tick 数、`--physics-ms` 只影响仿真步长，两者独立。
**这是错的**，实现后必须知道这条耦合：

引擎的 AI 节拍器全是「累加 delta，超过阈值才动作」型（`AI.java` 的 `aiDelayTimer`、
`baseBuildTimer > 25`、`zoneUpdateTimer > 80`、`Team.resourceUpdateTimer > 90`、
`unitUpdateTimer > 250`），且**每帧最多触发一次**。`gameSpeed` 的乘法发生在
`updateAllGame:1513-1517`，乘完的 delta 才喂给这些计时器，所以：

- **每游戏秒的 AI 决策次数是守恒的**（原假设「AI 决策变少」不成立）；
- 但 delta 一旦越过**最小阈值 25**，AI 就从「N 帧一次」退化成「每帧一次」，即轻微超频。

有效 delta = `physicsDelta × fast_forward`，而 `physicsDelta = physics_ms / 16.667`。
安全判据：

```
fast_forward × physics_ms / 16.667 ≤ 25
```

| `physics_ms` | `physicsDelta` | 安全 `fast_forward` 上限 |
|---:|---:|---:|
| 16（默认，真实时间） | 0.960 | **≤ 26** |
| 25 | 1.500 | ≤ 16 |
| 50 | 3.000 | **≤ 8** |
| 100（服务侧允许的上限） | 6.000 | **≤ 4** |

本次实现把 `fast_forward` 定在 1..32、`physics_ms` 定在 0..100，**范围本身没改**
（`fast_forward ≤ 26` 时在默认 `physics_ms=16` 下完全安全，而 27..32 只是把基地建设
逻辑提速 3.5%–23%，不是正确性问题）。但**任何人同时调高两者时都必须按上表核算**，
服务端校验只保证各自在范围内，不保证组合安全。

## 6. 结论：两个旋钮是互补的，不是相乘的

| 场景 | 用哪个 | 实测收益 |
|---|---|---|
| 只想看一局快跑完（推理页） | `frame_ms=1 → 0` | 20000 tick 的整局 **24.0 s → 4.0 s（6×）** |
| 训练吞吐 | `frame_ms=0` + `lockstep` | 单 env 决策 9.96 ms → **1.75 ms**；但 10 env 训练的墙钟**几乎不变** |
| 训练墙钟受限于 PPO 更新 + JVM 冷启动时 | `fast_forward` 会缩短 tick 数，从而**缩短每局时长** | 每局时长同比降，但 PPO 更新那一段不变 |

**为什么「不限速」没有让训练快 5 倍**：训练的根本成本已经不是等游戏了。
实测 10 env / 512 rollout 配置下，`frame_ms=1` 与 `frame_ms=0+lockstep` 的
每 update 墙钟是 35.85 s vs 36.51 s——**持平**。原因有三条，都已实测：
1. 4 路 env 聚合吞吐上限 ≈ 1000 decision/s（线程 + GIL），10 路只到 170/s 量级；
2. 单次决策里 Python 侧固定开销 1.5–2.4 ms（JSON 解码 + 观测编码 + 动作掩码），
   `recv` 占 33%、`json` 解码与 `encode_observation` 各占 ~15%；
3. 每局固定成本 JVM 1.5–2.4 s + 地图加载 0.28 s。

所以：**推理/观赛用 `frame_ms=0`（6×）；训练要更快得动第 1、2、3 条（并发模型、
观测编码向量化、进程池摊掉 JVM 启动），`fast_forward` 只能缩短每局 tick 数。**
