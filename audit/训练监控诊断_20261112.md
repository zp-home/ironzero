## 三个根因

### 1. 打不起来：地图上没有可攻击的敌人

实测首帧（`scripts/rwpp_obs_probe.py`）：

```
global_state: {"unit_count": 4, "own_alive": 2, "enemy_alive": 2, ...}
own    n=2  types={'commandCenter': 1, 'builder': 1}
enemy  n=2  types={'commandCenter': 1, 'builder': 1}
info: {"builders": [{"unit_type": "builder", "can_build": ["landFactory"]}]}
```

双方各只有 **1 个指挥中心 + 1 个建造者**，一枪不放。
`--units-per-team 2` 这个参数**根本不会生成坦克**——它只影响 obs/action 的形状
（`resolve_max_entities()`），真实单位来自地图 TMX 的预置。

地图上唯一的扩张是敌方 AI 自己造了一个 `extractorT1`（tick 191 起，
敌人 2→3）。所以 strategy 里 `enemy=24/26/28` 不是敌人在增援，而是
**同一个单位的 hp 在不同 episode 之间串了**（见根因 3）。

调试图标：[rwpp_obs_probe.py](scripts/rwpp_obs_probe.py)

### 2. 经济动作被掩码关死

`observation/masks.py` 要求 `has_builder and funds >= cost`：

| 动作 | 成本 | 首帧 funds | 是否可选 |
|---|---|---|---|
| `build_structure` | 800 | 4000 | ✓ |
| `produce_unit` | 250 | 4000 | ✓ |
| `build_extractor` | 700 | 4000 | ✓ |
| `upgrade_building` | 1200 | 4000 | ✓ |
| `repair_target` | — | — | ✓ |

掩码是开的，但 `build_extractor` 在 Java 侧必然被拒：

```
info.builders[0].can_build == ["landFactory"]   # 没有 extractor
```

于是策略选 `build_extractor` → 被拒 → `invalid` 惩罚 −0.05/次。
**掩码认为可选，引擎认为不可行** —— 掩码和引擎的能力集不一致，
这正是 105 个 update 里 −3.083 invalid 的来源。

### 3. 这个 run 跑的是**旧版桥接 jar**，把 20 棵树当成了敌人

**22 = 20 棵树 + 2 个真实敌人。完全对上。**

按优先级：

1. **重启训练**（最重要）。当前 run 用的是 11:47 之前部署的旧 jar，
   全程把 20 棵树算成敌人。现在 jar 已更新（`bdb889f`），必须重跑，
   这 105 个 update 的数据直接丢弃。
2. **换图**。官方 `[p2]Lake (2p)` 双方各只有 1 指挥中心 + 1 建造者，
   而且 `builder` 只能建 `landFactory`、**不能建 extractor**。
   想学经济/战斗建议用 `maps/ironzero/IronZero25.tmx`（25v25 纯坦克，
   实测能打：obs400 tick=3991 own=12 enemy=21，4659 tick 出胜负）。
3. **arena 图必须加 `--win-mode annihilation`**。实测 `IronZero25` 在 native 模式
   **tick=1 就判 defeat**（`DONE: {"tick": 1, "result": "defeat"}`），
   因为纯坦克图没有工厂/建造者，触发引擎 "no factory and no builder" 判负。
   `clearNativeDefeatFlags()` 只在 annihilation 下生效。
   （`scripts/rwpp_service/ppo.py` L249-250 的 arena 分支已自动带上，但
   直接跑 `train_rwpp.py` 时要手动给。）
4. **修掩码**（✅ 已修复）。`build_extractor` / `upgrade_building` 之前只看
   `has_builder and funds`，不看 `info.builders[].can_build`，所以在 Lake 图上
   永远可选、永远被拒、永远交 invalid 罚款。

   现已改为读引擎上报的能力（`src/ironzero/observation/masks.py`
   `_reported_capabilities()` + `_KIND_REQUIRED_BUILDABLE`），
   `rwpp/decoding.py` 把 `info.builders` 带进 state。
   实测同一份 Lake 地图观测现在的掩码：

   | 动作 | 修复前 | 修复后 |
   |---|---|---|
   | `build_structure` | 可选 | 可选 |
   | `build_extractor` | **可选（必被拒）** | **屏蔽** |
   | `produce_unit` | **可选（必被拒）** | **屏蔽** |
   | `upgrade_building` | **可选（必被拒）** | **屏蔽** |

   桥不给能力（离线 mock / 旧桥）时回退到原来的资金门控，不会把经济整体关死。
   回归测试见 `tests/test_mask_capabilities.py`（11 例）。
5. **修 eval 阻塞**（✅ 已修复）。根因有两层：

   **第一层：eval 是串行的。** 4 个 episode 一个个跑，实测 22.8s；
   而训练 10 个 update 只要 15s，所以后台 eval 永远追不上。
   已改为**每个 episode 一个独立游戏进程并行跑**
   （`training/evaluate_rwpp.py`，`parallel` 参数，默认全并行）：

   | 模式 | 实测耗时 |
   |---|---|
   | 串行（旧） | 22.8s |
   | 并行 4 路（新） | **6.5s** |

   加速 **3.5×**，且 4 局结果完全一致（都是 timeout）。
   代价是每个 worker 占用一个 port，所以 `_reserve_eval_ports()`
   改为**按块预留**（4 局 = 4 个连续 port），避免两个并发 eval 撞 port；
   超出 16 个 port 的池会直接报错，而不是静默回绕到正在用的 port。

   **第二层：忙的时候 eval 被丢弃。** 原来打印 `skipped` 就跳过，
   导致 400 update 里 20 次该评估只真评了 4 次。现在改为**延后不丢弃**
   （`PPOTrainer._claim_eval_slot()`）：记住最高的未评估 update，
   worker 空下来立刻补评，训练结束时再补一次。

   回归测试 `tests/test_eval_deferral.py`（13 例）+ 端口块测试，
   突变验证：改回"丢弃" → 9 failed；忽略延后值 → 6 failed。

6. **`units_per_team` 语义要写清**：它只影响 obs/action 形状，不生成单位。
   设成 2 不代表 2v2，容易误导（这次就误导了）。
