## 2. 两条「结构性阻断」（本次审计最重要的发现）

这两条是 Lead 独立实测确认的，不是文档转述。

### 2.1 阻断一：原版地图上，引擎在训练一局的时长内**物理上判不出胜负**

三个独立证据：

**证据 1 — 判胜路径从未执行过。** 扫描全部 8677 份真机日志：

| win_mode | 局数 | 出现「我方胜利」 | 判胜率 |
|---|---:|---:|---:|
| `annihilation`（自制竞技场） | 1544 | **386 次** | 25.0% |
| `native`（原版地图） | 7129 | **0 次** | **0%** |

判定代码 `IronZeroBridge.java:1199-1236` 在 native 模式下有两条判胜通道（`victoryScreenShown`、全部敌方 `defeated`/`wipedOut`），**在 7129 局里一次都没触发过**。而判负通道（`player.wipedOut`）触发了 7 次，其中 6 次的 tick 是 **46972 / 48248 / 48809 / 50734 / 63329**。

**证据 2 — 判负需要 ~47000 tick，训练只给 8000 tick。**

```
实测最早判负 tick            = 46972
训练 episode_ticks           = 8000     → 差 5.9 倍
recommended_episode_ticks()  = 20056    → 差 2.3 倍
8000 tick @60tick/s          = 133 模拟秒
而文档实测：矿场 tick141 → 工厂 tick491 → 首个战斗单位 tick2021 → 接战 5000+
```

**证据 3 — 原版 Lake 图没有声明 `winCondition`。** 直读 tmx：

```xml
<properties><property name="small-rock" value=""/></properties>
```

没有 `winCondition`。而被长期当作训练默认地图的 `challenge/Artillery.tmx` 声明了 `winCondition="mainBuilings"`。**「判胜靠打掉主建筑」这个机制在原版 Lake 上根本没被配置**，所以只能等「敌方全部被歼灭」——而敌方指挥中心 + 持续生产，几乎不可能在 133 秒内被全歼。

**机理补充（模块 A 独立验证）**：引擎的 `Team.updateDefeatCheck`（`Team.java:1612/1624`）判的是**能力**不是兵力——只要还剩 1 个 `isFactoryBuilding() || isBuilder()` 就 `defeated=false`，只要还剩 1 个活单位就 `wipedOut=false`。我方 builder + 指挥中心全程存活，两条判负通道也一起关死。

> **结论**：只要 `episode_ticks` 不提到 ≥20056（建议 30000+），**原版图训练永远只产出 timeout 样本**，`terminal` 永远是 0，胜率永远是 0。这与「策略好坏」无关。

### 2.2 阻断二：奖励结构把策略锁死在「造矿场」的局部最优上

**实测证据**（Lead 用训练好的 `checkpoint_best.pt` 真实跑一局，dump 终局）：

```
decisions=421  tick=8000  result=timeout

--- 我方终局 5 个单位 ---
  commandCenter  hp=4000  building=True   can_attack=True
  builder        hp= 170  is_builder=True can_attack=False
  extractorT1    hp= 800  building=True   can_attack=False
  extractorT1    hp= 800  building=True   can_attack=False
  extractorT1    hp= 800  building=True   can_attack=False
  → 可战斗单位（非建筑非建造者）= 0

--- 本局动作直方图 ---
  build_extractor  786
  move_group         3
  → 99.6% 的决策在重复「造矿场」

--- 本局奖励分解 ---
  income        +1.2000   ← 正
  bonus_build   +0.6000   ← 正
  potential     -0.7146   ← 负
  timeout       -0.2000   ← 负
  kills          0.0000   ← 永远为 0
  bonus_produce  0.0000   ← 永远为 0
  terminal       0.0000   ← 永远为 0
```

**为什么这是个稳定的死锁，而不是「还没学好」**：

1. `build_extractor` 每次接受即推进 `income`（速率增长）+ `bonus_build`（完工），**反馈周期短、信号强**；
2. `produce_unit` → 出兵 → 接战 → 击杀 → 终局这条链，**每一环都需要上千 tick**，而 8000 tick 内**到不了接战**（§2.1）；
3. 于是策略在有限步数内能拿到的唯一正梯度就是「造矿场、别死」——这正是 `potential` 长期为负（敌方爆兵、我方不爆兵）+ `income`/`bonus_build` 为正所塑造出来的形状；
4. 模块 B 独立统计 199 个 update 的奖励占比：`income` 37% + `potential` 24% + `bonus_build` 20% + `strategy` 9% + `timeout` 7.6%，**`kills`/`terminal`/`bonus_produce` 三项合计 0%**。

**这不是「算法调参」问题，是「奖励与目标反向」问题**：用户在 Web 上看到的曲线（income 上升、建筑数上升）看起来像在学习，实际学的是「怎么当一个不会打仗的矿工」。

## 3. 其余重要缺陷（按严重度）

### 3.1 观测帧丢弃 —— 训练与评估在看两个不同的世界

Lead 实测（同一 `session.py` 代码路径，只改并发）：

| 配置 | 每决策 tick | 帧消费率 |
|---|---:|---:|
| 单 env | 10.0 | **100%** |
| 4 envs | 10.5 | 95% |
| **8 envs（真实训练配置）** | **70.2** | **14%** |
| 4 workers（真实评估配置） | 19.1 | ~52% |

原因：`src/ironzero/rwpp/session.py:96-107` 的 catch-up 循环只保留**最新**一帧，中间的帧被静默丢弃。桥按 `DECISION_INTERVAL=10` tick 发帧（`IronZeroBridge.java:317`），但消费端跟不上就直接跳过。

后果：**训练时策略每 70 tick 做一次决策，评估时每 19 tick 做一次**，两者相差 3.7 倍。这正面解释了 `docs/P0修复后训练结论.md` §五.2 那个悬而未决的老问题：

> 「eval 与 train 行为不一致：final 那轮 train 的 own_hp 到 0.68，final eval 却是 0.33。同一 checkpoint 在 probe 里 900 步只发 hold。」

修复它不花算力（引擎本来就把帧算出来了），但会同时改善样本效率和 train/eval 一致性。

### 3.2 `--physics-ms` 实际无效（推翻了一项「P0 修复」）

Lead 实测：`physics_ms=2` 与 `physics_ms=16` 跑同样墙钟时间，**产生的 tick 数完全一样（都是 191）**，比值 0.86，若 physics_ms 真的是物理步长应为 8.00。

引擎源码确认原因（`RWGameEngine.java:1217`）：

```java
public void updateFrameInternal(float var1, int var2) {
    ...
    this.frameTimeMillis = (int)(this.frameTimeMillis + var1 * 16.666666F);  // var1 = 物理步长
    this.updateCameraFollow(var1);
    this.fpsTimeAccumulatorMs += var2;          // var2 只进 FPS 统计
```

而桥接层调用是 `engine.updateFrameInternal(1.0f, physicsElapsedMs)`（`IronZeroBridge.java:300`）——**物理步长被钉死为 1.0f，`physics_ms` 被送进了 FPS 参数位**。

影响：`docs/P0修复后训练结论.md` 的「A5：physics_ms 默认 0→16」这项修复**没有生效**，文档里「3600 tick × 16ms = 57.6s 游戏时间」「20000 tick × 16ms = 320s」的推算全部不成立。所有基于该假设的时长结论需重算。

### 3.3 「预热策略」静默加载错配的 BC 权重

Lead 实测：Web 表单默认 `init_mode=warmstart`，`resolve_bc_checkpoint(2)` 解析到 `runs/experiments/bc_ironzero25/checkpoint.pt`（25v25 布局），而 Lake 是 2v2 布局：

| | BC 权重（25v25） | Lake 实际需要 |
|---|---|---|
| obs_dim | 768 | **511** |
| max_entities | 25 | 8 |
| target_slots | 26 | 9 |
| map_channels | 4（含 terrain） | 3 |

逐张量比对结果：

```
trunk.0.weight   bc=(256,768)  vs lake=(256,511)  → 形状不兼容，随机初始化
heads.0.weight   bc=(5,256)    vs lake=(10,256)   → 形状不兼容，随机初始化
heads.4.weight   bc=(26,256)   vs lake=(9,256)    → 形状不兼容，随机初始化

可迁移参数 71,702 / BC 总参数 276,277 = 26.0%
Lake 策略 207,401 参数中随机初始化的比例 = 65.4%
```

**用户以为「站在 BC 肩膀上」，实际 65.4% 的参数是随机初始化的。** UI 上没有任何提示。

### 3.4 KPI 口径失效：`enemy_hp_frac` 在原版图上恒为 1.0

Lead 实测全部 61 份 eval_report：

| 地图类别 | 局数 | `own_hp_frac==1.0` | `enemy_hp_frac==1.0` |
|---|---:|---:|---:|
| 原版图（maps/skirmish） | 89 | 73.0% | **100.0%** |
| 竞技场图 | 221 | 1.8% | 7.7% |

原因：`reward.py:48-54` 用**开局**敌方 Σmax_hp（4170 = 指挥中心 4000 + 建造者 170）作分母，而敌方指挥中心永存且持续造兵，敌方总量一旦超过 4170 就被 `min(1.0, ...)` 永久夹在 1.0。

**后果**：用户在 Web 大屏上看到的「双方战力对比」在原版图上不承载任何信息——无论被打成什么样都显示 100% : 100%。训练侧和推理侧用同一段代码，所以两边「互相印证」成看起来没问题。

## 5. 修复路线图（按阻塞强度排序）

### 阶段 0：三个「不修就永远学不会」的阻断项

| # | 修什么 | 位置 | 验收标准（可测） |
|---|---|---|---|
| 0-1 | **`episode_ticks` 提到 ≥20056**（建议 30000），并改用 `recommended_episode_ticks()` 自动推导 | Web 默认值 `index.html`；`rwpp/config.py:265` | 原版图训练出现**首个非 timeout 的终局**；`terminal` 在某个 update 上非零 |
| 0-2 | **补观测帧丢弃**：catch-up 改为 lockstep 或按帧补偿步进，不再静默跳帧 | `src/ironzero/rwpp/session.py:96-107` | 8 envs 下帧消费率 ≥95%；训练与评估的「每决策 tick」一致（都是 10） |
| 0-3 | **修 `physics_ms` 语义**：把物理步长真的传给引擎第一参数 | `IronZeroBridge.java:300` → `updateFrameInternal(physicsMs/16.67f, frameMs)` 或按引擎文档调整 | 同墙钟下 `physics_ms=16` 产生的 tick 数是 `=2` 的 8 倍（当前是 1.0 倍） |

### 阶段 1：让「出兵 → 接战」这条链有梯度

## 7. 给用户的一句话总结

> **你现在可以在 Web 上完整跑完一次训练和推理，链路是真的通的。但训练出来的是一个「只会造矿场的矿工」：它会造矿场、会造工厂，却一个兵都不造、一枪都不开。**
>
> **而且这不是练得不够——原版 Lake 图上，引擎在 8000 tick 内物理上判不出胜负（判负最早要 47000 tick 才出现），奖励结构又把策略牢牢锁在「造矿场」这个局部最优上。**
>
> **所以 70% 胜率的答案是：当前配置下不可能。** 文档里那个 0.75 / 0.90 是真的，但它跑在「无经济的纯坦克竞技场」上，不是你要的原版地图。想达到目标，先做 §5 阶段 0 的三件事（episode 拉长到 20056+、补观测丢帧、修 physics_ms），这三件不花训练时间，但不做的话练多久都是同一条曲线。
