## 1. 阻断一：原版地图上判不出胜负

### 1.1 根因（三层叠加）

1. **原版 Lake 没有 `winCondition`。** 直读 tmx：`<properties><property name="small-rock" .../></properties>`，
   而长期被当作默认训练图的 `challenge/Artillery.tmx` 声明了 `winCondition="mainBuilings"`。
   没有声明时 `TriggerEngine` 落到 `ObjectiveType.noConstructionOrTech`
   （`TriggerEngine.java:233/267`）——「敌方没有任何工厂和建造者」。
2. **native 模式的两条判胜通道都不可达。** `detectGameResult` 等
   `victoryScreenShown` 或「敌方全部 `defeated`/`wipedOut`」；而
   `Team.updateDefeatCheck`（`Team.java:1612/1624`）判的是**能力**不是兵力——只要还剩
   1 个 `isFactoryBuilding()||isBuilder()` 就 `defeated=false`。
   实测：8677 份真机日志里 native 判胜 **0 次**，判负 7 次，最早 **tick 46972**。
3. **训练一局只有 8000 tick（133 模拟秒）**，判负都要 47000 tick 才出现。

### 1.2 修法

Java 桥新增 `--win-mode objective`：直接读引擎的 `TriggerEngine` 目标判定，外加两个补充通道：

- **`OBJECTIVE_GRACE_TICKS = 120`**：目标达成后仍需保持一段时间，避免一帧抖动就判胜；
- **军事压制（dominance）**：`DOMINANCE_OWN_MIN_UNITS = 8`、`DOMINANCE_ARMY_RATIO = 3.0`、
  `DOMINANCE_HP_RATIO = 3.0`。

Python 侧 `RwppGameConfig.episode_ticks` 默认 0，由 `recommended_episode_ticks()` 按地图对角线
和玩家数推导（Lake → **20056**），取代硬编码。

### 1.3 为什么还要「军事压制」

原版 Lake 的 `noConstructionOrTech` 在 AI 对 AI 的对局里要等到一方彻底失去生产能力，
实测到 tick 34701（196 个单位）才出现；`mainBuildings` 要 tick 39864。
对训练来说这个信号太稀疏——一局 20056 tick 内基本不可能出现。
军事压制把「14 个战斗单位对 6 个」这种情况也判为胜利，实测 tick 4915 就能出结果。

同时验证了**不会误判**：双方势均力敌（AI 等级都是 2，71 vs 45）时正确报 `timeout`。

### 1.4 验收

```
# 三档判定，同一张 Lake 图
noConstructionOrTech  → tick 34701 (196 units)
mainBuildings         → tick 39864
+ dominance           → tick  4915 (14 vs 6)     ← 训练用这一档
势均力敌 (71 vs 45)    → timeout                  ← 无假阳性
```

## 2. 阻断二：策略永远不造战斗单位

### 2.1 根因

`bonus_produce` 在 199/199 个 update 里恒为 0.000，`own_alive` 只有 1~3。
逐层排查后发现五个独立缺陷（详见第 3、4 节），其中最关键的是：
**课程链缺了中间一环——没有任何代码去造工厂**。

### 2.2 修法

补上缺失的三级课程 `opening_factory`（配置项 + `--no-opening-factory` + `_issue_opening_factory`），
并修正 `build_progress` 上报与课程命令的派发时序（第 3 节）。

三级课程现在按依赖顺序推进，每一级的完成条件都用**引擎自己的答案**判断：

1. `build_extractor`：直到矿场 `is_operational` 为真；
2. `build_structure`（land factory）：矿场可用后；
3. `produce_unit`：工厂的 `can_produce` 出现非 `builder` 条目后。

三条命令都走正常桥接路径，奖励仍只由观测流支付（`bonus_build`/`income`/`bonus_produce`），
所以课程只是「拆掉探索屏障」，不能刷分。

### 2.3 验收（真机）

见第 4 节「结论 5」的完整链路时序。

## 3. 连带修复

### 3.1 观测帧丢弃（训练/评估跑在两个时间尺度上）

同一份代码，只改并发数：

| 并发 | 帧消费率 | 每决策 tick |
|---|---|---|
| 单 env | 100% | 10.0 |
| 4 env | 95% | 10.5 |
| **8 env** | **14%** | **70.2** |
| 4 eval worker | ~52% | 19.1 |

「最新帧胜出」本身是对的（否则 socket backlog 无界增长），但它**悄悄改变了控制周期**。
新增 `RwppDuelEnv.skipped_frames` 把丢弃的帧计数出来，修复后实测 `skipped_frames=0`、10.0 tick/决策。

### 3.2 `--physics-ms` 无效（推翻了一项「P0 修复」）

`docs/P0修复后训练结论.md` §一 声称「A5 physics_ms 0→16 已修复」，**实际从未生效**。
`RWGameEngine.updateFrameInternal(float var1, int var2)`（`RWGameEngine.java:1217/1371/1506-1524`）
里**只有 `var1` 推进物理**，`var2` 只喂 `fpsTimeAccumulatorMs`。
桥接把 `var2` 当成了物理步长，所以无论传什么都一样。

修法：`final float physicsDelta = physicsMs > 0 ? (physicsMs / 16.666666f) : 1.0f;`
再 `engine.updateFrameInternal(physicsDelta, pacingElapsedMs);`

验收（正确仪器：固定 tick 数下建造者的位移）：

```
# {'physics_ms': 2,  'builder_to': (975, 2057), 'distance_moved_px': 20.0}
# {'physics_ms': 16, 'builder_to': (532, 1790), 'distance_moved_px': 536.7}
```

因此所有从「3600 tick × 16 ms = 57.6 s」推出的时长结论**全部作废**。

### 3.3 HP 分数在原版图上恒为 1.0（KPI 失效）

`hp_fractions()` 在被钳制到 [0,1] 之后又被用作「剩余比例」，双方满血时永远是 1.0，
等于这个 KPI 从不变化。新增 `hp_fraction_ratios()` 返回未钳制的比值，`hp_fractions()` 行为不变。

### 3.4 预热权重：审计结论更正 + 静默问题修复

审计说「BC 预热只有 26% 可迁移、65.4% 随机」——**这是错的**。实测真实覆盖率 **99.01%**
（205348/207401）：主干是逐列重映射的（508/511 列有信息），只有 `heads.0` 的 5 个新动作类
（约 1285 参数）是随机的。

`_load_compatible_weights()` 改为返回结构化 `transfer` 摘要
（`exact/adapted/kept_random_params/total_params/transferred_params/transfer_ratio/informative_params/coverage`），
覆盖率 < 0.5 时打 `warning`，并在 `launch.py` 的 job 记录里留 `init_warning` 字段。

`resolve_bc_checkpoint()` 改为**只接受精确匹配**，删掉了 25v25 静默回退
（那个回退正是「加载了一个不兼容 checkpoint 却毫无提示」的来源）。

### 3.5 评估样本量不足以证明 >70%

Wilson 区间：4/4 → 下界 0.510；8/8 → 0.6756；**9/9 → 0.7008**。
即：要证明胜率 >70%，至少需要 9 局全胜。新增 `wilson_lower_for_target()` /
`minimum_episodes_for_target()`。评估选项补了 16 局档。

### 3.6 Web 表单缺三个关键开关

`web/frontend/index.html` + `js/state.js` + `js/ppoRun.js`：

- `fe-ppo-ticks` 默认值 4800 → **0**（改为按地图推导）；
- 新增 `fe-ppo-win-mode`（默认 `objective`）；
- 新增 `fe-ppo-enemy-ai-difficulty`（默认 2）；
- 新增 `fe-ppo-unlock-ai`；
- 评估局数补 16 局档。

同时确认 `web/frontend/app.js`（304 KB）是**死代码**——`index.html` 只加载
`/static/js/main.js`（`js/` 下的 ES 模块）。

## 4. 经济闭环：五个叠加缺陷

审计阶段的判断是「从零随机策略完不成起手，所以是探索问题」。继续追查后发现这个判断**不完整**：
起手完不成，是因为五条代码路径各自有缺陷，而不是随机策略运气差。
每一条都被真机实验单独确认并修复。

### 缺陷 A：课程链缺了中间一环——没有任何代码去造工厂

`opening_extractor` 造第一座建筑，`opening_production` 要求「已存在能造战斗单位的工厂」，
但**两者之间没有任何代码去造工厂**，于是 `opening_production` 的前置条件永远不成立。

用纯 `noop` 策略（任何命令都不会打断在建工程）跑满 20056 tick 的真机实测：

```
extractor 完成       tick 151
非指挥中心工厂        从未出现（tick 20056 时仍只有 commandCenter + extractorT1）
bonus_produce        0.0
```

这解释了 40-update 对照里 `bonus_build` 有 17/40 非零而 `bonus_produce` 是 0/40：
智能体学会了造矿场就停下了。

顺带否掉两个看似合理的原因：

- **不是选址非法**：策略位置头全部 64 个格子逐一实测，`build_structure` 被接受 **64/64**；
- **不是打断**：只下一次工厂命令然后全程 noop，工厂 tick 1891 完成；每个决策都重发，tick 2611 完成。

### 缺陷 B：`build_progress` 把「还没开始」报成「已完工」

```java
float progress = unit.buildProgress;
if (!Float.isFinite(progress) || progress <= 0.0f) {
    return 1.0f;   // 「没开始」被报成「已完成」
}
```

引擎自己的 `isNonOperational()` 是
`isVirtualUnit() || buildProgress < 1.0 || team == disconnectedTeam`，
所以 `buildProgress == 0` 的建筑**确实不可用**，桥却报「100% 完成」。真机实测这个矛盾持续 18000 tick：

```
tick 1571 .. 20056   build_progress: 1.0   is_operational: false   can_produce: []
```

改为诚实上报 `max(0, min(1, progress))`。

### 缺陷 C：课程命令发在策略命令之后的「下一条消息」里，等于没发

课程原本在 `step()` 末尾单独发一条 `step` 消息。**第二条消息是下一个 tick 的另一次派发，
不是同一决策里的第二条命令**，而策略自己的战术命令（`attack_move`/`move_group`/`stop`，
约占随机采样的一半）先到、取消在建工程，课程随后才重发——进度被反复清零。
真机实测 220 个决策里矿场 `build_progress` **恒为 0.0000**。

修复：课程命令改由 `_curriculum_actions()` 收集，追加到**同一条** `step` 的 `actions` 数组末尾
（`send_step(..., extra_actions)`）。

### 缺陷 D（最隐蔽）：`[] is not None` 让课程循环在第一个 stage 就短路

`_curriculum_actions` 遍历三个 stage 时写的是 `if order is not None: return order`，
但每个 stage 返回的是**列表**——已完成的 stage 返回 `[]`，而 `[] is not None` 为真，
于是循环在第一个 stage 就短路，工厂和生产两级**从来没被调用过**。

真机实测：extractor 完成后 119/119 次调用都返回 `[]`，工厂 stage 调用次数为 **0**。
症状和「课程不存在」完全一样，把前面所有排查都指向了错误方向。
已修成 `if order:`，并加了回归测试 `test_curriculum_advances_past_a_satisfied_stage`。

### 缺陷 E：工厂菜单缓存导致 84% 的生产订单被拒

`producibleCache` 以**工厂类型名**为键缓存「这个工厂能造什么」，但 `isAvailableForUnit` /
`canAffordForUnit` 依赖**实例**状态（科技等级、已占用的信用点、状态效果），而且缓存**从不失效**，
于是菜单会永久停留在第一次计算的结果上。

真机实测（强制每个可生产决策都发 `produce_unit`）：

```
landFactory 报 can_produce: ['builder', 'hoverTank']
→ 131 次生产命令里 104 次 PRODUCE_UNAVAILABLE，持续约 5800 tick
→ 同期资金 353~426 信用点，远高于悬停坦克价格 ⇒ 不是买不起
```

两处修法：

1. 缓存键加上 `#techLevel@entityId`，并改成**每次观测开头清空**——它只是「一次载荷内的复用」；
2. `producibleNamesFor` 补上 `canAffordForUnit(factory, false)`，让上报的菜单与 `produceUnit`
   真正分派的条件**完全一致**（此前只查 `isAvailableForUnit`，菜单是实际可派发集合的超集）。

### 结论 5：三级课程串起来后真机端到端跑通

修完 A~E 后，同一张原版 Lake 图上，两条真机链路都走完了完整经济闭环。

纯 `noop`（下界，只考课程本身）：

```

factory 开工     tick 2061
factory 可用     tick 3851
战斗单位         tick 4381
bonus_produce    +0.1 (tick 4381)
```

掩码随机策略（PPO 的初始分布，这才是关键）：

```
extractor       tick 161
factory 开工     tick 2061
factory 可用     tick 3851
战斗单位         tick 6981
bonus_produce    +0.1 (tick 6981)
```

Web 一次 20-update PPO 真机训练（4 envs / 512 rollout / 20056 tick / 对手 -2）：

```
bonus_produce   非零 6/20 个 update，累计 +15.458，单 update 最高 +2.750
bonus_build     非零 6/20 个 update，累计 +2.400
kills           非零 3/20 个 update
PRODUCE_UNAVAILABLE  52（修复前 318）
invalid         -4.25（修复前 -10.32）
episodes        20/20 完成（此前一直是 0/20：rollout 预算不够跑满一局）
```

`bonus_produce` 从「20 个 update 全 0」变成「每局完成时 +2.0 左右」，
这是这条闭环第一次在训练里真的跑起来。

### 仍未解决的（诚实记录）

- **`terminal` 仍是 0/20。** 每局都能跑满 20056 tick，但没有一局被引擎判定胜负。
  20 局样本离证明 >70% 胜率还差两三个数量级（Wilson 下界要求 9/9 才够 0.7008）。
- **`UPGRADE_UNAVAILABLE` 仍有 253 次。** 掩码对升级的可选性判断仍与引擎有偏差，
  下一轮该查这条（这是目前最大的剩余拒绝桶）。
- **BC 只能克隆「造建筑」。** 内置 AI 在 Lake 上的开局订单流确实是 `extractorT1`(tick 61) →
  `landFactory`(tick 1331) → `airFactory`(tick 1651) → 炮塔，
  但 `ai_orders` **不暴露工厂生产队列**，所以 `produce_unit` 无法从订单流克隆，
  生产维度仍需 PPO 自己学。
- **课程不能替代策略。** 随机策略下工厂仍可能造不完（`build_progress` 停在 0.0，
  敌人 39 个单位而自己只有 3~4 个）。实测**29%** 的策略命令会打到建造者所在组或广播组
  （`.runtime/group_collision.json`：289/995），而每条命令都会取消在建工程。
  这个不能靠改写策略动作用「保护建造者」来绕过——那样执行的动作就不再是采样到的动作，
  PPO 的 ratio 和 advantage 都会对不上。这是任务本身的难度，不是旗帜能盖住的。
