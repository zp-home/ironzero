# 模块 A：环境与桥接层闭环复核（原版 Lake 上「从未判出胜负」的机理）

> **一句话结论**：在原版 `[p2]Lake (2p)` 上，引擎的 native 判胜路径在这套配置下**在结构上不可能被触发**——双方各自的「指挥中心 + builder」都活着，`victoryScreenShown` / `allEnemyDefeated` 永不成立；而唯一的判负通道是 `player.wipedOut`（我方单位被**全部**抹除），历史实测最早也要 **tick 46972**，而训练跑的是 **8000 tick（=133 模拟秒）**。同时我方从第 1 局到第 1675 局**一个战斗单位都没造出来过**（`bonus_produce` 在 199 个 update 上恒为 0.000），所以连「被打败」的资格都不成立——1724/1724 timeout 是这两条结构性事实的必然结果，不是"策略学得差"。

## 2. 引擎的胜负判定链：为什么 5 vs 17 不判 defeat

**native 分支**（`src/ironzero_bridge/java/ironzero/IronZeroBridge.java:1199-1236`），
按顺序只有三个出口：

```java
:1199  if (engine.defeatScreenShown || player.defeated || player.wipedOut) -> "defeat"
:1206  if (engine.victoryScreenShown)                                   -> "victory"
:1211  for (Team t : Team.getTeams()) if (!t.defeated && !t.wipedOut) enemyAlive = true;
:1230  if (enemySeen && !enemyAlive)                                     -> "victory"
```

**这两个信号在 Lake 上分别靠什么成立**：

1. `victoryScreenShown` ← `TriggerEngine` 慢路径（`TriggerEngine.java:1043-1086`），
   `winObjective` 由地图 `map_info.winCondition` 决定。原版 `[p2]Lake (2p).tmx` 的
   `map_info` **只有** `<property name="type" value="skirmish"/>`，**没有 winCondition**，
   于是走 `TriggerEngine.java:233/267` 的默认值 `ObjectiveType.noConstructionOrTech`
   （胜利条件 = 敌方**没有任何** `isFactoryBuilding()` 或 `isBuilder()` 的单位，
   见 `TriggerEngine.java:1121-1122`）。敌方指挥中心是 `isFactoryBuilding()==true`
   （`CommandCenter.java:264`），builder 也一直在 → **永不满足**。
   同时 `loseObjective = winObjective`（`TriggerEngine.java:297-299`），
   我方 CC + builder 也一直在 → 反向同样永不满足。
2. "敌方全部 defeated/wipedOut" ← `Team.updateDefeatCheck`（`Team.java:1587-1658`）：
   - `wipedOut = true` 仅当「一个非 `isNonOperational()` 的单位都不剩」（:1624-1630）；
   - `defeated = true` 仅当「没有任何 `isFactoryBuilding() || isBuilder()`」（:1612-1615, :1652-1655）。

**所以 5 vs 17 为什么不是 defeat**：判定看的是**能力**（有没有工厂/builder、有没有单位），
**不是兵力对比**。我方即便只剩 1 个单位，只要还有 1 个 builder 或 1 座工厂，
`defeated=false`；只要还有 1 个活单位，`wipedOut=false`。我们的 builder 与 CC 全程存活，
于是两条判负通道都关死。

**反证（历史真机证据）**：全库 6 份 Lake 的 `game over: defeat` 全部是
`defeated=false wipedOut=true screen=false`，tick 分别
**46972 / 48248 / 48809 / 50734 / 63329**（另 1 份 tick=1 是 `--ai-pilot` 异常）：

```
game-5134-61581.log: [ironzero] game over: defeat tick=50734 defeated=false wipedOut=true screen=false   (--ticks 100000 --frame-ms 2)
game-5131-70561.log: [ironzero] game over: defeat tick=63329 defeated=false wipedOut=true screen=false
```

即：**判负只能靠"被我方单位全灭"，而这一事件最早出现在 tick 46972**，是训练
`episode_ticks=8000` 的 **5.9 倍**。`config.py:59-88` 自己算出来的
`recommended_episode_ticks(2600,2600,2) = 20056` 也仍小于 46972。

> 代码这么写 ≠ 真机实测：上面 tick 数是 6 份真机 log 的实测值，不是推算。

## 3. 内置 AI 侧：aggressiveMode 已修、difficulty 只改经济、133s 打不穿

- **aggressiveMode 已修且已进生产 jar**：`IronZeroBridge.java:1351-1363` 的注释明确写
  "不要再设 aggressiveMode"；`unlockAiTeams()`（:1365-1390）现在**只**清
  `aiLimitedUse`。我直接读了生产 jar
  `E:\IronZeroBuild\rwpp-runtime-1.15\extensions\ironzero-bridge.jar`
  （2026-11-14 02:46，24832 B）里的 `ironzero/IronZeroBridge.class`，
  常量池中**不存在** `aggressiveMode` 字符串 → 修复确实编译进去了（与
  `docs/内置AI不进攻_根因与修复.md` §4 一致）。
- **但本 run 是 `unlock_ai=false`**（`game-*.log` 的 arguments 行）
  → 敌方那 2 个地图预置单位 `aiLimitedUse=true` 未被清，于是被
  `AIUnitGroup.recruitUnits`（`AIUnitGroup.java:205`）与
  `Base.countAttackerUnits`（`Base.java:436`）排除在战斗组之外。
  注意：`aiLimitedUse` **只挡"编入攻击组"，不挡建造与生产**
  （`Base.updateBuildLogic` 未引用它）——所以 AI 照样铺经济、造兵，
  与我实测的 `enemy_alive` 2→13~18 一致。
- **`enemy_ai_difficulty=2` 的实际作用**：只经
  `Team.getAIDifficultyIncomeMultiplier()`（`Team.java:1048-1069`，level2 → **x1.8**）
  给 AI 加钱；`getAIDifficultyArmyValue()`（`Team.java:931`）**只被排行榜列调用**，
  不参与进攻决策。进攻闸门是纯单位计数：`AI.java:1890`
  `defenseGroupsReady >= 防御组数 || defenseUnitCount > 6` + `AIUnitGroup` 的
  `desiredUnitCount`（3/5/7，`AI.java:1892-1897`）+ `attackDelayTimer` 初值 1000
  （`AIUnitGroup.java:30`）。难度 2 的 `PENDING_isHardOrLateGame()` 是
  `difficulty==3 || >300` → **level 2 不算 hard**，攻击组规模不会放大。
  这与 Lead 第 3 条一致：难度旋钮在这里只等于「AI 更富」。
- **为什么 133s 内打不掉我方基地**：见 §2 的 tick 46972 实测；再叠加 Lake 的
  地图对角线 3677 px、地面单位 66 px/s，单程接近就要 ~27 s，加经济成型 ~2021 tick
  （33 s）、合成部队成型与推进，133 s 只够"接战开始"。

## 4. 观测丢帧（14%/52%）如何具体破坏「经济→造兵→接战」

**机理（不是泛泛而谈）**：

1. 桥是**自由运行**的：`IronZeroBridge.java:317` 每 `DECISION_INTERVAL=10` tick
   无条件写一条 obs，不等 client 的 `step`（:65）。
2. Python 侧 `session.py:96-107` 的 catch-up 循环**只保留最新一帧**
   （`if extra.get("type") == "obs": latest = extra`），中间帧被丢弃。
3. 一旦策略一次前向比桥产帧慢，桥就领先 k 帧，下一决策的观测时间戳直接跳到
   `t + 10k`。所谓"每决策 10 tick"退化为"每决策 10k tick"。

**实测 k（两套口径，方向一致）**：
- 我按 `metrics.json` 反算：`200 update × 256 steps × 8 envs = 409600` 决策，
  完成 episode `1675` 局 × 8000 tick → **32.7 tick/决策 = 设计值的 30.6%**；
  评估段 `mean_decisions` 序列（221→418）→ **19~35 tick/决策**。
- Lead 直接实测：训练 **70 tick/决策（14%）**、评估 **19 tick/决策（52%）、单 env 100%**。
- 两者都 ≫ 10，且**训练与评估不是同一个 dt**（70 vs 19，约 3.7 倍），这是关键。

**它具体破坏了什么（四段因果，逐段有据）**：

1. **建造不可能完成**：一次 `build_extractor` 需要 ~140 tick 不被打断
   （`.runtime/buildprogress.json`：landFactory `completed_at_tick=221`，
   `many_action.json` 里 extractor 进度 0→1.0 跨 ~100 tick）。
   在 32.7~70 tick/决策下，一栋建筑只跨 **2~4 个决策**；而任何非 `noop` 指令
   都会取消在建（`decoding.py:305-309` 注释明说）。→ 建成的概率被 dt 压到极低，
   这正是 `opening_extractor` 课程存在的原因（`config.py:244-261`）。
2. **经济→造兵的时序被压缩成"看不见"**：Lake 的
   `141（矿场）→ 491（工厂）→ 2021（首兵）`。8000 tick 只有 133 s 且只有 ~245
   （或 ~114）个决策；一次决策跨 3~7 s 游戏时间，等于**每步跨过一个建筑阶段**，
   credit 与建造进度之间的 credit assignment 被打散。
3. **接战信号被采样混叠**：`engagement` 是"两军**战斗质心**距离的一阶差分"
   （`reward_shaping.py:383-389`）。dt 变成 3~7 秒后，一辆坦克一次决策走 66 px/s×3.3s
   ≈ 218 px，差分项变成**大幅正负抖动**而不是"接近速度"。实测 `engagement`
   均值仅 +0.00357（范围 -0.0027~+0.0098）→ 密集接战梯度基本被抹平。
4. **训练/评估 dt 不一致 = 策略在两个时间尺度上被学/被测**：策略在训练里学到的是
   "一个动作 = ~70 tick 的效果"，评估时突然变成 ~19 tick。同一组权重面对
   完全不同的状态转移算子；`eval_report.json` 里 `own_hp_frac=1.0 /
   enemy_hp_frac=1.0` 说明评估侧观测**根本没有变化信息**（见 §6 第 5 项），
   于是"训练时学经济、评估时被冻住"完全解释得通。

> 一句话：**丢帧把「造一栋楼 = 4 个决策的事」变成了「造一栋楼 = 1 个决策的事」，
> 同时在评估里把这 1 个决策的效果缩小 3.7 倍。** 经济行为在训练里被奖励、
> 在评估里不产生同样后果，两边不可能收敛到同一个策略。

**顺带一个代码与注释不符的点（需实测确认，非本轮实测）**：
`IronZeroBridge.java:300` 调 `engine.updateFrameInternal(1.0f, physicsElapsedMs)`，
而 `RWGameEngine.updateFrameInternal(float var1, int var2)` 用 `var1` 做物理增量
（`updateAllGame(var1)`，`RWGameEngine.java:1371`）、`var2` 只进 FPS 统计
（`:1217 fpsTimeAccumulatorMs += var2`）。也就是说 **`--physics-ms` 不改变物理步长**，
物理恒为 1.0 游戏帧/tick（16.67 ms）——与 `config.py:158-172` 的注释表述相反。
`8000 tick = 8000×16.67 ms = 133 s` 正是按这个算的，与 log 一致。

## 5. 「默认部队」核对：`units=24` 是什么

直接解码 `E:\IronZeroBuild\rwpp-runtime-1.15\assets\maps\skirmish\[p2]Lake (2p).tmx`
的 `Units` 层（gzip+base64，130×130，非 0 tile 仅 **4** 个）：

| tile (x,y) | gid | 单位 | 队伍 |
|---|---|---|---|
| (61,10) | 425 | `commandCenter` | team 1（敌方） |
| (61,13) | 420 | `builder` | team 1 |
| (49,100) | 380 | `commandCenter` | team 0（我方） |
| (49,103) | 375 | `builder` | team 0 |

引擎自报与之完全吻合：`there are 4 units on this map and 20 trees`
（`game-5204-17523.log`），而 `world ready: units=24` 是
`countUnits()`（`IronZeroBridge.java:2660-2671`）对 `Unit.unitList` 的计数——
`Tree extends NonGameUnit extends Unit`（`Tree.java:251`），20 棵树被算进去：
**24 = 4 个真单位 + 20 棵树**。

**含义**：
- 原版 Lake 是**纯经济开局**：每方只有 `指挥中心(4000 HP) + builder`，
  **一个战斗单位都没有**。所以「默认部队」在这里 = 「没有部队」，
  想打仗**必须先造**：`builder → 矿场（tick141）→ 工厂（tick491）→ 首兵（tick2021）`。
- 这对"学会经济/建筑/生产"是**必要条件而不是可选加分项**：不造经济就没有任何
  战斗单位，不造战斗单位就永远不可能触发任何胜负判定（§2）。
- 反过来也说明：**25v25 竞技场（IronZero25）的成功经验完全不能迁移**——
  那张图预置 25 辆坦克、不需要经济，`bonus_produce`/`kills` 立刻有信号；
  而用户要的原版图把这条链拉长到 2021 tick 以上。
- 另一个与用户目标直接冲突的点：`challenge/Artillery.tmx`（代码里的
  `config.py:32 DEFAULT_MAP`）声明了 `winCondition="mainBuilings"`，
  原版 Lake **没有**。所以"默认地图"恰好是判胜条件最不友好的那张。
