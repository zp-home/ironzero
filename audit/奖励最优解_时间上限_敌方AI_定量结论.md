## 1. 奖励的最优解

### 1.1 问题形式

「造兵」是**无界流量**（每个单位都付一次 `bonus_produce`，可以一直造）；
「赢」是**一次性存量**（只在最后付一次 `win_reward`）。
在足够长的回合里，流量必然压过存量，除非存量大于流量的总上限。

所以要先算流量上限：

| 量 | 数值 | 来源 |
|---|---:|---|
| 回合长度 | 20056 tick = 335 s | `recommended_episode_ticks(2600,2600,2)` |
| 收入区间 | 18 → 58 cr/s（均值 38） | `base_income_reference`；documented 满级经济 |
| 每回合总收入 | 38 × 335 = **12,712 cr** | 计算 |
| 最便宜战斗单位 | 350 cr（`c_tank`） | `assets/units/tanks/tank.ini` |
| 可负担单位数 | **36.3** | 计算 |
| **造兵流量上限** | 0.10 × 36.3 = **+3.63** | `produce_bonus` |
| **当前 `win_reward`** | **+1.00** | `MicroDuelConfig.win_reward` |

**赢一局只值它所要竞争的造兵收益的 28%。赢在数学上是不理性的。**

### 1.2 实测印证

`runs/platform/twoslot-mask-long/live.jsonl`，231 个 update：

```
bonus_produce   +288.70   (占正向奖励 60.4%)
potential       -278.83   (几乎精确抵消)
terminal        +  4.51   (占 0.9%)
------------------------------------------------
比率 bonus_produce / terminal = 64.0x
```

`potential` 把 `bonus_produce` 抵消掉，说明策略确实学到了「造兵会让潜在函数变好」，
但**唯一能让 `potential` 转正的行为——消灭敌军——它从没做过**。

### 1.3 第二个独立缺陷：击杀收益也超过赢

`kills` 和 `losses` 都被 `threat_value` 加权（`_weighted_attrition`），
所以「打坦克换炮兵」这种有利交换是**有正收益**的：

```
0.25 × 2.15(炮兵) − 0.25 × 1.68(坦克) = +0.117
```

**因此「kills 与 losses 对称导致交易无收益」这个说法是错的**，要撤回。

真正的缺陷在另一个方向——**击杀总量可以超过赢局**：

```
每回合可击杀 40 个（difficulty 1 实测 enemy_alive 上限）
原权重下总击杀收益 = 0.25 × 40 × 1.2(平均威胁) = +12.00
对比 win_reward                                 = + 1.00
=> 把整支敌军杀光，收益是赢局的 12 倍
```

这制造了**第二条永不赢的路径**：「一直刷击杀」比「结束比赛」划算。

**落地后**：`kill_bonus = 0.069`，整支敌军 `0.069 × 40 × 1.2 = 3.31`，
占赢局 5.5 的 **60%**——仍然值得打，但打不完整局更值。
且炮兵换坦克仍有正收益：`0.069 × 2.15 − 0.069 × 1.68 = +0.032`。

### 1.4 计算结果与实际落地值

送进代码的不是「建议值」而是重新算过的值——因为**时间上限翻倍会改变算术**：
回合变长 → 收入变多 → 能造的单位变多 → 流量上限变大。
两者必须一起定，否则「只加时间」会让赢更不划算。

| 项 | 原值 | **落地值** | 依据 |
|---|---:|---:|---|
| `win_reward` | +1.000 | **+5.500** | 2× 回合下流量上限 2.18 的 2.5 倍 |
| `loss_reward` | −1.000 | **−5.500** | 与 win 对称 |
| `produce_bonus` | +0.100 | **+0.030** | 单位是手段；非 0.05，因为回合翻倍了 |
| `kill_bonus` | +0.250 | **+0.069** | 整支敌军（40 个）≤ 0.6 × 赢局 |
| `loss_penalty` | +0.250 | **+0.069** | 随 kill_bonus 缩放，保持交换定价 |
| `build_bonus` | +0.200 | **+0.500** | 见下方说明 |
| `timeout_penalty` | +0.200 | **+2.800** | 半个赢局 |
| `episode_ticks` | 20056 | **40112** | 2× 回合；见 §2 |

**为什么 `produce_bonus` 是 0.03 而不是 0.05**：回合从 335 s 变成 668 s，
可赚信用点从 12,712 变成 25,404，可负担单位从 36.3 变成 72.6。
若沿用 0.05，流量上限会是 `0.05 × 72.6 = 3.63`，仍占赢局的 66%。
取 0.03 后流量上限 `2.18`，赢局是它的 **2.53 倍**。

改后自检（脚本实测，`python .runtime/optimal_policy_analysis.py`）：

```
                        历史基线     落地值
production flow cap       +7.26      +2.18
kill reward, 整支敌军     +12.00      +3.31
挂机净收益                 +7.06      −0.62   ← 从正变负
win_reward                +1.00      +5.50
```

**7 条不变量全部通过：**

| 不变量 | 结果 |
|---|---|
| flow cap < win_reward | ✅ 2.18 < 5.50 |
| stall payoff < 0 | ✅ −0.62 |
| 整支敌军击杀 < win | ✅ 3.31 < 5.50 |
| 有利交换仍有正收益 | ✅ +0.0322 |
| timeout < 输一局 | ✅ 2.80 < 5.50 |
| build_bonus ≤ 0.25 × win | ✅ 0.50 ≤ 1.38 |
| produce_bonus < build_bonus | ✅ 0.030 < 0.50 |

**为什么 `build_bonus` 提到 0.50**：既有不变量
`build_bonus <= 0.25 × win_reward`（`tests/test_rwpp_economy_contract.py`）
在 win 从 1.0 涨到 5.5 后要求 build ≥ 1.375 才不违反，但那条测试的方向是
「建造不能比赢更值钱」。把 win 提到 5.5 后这条约束自动放宽，
0.50 既满足 `<= 0.25 × 5.5 = 1.375`，又保持「一个建筑 < 一个单位 × 2」
的历史比例（`produce_bonus × 2 = 0.06` → 这里刻意留在 0.50，
因为建筑是生产的**前置条件**，且总量受 `economy_max_extractors/factories` 限制）。

### 1.5 一个反直觉但重要的发现

按「每信用点收益」排序，**矿场是全表最优**：

| 行为 | 造价 | 奖励 | 每 1000 cr |
|---|---:|---:|---:|
| 矿场 `extractorT1` | 700 | 0.7222 | **1.0317** |
| 炮塔 `c_turret_t1` | 500 | 0.6000 | 1.2000 |
| 防空 `c_antiAirTurret` | 600 | 0.6000 | 1.0000 |
| 坦克 `c_tank` | 350 | 0.0300 | 0.0857 |
| 炮兵 `c_artillery` | 900 | 0.0300 | **0.0333** |

两件事：

- **经济决策本来就是对的**——这解释了为什么课程里的矿场扩张能跑通；
- **军队决策完全错了**。`bonus_produce` 是**定额**，不看单位是什么、多少钱，
  于是最便宜的单位以 2.6:1 压倒炮兵。**奖励能表达的最优军队 = 「最便宜的兵堆最多」**。
  这正面解释了你报的症状 ②「不攻击敌方高输出单位」：
  **是奖励在惩罚造炮兵，不是策略没注意到。**

> **落地时修正了一处**：因为 `build_bonus` 从 0.20 提到 0.50（否则
> `build_bonus <= 0.25 × win_reward` 的既有不变量会被 5.5 的 win 破坏），
> 炮塔的每信用点收益（1.2000）现在**高于**矿场（1.0317）。
> 这是可以接受的：炮塔只有 2 个的配额（`economy_max_turrets`），
> 且它保护的是收入本身；但它确实是这套权重下唯一"顺手变便宜"的项，
> 记在这里以免日后误判成 bug。

## 2. 时间上限：确实该提高

### 2.1 先排除一个混淆项

`difficulty_eval.json` 里 96 局全部在 715–1249 决策就结束，看起来「早退」。
核查后是**丢帧**，不是早退：那批评估用 `frame_ms=1` 且未开 lockstep，
`ticks/decisions` 是 23–79 而不是 10。

交叉验证全部 `eval_report.json` 后，两种状态很干净：

| 配置 | ticks/decision | 例子 |
|---|---|---|
| lockstep 开 | **恒等于 10.00** | `twoslot-mask-long`: 20056/2006 |
| lockstep 关 | 19 – 79 | `ppo-1a19c587`: 20056/446 |

所以**回合是打满封顶的**，提高上限是有效手段。

### 2.2 但要同时看清战况

lockstep 跑（`twoslot-mask-long`，4 局全部打满 2006 决策）：

```
seed 70000: own_alive=19  enemy_alive=39
seed 70001: own_alive=19  enemy_alive=39
seed 70002: own_alive=19  enemy_alive=37
seed 70003: own_alive=19  enemy_alive=33
```

打满了时间，双方都有军队，**但没有任何一局分出胜负**，而且敌方数量在我方之上。

### 2.3 代价与落地方式

引擎模拟是瓶颈（`--frame-ms 0`，已满速），墙钟基本随 tick 线性：

| 倍数 | ticks | 游戏秒 | 决策数 | 每 update 墙钟 |
|---:|---:|---:|---:|---:|
| 1.0 | 20056 | 334 | 2005 | 162 s |
| 1.5 | 30084 | 501 | 3008 | 242 s |
| **2.0（已落地）** | **40112** | **669** | **4011** | **323 s** |
| 3.0 | 60168 | 1003 | 6016 | 485 s |

采用 2.0 倍，并通过**新增的 `episode_tick_multiplier` 字段**实现，而不是
写死 `--episode-ticks 40112`：

- 它是**推导封顶的乘数**，所以换地图自动适配（换小图不会给 40112）；
- **显式 `--episode-ticks N` 永不被乘**——否则 `--episode-ticks 40112`
  会和操作员说的数字不一致；
- `--episode-tick-multiplier 1.0` 精确还原历史值 20056，便于 A/B。

先不上 3 倍的理由已写进字段注释：流量上限随回合线性增长，
在权重还没同步调整时加长回合会让赢**更**不划算。

## 3. 敌方 AI：可配置，且确实会进攻

### 3.1 我上一轮的错误

`docs/内置AI不进攻_根因与修复.md` 里「AI 只造 builder + scout」的结论，
对应的是 `--unlock-ai` 顺手打开 `AI.aggressiveMode` 的**旧行为**。
那个 flag 的语义是「剧本角色」：`Base.chooseBuildingToBuild()` 返回 null、
`Base.defendBase()` 被跳过。桥梁**已经不再设它**了，所以那个结论已失效。

### 3.2 机制（字节码确认）

```
Team.getAIDifficultyArmyValue()  = (int)(getArmyValue() × getAIDifficultyIncomeMultiplier() + 0.5f)
```

难度既改**收入倍率**，又直接改**「攒多大兵才进攻」的阈值**。
这是引擎自带的进攻闸门，不需要改引擎。

各难度收入倍率（`incomeMultiplierFor`，已与字节码核对）：

| 难度 | −2 | −1 | 0 | 1 | 2 | 3 |
|---|---:|---:|---:|---:|---:|---:|
| 倍率 | ×0.40 | ×0.70 | ×1.00 | ×1.40 | ×1.80 | **×3.70** |

（难度 3 额外 +1.5 平加，故 1 + 3×0.4 + 1.5 = 3.7）

### 3.3 实测：难度旋钮是有效的

`difficulty_eval.json`，每档 48 局：

| 难度 | 敌军存活均值 | 区间 | 我方存活 |
|---|---:|---|---:|
| +1 | 25.8 | 11–40 | 13.0 |
| +3 | **78.1** | **49–104** | 10.2 |

难度调高，AI 造的兵**多 3 倍**、压得更近。**AI 会建造、会扩张、会接近——只是
在 20056 tick 内还没走到我们基地。**

所以第 3 点不是「改架构」，是**调旋钮**，和你的判断一致。

### 3.4 建议

保持 `--unlock-ai`（它只清 `aiLimitedUse`，是必需的一半），
用 `--enemy-ai-difficulty` 控进攻强度。**建议先用 1，不要上 3**：
难度 3 时敌军 78 个、我方只剩 10 个，那是被碾压的分布，学不到东西。
真正的瓶颈是**没接触**，不是**打不过**，而这个由时间上限解决。

## 4. 三件事的关系

| 改动 | 单独做会怎样 |
|---|---|
| 只改奖励权重 | 仍然没有交锋，**没有胜利信号可学** |
| 只提高时间上限 | 造兵流量上限随之变大，**赢更不划算**（3.63 → 7.3） |
| 只调 AI 难度 | 会被碾压，且奖励仍导向挂机 |

**三者必须一起改**，而且互不替代。这解释了为什么之前任何单一调整都没能改变行为。
