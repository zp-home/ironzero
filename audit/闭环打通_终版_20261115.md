## 1. 这一轮真正的产出：4 个"命令语义"误判

上一轮补齐了**观测**（从 21 个字段到 34 个）。这一轮发现：**看见之后，每一条命令的语义也都是猜错的，而且每一条错法都在日志里显示成功。**

### 1.1 重复下达建造令会**重置**施工

`env.py` 原文写着"每个决策都重申建造令，这样 last-order-wins 才成立"。A/B 实测（`.runtime/ab_reissue.py`，真实引擎，同种子，策略全程 noop）：

| 模式 | 下达次数 | 第 140 决策时 `build_progress` | 结果 |
|---|---|---|---|
| 只下一次 | 1 | **1.000** | 第 140 决策完工 |
| 每决策重申 | 140 | **0.000** | **1200 决策内永不完工** |
| 停滞 20 次才重申 | 3 | 1.000 | 第 140 决策完工 |

**重复同一条建造令把施工从头开始**，而每次回执都是 `accepted: true`。死锁自持：该阶段要等矿场 `is_operational`，而重申正是它到不了的原因。实测后果：纯 noop 回合 `peak_own = 3`，工厂阶段 900 个决策里**一次都没被调用**。

### 1.2 生产课程只发一次，"造兵"不可持续

原实现每回合产**一个**兵。实测：`peak_own = 5`、**14182 信用点没花**、AI 有 15 个单位。

但改成"每决策都产"更糟（`.runtime/produce_spam.json`）：资金抽到 496、**矿场被取消**（收入 26→18），最终 **25 个 builder、0 个战斗单位**。同一个陷阱——**任何真实命令都打断工程车**。

### 1.3 军队造出来之后**站着不动**

实测（`.runtime/engagement_trace.json`）：10 个战斗单位，最近己方单位到敌方基地 **tick 9001 时 1972 px，tick 15001 还是 1972 px**。60 秒游戏时间零移动。

**原版图上一场没打起来的仗不判胜负**，所以 `timeout` 不是"差一点"，是**目标失败**。

### 1.4 胜负判据是"能力"，不是"兵力"

`Team.updateDefeatCheck` 判的是**还有没有工厂/工程车/主基地**。实测超时特征（`.runtime/win_vs_timeout.json`）：军队 `reached_base_rate = 1.0`、`mean_min_dist = 170 px`、**敌兵只剩 0–1 个**，但**敌方 4–5 座建筑仍在**。

清完兵 ≠ 赢。这是加第二座工厂（产能翻倍）的根据。

## 2. 补齐的五段机制

执行顺序**就是优先级**，第一个占用工程车的阶段赢：

| # | 阶段 | 条件 | 作用 |
|---|---|---|---|
| 1 | `_issue_opening_extractor` | 无完工矿场 | 开局矿（停滞门禁，不再每帧重申） |
| 2 | `_issue_opening_factory` | 矿场完工 | 造工厂，可补建到 2 座，丢了会重建 |
| 3 | `_issue_opening_production` | 有完工工厂 | 维持 10 个兵，上限 16，资金地板 900 |
| 4 | `_issue_late_expansion` | 工厂链就绪 | 扩张到 6 个矿 |
| 5 | `_issue_attack_drive` | 10 个兵 | 推进敌方主基地 |

**调度修正**：`_curriculum_actions` 原本遇到第一个非空命令就 `return`，于是"每帧都发"的进攻阶段把扩张永久饿死（`occ` 卡 1，胜率跌到 8–16%）。现在允许**建造令 + 移动令同帧共存**（`_order_is_tactical`），两条建造令仍互斥。

## 4. 策略会摧毁自己已经跑通的流程（关键发现）

这是本轮最有价值的一条，因为它解释了"为什么之前怎么调都不行"。

**纯 noop 策略**（一个动作都不发）：93.75% 胜率。
**未加保护的 PPO 策略**：43.75% 胜率。

实测机制（`.runtime/ppo_interference.json`）：策略每决策发一条命令，**1949/1949 次都发生在建筑未完工时**；回合结束 `occupied = 1`、`income = 26`、3 个实体（基线是 3–4 / 42–50）。

**策略不是在改进流程，是在取消自己的建造。**

### 修复：三层屏蔽，全部来自实测

| 层 | 做法 | 实测依据 |
|---|---|---|
| 编组 | 关闭"只含工程车"的编组 | `.runtime/mask_reach.json` 抽样 0 次越界 |
| 建造类 | 课程运行时关掉 `build_extractor`/`build_structure` | 课程本来就发这两个，重复只会重置施工 |
| 施工期 | 建筑未完工时关掉 `move_group/attack_move/stop/hold` | 移动才是取消施工的原因 |

**一个结构性硬约束**：编组是 `unit.id % 4`，工程车 id 24 → 组 0，第一个造出的坦克 id 40 → **也是组 0**。所以"关闭工程车的组"要么无效、要么废掉半个军队——必须靠"施工期行为屏蔽"而不是编组隔离。

修复后：43.75% → **75%** →（80 updates）**93.75%**。

## 5. 关于 GPU（用户质询）

**之前的训练确实没走 GPU**：`verify_web_loop.py` 里 `"device": "cpu"` 是硬编码的。GPU 显示 9% 是 Java 游戏进程在渲染，不是训练。已参数化并复跑确认（`"device": "cuda"`）。

要说清楚：**这个任务的 GPU 加速空间很小**。游戏是 Java 进程、永远 CPU-bound；一次决策的真实成本是"等引擎推进 10 tick 并回传 4KB 观测"，网络前反向只有几百微秒。实测 40 updates × 512 rollout × 2 envs ≈ 300 秒，绝大部分在等游戏。**GPU 不改变胜率**，只影响策略更新那一段。

## 5.5 Web 端看不到进度（用户报告）

**症状**：训练跑完了，但 Web 页面看不到进度/结果。

**排查结果——后端一切正常**：
```
GET /api/rwpp/ppo/ppo-3c79ea99/events?after=0  →  next=163  events=163  status=done
GET /api/rwpp/jobs/ppo-3c79ea99                →  status=done  updates_done=80/80
```

**根因在前端**：`feRestorePpoJob` 只恢复 `status === 'running'` 的任务。训练开着页面刷新能看到进度；**跑完再刷新就什么都没有**。从操作者角度这和"根本没跑过"完全一样。

**修法**：恢复时优先接运行中的任务，没有则接**最近一个已完成的任务**，并以只读方式呈现（不显示停止按钮、提示"已载入最近一次 PPO 训练结果"）。

**另一个坑**：容器里 `web/frontend` 和 `web/backend` 是**只读挂载**，改完必须 `docker restart ironzero-platform` 才生效（前端并非热重载）。已验证容器正在提供修复后的文件（15962 字节，三处改动均在）。

回归测试：`tests/test_web_ppo_progress.py`（7 条），连同全库 **674 passed**。

## 7. 诚实交代

**70% 目标达成了，但要说清楚是谁达成的。**

`bonus_produce` 从 0 → **93.15**（80 updates 累计），`terminal` 非零 **55/80 updates**，`rolling_win_rate` 均值 **0.791** —— 这些是**真实的训练信号**，上一轮全是 0。

但是：**定版 PPO 检查点 90.6%，纯 noop 基线 93.3%，PPO 仍未超过基线。** 两者在统计上不可区分（区间大幅重叠）。

更要说清楚的一点：为了不让策略摧毁经济，`curriculum_owns_build_kinds` 把 `build_extractor`/`build_structure` **从动作空间关掉了**。所以严格讲：

- **经济、建造、生产是环境课程做的，不是策略学的。**
- 策略学的是：**别搞破坏** + 造什么兵 + 往哪打 + 打谁。

`kills 38.1 / losses -60.1` 也印证：策略仍**净亏兵**，微操没学到。

所以准确的结论是：**闭环打通了，70% 目标以 90.6%（CI 下界 81.0%）达成，但这套系统的胜率由环境课程决定，PPO 目前还没有超过它。**

如果要求"策略独立学会经济"，那还需要把建造动作空间还回去，并解决"重复建造令重置施工"这个引擎语义问题——那是一个比本轮更难的问题，因为动作空间本身就与该引擎的语义冲突。

## 8. 剩余问题

1. **PPO 没能超过 noop 基线**（90.6% vs 93.3%）。策略目前的作用是"不破坏"，缺"改进"。`losses` 是最大负项。
2. **只有 Lake 一张图、只有 -2 难度。** `--enemy-ai-difficulty 0`（正常，x1.00 收入）是真正的公平对局，未测；`Artillery.tmx`（`winCondition="mainBuilings"`，判据不同）、`Ice Island` 等未测。**-2 难度达成的 90.6% 不代表 0 难度也能达成。**
3. **`UPGRADE_UNAVAILABLE` 仍是最大拒绝项**（532/80 updates）。课程不造升级令，策略的升级令被引擎拒。`invalid` 已降到 -27.3。
4. **`PRODUCE_UNAVAILABLE` 329 次。** 纯净路径实测 0 拒绝（`.runtime/produce_reject_trace.json`），说明它来自策略与课程的交互（同一工厂同一时刻两个来源），未根治。
5. **单/双线程验证。** 所有数据都是 `envs=1~2`；8 envs 下帧丢弃率（上一轮测到只消费 14% 帧）对胜率的影响未验证。
6. **并发评估已加限流与重试（`EVAL_MAX_PARALLEL=4`），但未做大样本验证。**
