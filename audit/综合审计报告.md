## 0. 摘要：一句话结论

**这个仓库的"战术层"是真实可用的，"战略层"大面积是文档虚构的；而当前工作区正处在一个危险的中间态——一次"经济系统 5→7 动作头"的改动只改了三分之一，导致 HEAD 上 201 个测试全绿的状态变成了 11 失败，并且让 158 个历史 checkpoint 中的 143 个无法加载。**

如果只能记住三件事：

1. **工作区当前是坏的，且不是测试过期，是功能真的断了一半。** 已验证：`git stash` 后 HEAD 跑 `201 passed`，恢复工作区后 `11 failed, 190 passed`。
2. **"经济/建造/生产"整套能力在真机上根本不存在。** Python 协议定义了 10 种动作，Java 桥接只实现 5 种；剩下 5 种（`build_extractor`/`build_structure`/`produce_unit`/`upgrade_building`/`repair_target`）在真机被静默计入 `rejected`，既不回 error 也不回原因码。
3. **文档承诺的"战略层"几乎全是空壳**：课程学习、自博弈/Elo/模型晋级、MatchSpec、Episode 状态机、Policy Service、Safety Supervisor、`lan_eval` —— 在 `src/ scripts/ web/ tools/ tests/ configs/` 中 grep **全部零命中**。

## 2. 最重要的一张表：动作空间五方错位

这是整个系统最深的裂缝。同一条策略输出，在五个环节有不同的含义：

| 来源 | 动作种类数 | 位置 |
| :--- | :--- | :--- |
| `protocol.ActionKind`（协议真源） | **10** | `protocol.py:28-37` |
| `mock_engine.ACTION_KINDS`（位置即动作 id） | **10** | `mock_engine.py:34-45` |
| `MicroDuelConfig.action_nvec[0]`（策略头宽度） | **7** | `micro_config.py:103` |
| 真机 Java `applyStep` 实际支持 | **5** | `IronZeroBridge.java:619-642` |
| 宏控 `MacroController` 产出 | **3**（build_extractor/build_structure/produce_unit） | `macro_controller.py:70-103` |

由此产生三个具体后果（均已实测）：

- **策略不可达动作**：`action_nvec[0]=7` 只能采到索引 0..6，而 `ACTION_KINDS` 有 10 项 → `produce_unit`/`upgrade_building`/`repair_target`（索引 7/8/9）**永远不可能被选中**，纯属死维度。
- **mock 路径经济动作 100% 失败**：`env.py:170-203` 的 `decode_actions` 没有 `build_*` 分支，发出去缺 `slot_id`/`x,y` → 引擎返回 `INVALID_MESSAGE`（实测连发 35 步得 140 条拒绝）。
- **真机路径静默丢弃**：`IronZeroBridge.java:643-647` 对未识别 kind 直接 `rejected++`，**既不回 error 也不回原因码**，Python 侧只看到一个不透明的计数。

## 4. 垃圾代码（最恶劣的几处）

### 4.1 占位注释冒充实现 —— 本次审计最典型的"上一个 AI 的半成品"

`src/ironzero/observations.py:313-317`：

```python
group_mask = np.zeros(cfg.groups + 1, dtype=bool)
# ... (keep existing group logic)          # ← 这句注释是假的
for unit in own:
    group_mask[int(unit.get("group_id") or 0) % cfg.groups] = True
group_mask[-1] = True
```

`# ... (keep existing group logic)` 声称"保留原有逻辑"，实际上 `git diff` 显示原来的 `group_ids_known` 兜底分支（当真机桥不提供 `group_id` 时开放全部 group）**被真删了**。同一函数 L322 还有一句 `# ... rest of the function remains similar`。

**实测后果**：真机桥只发 unit id、不发 `group_id`，于是

```
group_mask = [True, False, False, False, True]   # 4 组里只有 1 组可指挥
```

即 **75% 的部队无法被策略指挥**。这是 `tests/test_rwpp_25v25.py:178` 的失败原因，也是"真机学习效果差"的一个直接解释。

### 4.2 一行塞两个奖励项 + 语义挪用

`src/ironzero/rwpp_env.py:702`：

```python
"income": float(self.micro.extractor_reward) * float(economy_stats.get("income", 0.0) / 10.0), "bonus_build": 5.0 if any(...) else 0.0,
```

三重问题：① 把"造矿奖励系数"当"收入系数"用；② `bonus_build` 硬编码 `5.0`，比 `potential_coef=0.5` 的势能项大 10 倍，是事实上的主导奖励；③ **`income` 恒为 0** —— 因为 `IronZeroBridge.java:281` 把 `income` 硬编码成了 `0.0`。这个奖励分量在真机永远贡献 0，纯属噪声。

### 4.3 静默吞异常

| 位置 | 问题 |
| :--- | :--- |
| `train_rwpp.py:209-213` | `except Exception: pass` 吞掉线程池二次 `map()` 的 `RuntimeError` |
| `rwpp_ppo.py:85-86` | 注释写"shutdown must never mask training errors"，实际把**所有**关停异常都掩盖了 |
| `web/backend/app.py:680-699` | 裸 `except:` 吞掉 checkpoint 扫描异常 |

### 4.4 假测试

`tests/test_training_pipeline.py:74`：

```python
self.assertTrue((out / "summary.json").exists() or True)   # or True → 永远真
```

而 `summary.json` 实际由 `train.py:64` 写、不由 `PPOTrainer.train()` 写，所以这条断言本来会失败——是用 `or True` 糊过去的。

### 4.5 三份重复实现

- **focus-fire 控制器**抄了三份：`baseline_rwpp.py:93-113`、`bc_warmstart_rwpp.py:125-145`、`mock_engine.py:913-989`

## 10. 对"上一个 AI"的整体判断

这个仓库不是垃圾工程 —— PPO/GAE/掩码/评估/回放/真机托管的骨架是扎实的，201 个测试在 HEAD 上是全绿的，`runs/final_eval_ft` 里也有真实的 30 胜 10 负评估记录。

问题出在**迭代方式**：

- **一次改不完就留在工作区**：5→7 的动作空间改动明显是中途被打断的，留下了 11 个失败测试和 143 个损坏的 checkpoint。
- **用注释冒充代码**：`# ... (keep existing group logic)`、`# ... rest of the function remains similar` —— 这是最危险的模式，因为它让 `git blame` 看不出逻辑被删了。
- **先写文档后写代码，且从不回头对账**：6 项核心能力零代码，README 的"102 项测试"实际是 201。
- **调试残留随手丢在 `src/`**：`test_tutorial.py` 放在 `src/` 里从未被 pytest 收集。

**建议的第一个动作**：先把工作区那个未提交的 5→7 改动**决定去留**（回滚或补完），让 `pytest` 回到 201 全绿，再谈其他。在此之前，任何训练结果都不可信。
