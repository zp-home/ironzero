# 观测契约补齐：桥到底缺了什么信息，补完还剩什么

日期：2026-11-15
范围：`src/ironzero_bridge/java/ironzero/IronZeroBridge.java`、`src/ironzero/observation/features.py`、`src/ironzero/micro_config.py`、`src/ironzero/engine/constants.py`、`tests/test_observation_contract_fields.py`

---

## 0. 一句话结论

**你的判断是对的：桥梁确实缺信息，而且缺得比想象的多——不只是"少了几个维度"，是已经写进代码的维度全部在被喂常数。** 补齐之后，闭环并未因此打通（胜率仍是 0），但**能看见的东西**从 `21` 个字段涨到 `34` 个，其中 8 个是新列、1 个是修好的死列、1 个是修好的死字段。**剩下的瓶颈不再是"看不见"，而是"看见了但学不会"**——这一条在第 6 节用数据说明。

同时，补齐过程中发现 **8 个独立缺陷**，其中 3 个是**从来没有生效过**的功能（不是回归，是从来就走不通），1 个是**信息本身错误**（`can_upgrade` 对半成品建筑报 true，直接制造了全程最大的负奖励项）。

## 2. 最严重的：`order_type` 这个列从一开始就是死的

`features._entity_features` 第 5 列读的是 `unit["order_type"]`：

```python
order = ORDER_IDS.get(str(unit.get("order_type", "idle")), 0)
```

**桥从来没有发过这个键。** 实测 40 个真实决策帧（`.runtime/contract_gap.json`）：

```
order_type_values_seen: ["None"]
```

也就是说这一列**对每一个单位、每一帧、每个回合都是常数 0**。网络有一列输入永久恒为 0，等于少了一列的容量，而且这一列本该回答"这个单位是在建造、在移动、还是在打"——正是经济闭环最需要的那一列。

修法分两处：
1. 桥里新增 `orderName(Unit)`，读引擎 live waypoint（`getCurrentWaypoint()` + `getEffectiveAttackTarget()`），映射到 `ORDER_NAMES` 的拼写；
2. `ORDER_NAMES` 补了 `build` 和 `repair`。**不补这两个，正在造东西的工程车会退化读成 `idle`**——恰好把这个单位最重要的事实抹掉。

## 3. 补齐过程中发现的 8 个缺陷

### 3.1 资源池占用永远是 `false`（从来没过）

这是**最贵的一个**。

```java
// 旧代码
if (slotLevels.length > 0 && unit.isBuilding() && unit.placeOnlyOnResPool()) {
```

`Unit.placeOnlyOnResPool()` 硬编码返回 `false`（`Unit.java:1922`），**整个 stock 代码库没有任何子类覆盖它**——`Extractor` 也没有。"只能建在矿上"这件事存在**单位类型**上：`UnitType$1.placeOnlyOnResPool()` 返回 `true`。

后果，实测（`.runtime/raw_entity.json`，旧 jar）：

```
矿场在 (1170, 2050)  →  slot 0 也在 (1170, 2050)
slot 0: occupied=false, extractor_level=0
```

矿场就站在矿上，矿报"没人占"。连带三条：
- Python encoder 的 `extractor_slots`（已占矿数）永远 0；
- `build_extractor` 专挑**空**矿（`decoding.py` 的 `free` 过滤），所以它会**对同一个矿反复下命令**；
- 收入涨了（18 → 26）但观测里看不出为什么。

修法：新增 `placeOnlyOnResPool(Unit)` 走 `getUnitTypeInterface()`，三处调用点全部改过去。

验证（`.runtime/stream_dump.json`，新 jar，同图同种子）：

```
slot_transitions:
  occupied=False,level=0 : 9615
  occupied=True,level=1  : 1185     ← 旧 jar 里这个数字是 0
first_occupied_tick: 151
```

### 3.2 `--win-mode objective` 从来没生效过

日志里一直是：

```
[ironzero] unknown --win-mode: 11 (keeping native)
[ironzero] world ready: ... winMode=native ...
```

启动器传的是 `--win-mode objective`。原因有两层：

1. **`objective` 从来不是合法值**（`git show HEAD` 确认）：旧代码只认 `annihilation|native`。所以审计里"改成 objective 模式"的那个修复**没有落地**——参数被拒，静默回落到 `native`。
2. 我加 `--seed` 时，把 win-mode 的解析块**误并进了 seed 分支**，于是它拿 seed 的数值当模式名。seed=0 时该参数不发送，所以**日志里一个字都没有**，看起来像"没这功能"。

两层都修了：独立分支 + 接受 `objective`。验证：

```
win_mode_reached_engine: "objective"
```

这条直接关系到"原版地图判不出胜负"这个阻断——`noConstructionOrTech` 目标在 stock 图上是靠 `win-mode objective` 之外的判据处理的，回落成 `native` 就等于这个修复不存在。

### 3.3 激光塔不算防御建筑

`LaserDefence.canAttack()` 返回 **`false`**（`LaserDefence.java:268`）——它是**弹丸拦截器**，不是炮。所以 `isBuilding() && canAttack()` 会把游戏里最显眼的防御建筑判定成"无害农场"。

修法：`isBuilding() && (canAttack(unit) || isLaserType(unit))`。

### 3.4 炮塔等级永远报 1

`Turret` **不覆盖** `Unit.getTechLevel()`，继承到常数 `1`。所以一门 T3 炮报"1 级"，而炮塔等级恰恰决定"这一波推得推不动"。真值在 `Turret.getTurretLevel()`。

### 3.5 队列字段抛异常风险

`CustomUnit.getTurretShootDelay(int)` 直接索引 `turretTemplates` 不检查越界；`getTurretCount() < 1` 的守卫是**必需的**，不是防御性冗余——否则一个 mod 单位就能让整帧观测失败。

### 3.6 `can_upgrade` 在建筑没造完时就说 `true`

这是**唯一一个「信息本身是错的」**的缺陷，不是缺失，是污染。

`getBuildActionId()` 回答的是"这个类型有没有下一级"，**不是**"现在能不能升"。正在施工的建筑在整个建造期间都报告一个真实的升级 action。实测（`.runtime/raw_entity.json`）：

```
tick 161: build_progress 0.000  is_operational false  can_upgrade TRUE
tick 301: build_progress 0.029  is_operational false  can_upgrade TRUE
...
（整个 18000 tick 的建造期，全部为 true）
```

后果链条：Python 的 mask 只要**任一**己方实体报 `can_upgrade` 就打开 `upgrade_building`，`decode_action` 再从这些实体里挑一个 → 于是**开局矿场的整个建造期**，mask 都在广告一次引擎必然拒绝的升级。

实测 24 个 PPO update：`UPGRADE_UNAVAILABLE = 798`，对比 `BUILD_UNAVAILABLE = 157`，占了 `invalid = -17.49` 的大部分——**而 `invalid` 是全程最大的负奖励项**。

修法：`canUpgrade` 增加 `isNonOperational()` 门禁。"没造完就不能升"是引擎自己的定义，不是补一个启发式。

**修前 / 修后（同图、同种子、同 24 updates × 512 rollout × 4 envs，obs_dim 都是 639）：**

| | 修前 | 修后 |
|---|---|---|
| `UPGRADE_UNAVAILABLE` | **798** | **0**（消失） |
| `BUILD_UNAVAILABLE` | 157 | 96 |
| `UNIT_NOT_OWNED` | 31 | 16 |
| `invalid` 合计 | **−17.4917** | **−1.6375** |
| `potential` 合计 | −18.5051 | −12.2876 |

**总拒绝数 986 → 112（−88.6%），`invalid` 负奖励缩小 90.6%。** 这是本轮单项影响最大的修复，而它甚至**不是缺信息**——是**错信息**。这一条恰好回答了你的问题：缺信息要补，但**已有的错信息比缺信息更贵**。

### 3.7 我自己写的 JSON 括号错（`]}` 多一个 `]`）

`factoriesJson` 里 `queued[]` 已经闭合，工厂对象又用了 `"]}"`：

```
..."queue_progress":0.000]}]}}
```

**每一行观测都是非法 JSON。** 900 条消息，900 次 `JSONDecodeError`。Python env 的读取器宽容到把这个错误吞掉了，所以从 env 里面完全看不出来——只有按协议读裸字节才暴露。这是本轮的教训：**契约层的 bug 必须用协议层的手段验证**，用编码器的单元测试永远查不到。

### 3.8 `--init-checkpoint` 预热一直用错源布局

`train_rwpp.main` 调 `_config_from_saved(payload)` 传了整个 checkpoint payload，但这个函数要的是**配置字段字典**，而那些字段全在 `payload["micro_config"]` 下面。过滤后字典为空 → 直接返回 `DEFAULT_CONFIG`。

```python
old (whole payload)  -> max_entities=8  map_channels=3  == DEFAULT? True
new (micro_config)   -> max_entities=25 map_channels=4
```

所以**每一次预热都被告知源布局是 8v8/3通道的默认值**，不管 checkpoint 实际是什么。`_column_source` 于是按一个从未存在过的布局算重映射，迁移过来的 trunk 列被绑到错误的特征上——这正是"加载了 99% 参数但行为像噪声"的失败模式，而且因为形状都对得上，**一句警告都不会有**。

## 6. 补完之后还剩什么——这才是回答你的问题

**不是"缺信息"了。** 缺的信息补上了，可测的东西都测到了。但胜率不会因为这个数字变动就跳到 70%，原因是三层，且都不在桥里：

### 6.1 动作空间表达不了"同时做两件事"

工程车是**双用**单位：它既是经济单位（造矿造厂），又是机动单位（`unit.id % 4` 编组）。但一次决策只发**一条**命令，而**任何真实命令都会取消上一条**。所以策略只能在"继续造"和"去看一眼"之间来回切换，而一个建筑要 ~140 tick 不被打断。

代码里其实**已经写好了双槽动作**（`decoding.ECONOMY_ACTION_KINDS` / `TACTICAL_ACTION_KINDS` / `decode_action_multi` / `multi_action_nvec`），**但没有任何脚本用它**，训练器还在用单槽 `micro.action_nvec`。这是现成的、已验证的桥梁，只是没接上。

### 6.2 变长需要的不只是观测

`max_entities=25` 但每回合存活单位在 1–50 之间浮动，`prioritise_own` 只保证建筑/工程车排在前面。要打出"经济→科技→兵力"的完整链条，需要的不是更多观测列，是**分层策略**（宏观指令 + 微观执行），而 `strategy/` 下已经有 `macro_controller` 的骨架。

### 6.3 敌人不是"另一个玩家"，是带作弊的 AI

`enemy_ai_difficulty=-2` 时 AI 收入 ×0.400。**这个数在观测里看不见**（`ai_teams` 在 `info` 里，没进 `global_state`）。所以策略无法知道对手的经济规模——这不是"缺一个字段"的问题，是这个字段会泄漏对手作弊量，属于设计取舍。

## 8. 诚实交代：这一轮**没有**解决的问题

1. **胜率仍是 0。** 补齐观测不等于学会。两次 24-update 实跑全部 `timeout_rate = 1.0`，`bonus_produce` 两次都是 0.0。观测契约修好了、总拒绝率降了 88.6%、`invalid` 负奖励缩小 90.6%，但**"学会经济"这一步没有发生**。

2. **`bonus_produce` 为 0 的原因现在更清楚了**：不是"产不出兵"，而是策略在这 24 个 update 里**从没选过 `produce_unit`**。开局的产兵课程本该在工厂造好后代发一次，但 §6.1 的单槽限制让"继续造厂"和"去造兵"互斥——课程发的那一单被策略自己的命令顶掉。这条要在双槽接上之后再测。

3. **`getTurretDamage` 对 stock 坦克返回 0**。引擎把 stock 单位的伤害藏在 `Projectile.reloadTime` 里：`Tank.fireTurret` 设 `var4.reloadTime = 30.0F`（`Tank.java:133`），而 `Projectile.java:1177-1179` 再把它当伤害用：

   ```java
   float var91 = this.reloadTime;
   ... applyDamageToUnit(...);
   ```

   同一个字段在开火时是"伤害"、在冷却里是"装填时间"，没有静态访问器能区分。我**没有**发一个假的"伤害=0"字段（那会让 policy 以为坦克不痛），所以**伤害依然不可观测**。要做只能运行时遍历 `Projectile.allProjectiles` 反推，代价是每帧额外扫描、且对未开火单位无解。

4. **AoE 半径不可按单位取**。同理，只有自定义单位暴露。

5. **`remembered_enemies` 填不了**。`Unit.teamVisibility` 和 `an` 都是包级私有，无公开 API，不改引擎拿不到。

6. **AI 作弊量（income multiplier）没进观测**。见 §6.3，属设计取舍。

7. **`BUILD_UNAVAILABLE` 仍有 96 次**。绝对数比修前的 157 少（因为总交互变少），但占拒绝总量的比例升到了 86%。主因推测是建造令的编组寻址，`_builder_group` 已经改成广播槽，剩下的需要单独排查，本轮没查。

8. **`can_upgrade` 的门禁只挡了"没造完"**。造完之后如果资金不足，`can_upgrade` 仍报 true（它只回答"有没有下一级"）。掩码另有资金门禁（`extractor_upgrade_cost = 1200`），所以暂时不是问题；但如果引擎价格和 `MicroDuelConfig` 里的常数漂移，就会重新出现拒绝。**这两个价格表没有任何一处互相校验**，是下一轮该补的钉子。
