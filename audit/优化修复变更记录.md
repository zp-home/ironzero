## 6.5 实机验证（第二轮新增，含 3 个真机缺陷修复）

第一轮只做到"Java 编译通过"，本轮把桥接真正装进 RWPP 运行时跑了实机对局，**发现并修复了 3 个只能实机暴露的缺陷**：

| # | 缺陷 | 发现方式 | 修复 |
| :--- | :--- | :--- | :--- |
| 1 | **每条 obs 都不符合协议** | 用 `protocol.parse_message` 校验真实桥接输出，240/240 全失败 | `entityJson` 对无主地图要素（树）输出 `team_id=-1`，而协议是 `Field(ge=0)`。改为中性哨兵 `NEUTRAL_TEAM_ID=255` |
| 2 | **树木被当成敌人** | 实机 `global_state.unit_count=24` 但真实单位只有 4 个 | 无主要素 `teamId<0` 未过滤就进入 `else` 分支 → 敌方列表混入 20 棵树。已加过滤 |
| 3 | **回执谎报 accepted** | 回执说 `accepted=true`，引擎日志同时打印 `can not queue build` | `canQueueAction` 只反映建造菜单，不校验落点。补 `isLocked()` + `Waypoint.setBuildTo()` + `isValidNewWaypoint()` 三重预检，不可能的单不再谎报成功 |

另外把 `land_factory` → `landFactory` 的 snake_case↔camelCase 转换做成 `resolveUnitTypeName()`，兼容协议与引擎两套命名。

### 实机验证结果

```
$ python scripts/rwpp_econ_probe.py
own unit types = ['builder', 'commandCenter']
protocol errors= 0          ← 修复前 240/240 失败
engine rejects = 0
false-positive receipts = no
ECONOMY PROBE PASS (protocol clean; no capable builder on this map)
```

**一个必须说清的事实（已修正此前误判）**：`build_extractor` 在实机上仍无法执行，`build_structure` 则**取决于地图**。逐张实测 76 张官方地图后得到确切结论：

| 建造动作 | 官方地图现状 | 依据 |
| :--- | :--- | :--- |
| `build_structure`（landFactory） | ✅ **可以建造** | 实测 76/76 张官方地图的 `builder` 均 `can_build: ["landFactory"]` |
| `build_extractor` | ❌ **无法建造** | 全仓库 `assets/units` + `builtin_mods` 中，**只有 `megaBuilder`（Mega Builders mod）**的配表含 `canBuild_name: extractor`；官方默认的 `builder` 单位没有 |

也就是说：**官方图能造工厂，但造不了矿场（extractor）**。原因是 `extractor` 在原版里属于「占领矿点后自动生成」的设施，并非由建造者放置；`builder` 的建造菜单只有 `landFactory`。唯一能造 `extractor` 的 `megaBuilder` 属于内置 mod，且该 mod 默认未启用、实测启用后也未改变 `builder` 的菜单。

所以桥接现在的行为是**正确的**：它明确回 `ACTION_MASKED` 而不是谎报成功。
