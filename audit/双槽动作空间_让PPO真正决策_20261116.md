# 双槽动作空间落地：让 PPO 真正做决策

日期：2026-11-16
状态：**基础设施完成并验证通过**；训练结果尚未达标（本文最后一节说明）

---

## 零、为什么做这件事

用户的质疑（原话）：

> 什么时候出击不应该是 ppo 自己训练出来的吗？经济不也应该交给 ppo 进行宏观调控吗？为什么有课程写死多少钱干什么呀

这个质疑是对的，而且比"风格问题"更严重。核实到的代码事实：

| 维度 | 改之前由谁决定 | 位置 |
|---|---|---|
| 什么时候出击 | 课程硬编码（`attack_at_army`） | `env.py:_issue_attack_drive` |
| 打哪里 | 课程硬编码（敌方指挥中心） | 同上 |
| 经济规模（6矿/2厂/10兵/900保留款） | 课程硬编码 | `config.py:economy_*` |
| 造什么建筑 | 课程（工程车只造矿场和工厂） | `env.py:_issue_*` |
| 兵种搭配、走位、目标选择 | PPO | — |

而且循环的实现方式是：`stepping.py:91-93`

```python
actions = decode_action(action, env.obs_state, env.micro)
if extra_actions:
    actions = list(actions) + list(extra_actions)   # 课程排在策略之后
```

同一 dispatch 里课程排在策略**后面**，引擎"后到者胜"。课程的攻击阶段每轮轮换一个兵组发 `attack_move`，轮到哪组哪组就听课程的，**不吃策略的指令**。

### 更严重：之前的胜率测量因此没有证据力

所有"难度1 = 0%"的测量都是用 **noop 策略**跑的 —— 测的是课程的表现，不是 PPO 的表现。

代码注释里早就记录了一个决定性反例（`stepping.py:73-84`）：

> 训练后的策略：**43.75%**（16局7胜）
> 什么都不做的策略：**93.75%**
> "the trained policy's measured contribution was **negative**"

策略比什么都不做还差，因为它的战术指令会打断工程车的施工。

### PPO 学不会的两个机制性原因

1. **动作空间无法表达**：单槽 `[kind(10), group(5), x(8), y(8), target(9)]`，一个决策 = 一条指令。造矿场和出兵互斥。
2. **奖励在 2000 个决策之后才给出**：20056 tick 一局里，"第 80 个决策建矿场是对的"要穿过约 1900 个决策才能兑现。

## 一、做了什么

### 1. 双槽动作空间（`decoding.py` 里早已写好，但从未被调用）

`decoding.py:400-461` 的 `ECONOMY_ACTION_KINDS` / `TACTICAL_ACTION_KINDS` / `multi_action_nvec` / `decode_action_multi` 完整实现且有测试，但全仓库没有调用方 —— 因为 `masks.py` 只有单槽的 `build_masks`。

新增：

| 文件 | 改动 |
|---|---|
| `micro_config.py` | `action_slots: int = 1`；`action_nvec` 按布局分派；`is_two_slot` |
| `observation/masks.py` | `build_masks_multi()`（10 个带前缀键）+ `build_masks_for_config()` 统一入口 + `MULTI_MASK_KEYS` |
| `observation/__init__.py`、`observations.py` | 导出新符号 |
| `rwpp/stepping.py` | 唯一派发点按 `env.micro.is_two_slot` 分派解码器 |
| `rwpp/env.py` | 掩码构造改走 `build_masks_for_config` |
| `training/policy.py`（队友） | 10 头支持；5 头路径逐位不变 |
| `training/{train_rwpp,ppo,vec_rwpp,...}.py`（队友） | `--action-slots` / `--curriculum-mode` 透传 |

`build_masks_multi` 的核心设计是**"只收窄，不发明"**：先调 `build_masks` 拿单槽合法集，再投影到各槽词表。所以分槽不可能放出单槽关着的指令——这条 invariant 有测试守着。

**一个实现陷阱**（已修）：`build_masks` 用 `config.action_nvec[0]` 定 kind 头宽度，双槽 config 下那是 5（经济槽词表长度），会 `IndexError`。所以内部有个 `_single_slot_view(config)` 把 config 换成单槽视图再复用。

### 2. 课程降级：`curriculum_mode`

`config.py` 新增 `curriculum_mode: str = "orders"`：

- `"orders"` —— 现状：课程发真指令
- `"mask"` —— 课程**不发任何指令**，只通过掩码提供"这个指令引擎会拒绝"的知识
- `"off"` —— 连掩码知识也不用

配套：`curriculum_issues_orders` / `curriculum_enabled` / `curriculum_applies_masks` 三个属性，`_curriculum_actions()` 开头一处 return，保证新加的 stage 无法意外绕开。

**关键联动修复**：`curriculum_owns_build_kinds` 原本只绑 `opening_extractor`。在 `mask` 模式下课程不发指令，如果还关着 `build_extractor`，**没有任何人能建第一个矿场**——实测确认这个状态（`build_extractor` 在掩码里关闭，收入永远停在基础值）。已改为同时要求 `curriculum_issues_orders`。

### 3. 修掉的三个真实 bug

**(a) 双槽下课程静默全失效**（最严重）

课程所有 stage 构造的是 **5 元** action 向量，而 `decode_action` 校验 `len(config.action_nvec)`，双槽下是 10 → 抛 `ValueError` → 被 `_send_curriculum_order` 的 `except` 吞掉 → 课程看起来"选择什么都不做"。

实测：`action_slots=2, curriculum_mode="orders"` 时，`curriculum_issues_orders=True` 但 `_curriculum_actions()` 在 **400/400** 个决策返回 `[]`，`peak_extractors=0`，收入整局停在 18.0。

这个失败模式**天然静默**：课程本来就大部分时间返回 `[]`（各 stage 都有门控），所以"从不触发"和"每次都异常"从指令上完全看不出来。

修复：新增 `_decode_curriculum_action()`，双槽时用单槽视图解码（`_decode_heads` 只读 `vector[0..4]`，正是课程放值的地方）。修复后矿场在决策 17 出现。

**(b) 攻击阶段的死锁**

`attack_at_army` 是唯一门控。实测（`combined_ab.json`）：把它提到 18 后，兵力峰值 17、终局还是 17，但**离最近敌方建筑 720.9px —— 军队根本没出门**。同一经济在默认 target=10 下能推进到 **78.8px**。

即：经济负担不起的门槛不会让军队更强，只会让它不动。已加"平台化"规则：兵力达到 `cap*0.6` 也要出击。

**(c) 课程阶段顺序的信贷死锁**

`expansion` 排在 `production` 之后，两者共用同一个 `economy_credit_reserve` 门槛。production 先跑，把高于保留款的资金全变成兵，门槛重新关闭，expansion 永远轮不到。

实测（`stage_trace.json`）：`funds_below_reserve` 占 expansion 阻塞原因的 **747/1081（69%）**，收入整局 26.0（1 个矿场），矿场数为 1 的比例 98.5%。

改成 `expansion` 先于 `production`（`MACRO_GOALS` 默认顺序）：收入 30→46，矿场 1→3（`order_ab.json`）。

## 三、一个我修错又回滚的改动（诚实记录）

我怀疑"回执归属错误"会让 PPO 为它没发的指令挨罚，于是按 `decision_id` 加了过滤。结果**它更糟**：600 决策里只保留 2 个回执，丢掉 589 个，`invalid_penalty` 几乎永不生效。

真实机制是：桥接自由运行，回执**总是比决策晚一步到达**

```
receipt_ids: ["d-rwpp-88000-1-1", "d-rwpp-88000-1-1"]   ← 上一步的
sent_decision_id: "d-rwpp-88000-1-2"                     ← 这一步的
```

所以原代码"收本步期间到达的回执"本来就是对的，只有一步延迟，在折扣回报下可忽略。**已完整回滚**（`_receipts_for_decision` 方法已删除，`step` 恢复原样，73 个相关测试通过）。

## 四、还没解决的：训练结果

`mask` 模式下随机策略 **建不出矿场**（`peak_extractors=0`，收入 18.0）。这正是 PPO 需要学会的东西 —— 也是课程当初存在的理由。

现在的状态是：**"让 PPO 自己学"这个前提条件已经成立**（动作空间能表达、课程不再抢答、解码精确），但"它能学会"还没有证据。这需要：

1. 完整训练跑（不是 3 个 update）
2. 奖励重新设计：让"矿场建成"或"收入翻倍"在**当下**兑现，而不是等 2000 个决策后的终局（potential-based shaping）
3. 换动作空间的代价：**现有所有 checkpoint 失效**
