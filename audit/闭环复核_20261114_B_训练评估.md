## 2. 逐条回答 task-2 的 6 个问题

### 2.1 采样结构是否与单局长度匹配？`episodes=0` 是否仍存在？

**结论：`episodes=0` 已修复；但「匹配」只对了一半，真正的问题换成了决策节奏漂移。**

**(a) 采样长度已足够（✅ 这部分）**

- 最新 run 配置：`rollout_steps=256`、`num_envs=8` → **2048 决策/update**（`rwpp_summary.json` L186-207，`config` 段）。
- 单局实测决策数：**244.5**（=`409600 ÷ 1675`，其中 `409600 = 200×256×8`）。
- 因此每个 env 每 update 完成约 `256 ÷ 244.5 = 1.05` 局，`episodes` 稳定在 8–14。
- 实测 `episodes` 分布（`live.jsonl` 200 条 update 事件）：`min=0, max=14, 合计 1675`，**只有 1 个 update 是 0**（update 1，首轮还在跑第一局）。
- 对照 `docs/闭环差距分析.md` §2.6 记录的历史症状「bench4 全部 6 个 update `episodes=0`」：**该症状在 `612bdc58` 上不再出现**。

> 另一条旁证：`runs/platform/rwpp-ppo-ppo-b194f361`（4 envs / rollout 64）的 `episodes` 仍有 **119/200** 个 update 为 0（`econ_fix_long` 是 44/60）。所以 `episodes=0` 不是被"彻底修好"，而是被 `rollout_steps=256 × 8 envs` 这个配置**压过去了**；配置降回 rollout 64 就会复发。

**(b) 但「单局长度」本身是错的：有效决策间隔随并发漂移（❌ 这是新根因）**

桥的契约写死每 **10 个仿真 tick** 发一帧观测：

- `src/ironzero_bridge/java/ironzero/IronZeroBridge.java:65` → `private static final int DECISION_INTERVAL = 10;`
- `src/ironzero_bridge/java/ironzero/IronZeroBridge.java:317` → `if (engine.simulationTick - lastSentTick >= DECISION_INTERVAL || ...)`
- `src/ironzero/rwpp/config.py:38-40` 也把它写成「part of the bridge contract」的 `DECISION_TICKS = 10`。

一个 8000-tick 局因此应产生 **800 帧**。但实测 `ticks / decisions`：

| 并发 | run | 决策/局 | tick/决策 | 相对桥契约 |
|---|---|---:|---:|---:|
| 8 envs | `612bdc58` | 245 | 32.7 | **3.3×** |
| 8 envs | `8e080d15` | 242 | 33.1 | 3.3× |
| 4 envs | `b194f361` | 430 | 18.6 | 1.9× |
| 4 envs | `econ_fix_long` | 480 | 16.7 | 1.7× |
| 4 envs | `econ_fix_verify` | 512 | 15.6 | 1.6× |
| **4 eval workers** | `612bdc58` eval@200 | **418** | 19.1 | 1.9× |

数据来源：各 run 的 `metrics.json` → `evaluations[].episode_results[].{decisions,ticks}`（`ticks` 全部为 8000）。

**为什么会丢**：`src/ironzero/rwpp/session.py:96-107` 的 catch-up 循环——首帧到手后，把 socket 里已经排队的消息全部 drain 掉，**只保留最新的一帧**（`if extra.get("type") == "obs": latest = extra`），中间所有观测直接丢弃。这本身是**必要**的（`session.py:64-69` 的注释解释了不 drain 会让 `done` 裁决被 RST 吃掉，那正是历史上「引擎赢了却记成 timeout」的根因）。但后果是：

1. **决策节奏 = 引擎产出速度 ÷ 客户端消费速度**，是个和代码常量无关的、随负载浮动的量。8 并行时策略实际在「每 33 tick 决策一次」的 MDP 上训练，和 `DECISION_TICKS=10` 声明的契约不是同一个 MDP。
2. **训练与评估的控制频率不同**（245 vs 418，差 1.7 倍）。这**精确复现**了 `docs/P0修复后训练结论.md` §五.2 记录的「eval 与 train 行为不一致（train own_hp 0.68 / eval 0.33）」——那不是策略退化，是两者跑的不是同一个决策节奏。
3. **丢弃不省时间**：一局的墙钟由引擎决定（下面 2.6 节实测 12.51 slot·s/局 ≈ 640 tick/s/env）。少读观测不会让引擎跑得更快，只是把已经算出来的样本扔掉。

> 这条**不是**历史 `episodes=0` 的重复，而是它被压住之后露出来的下一层。修它不需要改 Java，只需要在 `session.py` 的 catch-up 里返回全部缓存的 obs（或至少按固定 stride 采样），代价是 PPO 每 update 要多做几次前向（511 维 MLP，RTX 4070 上可忽略）。

**(c) 另有一个只在极端配置下才暴露的结构问题**

`rollout_steps` 与「单局决策数」之间**没有任何断言或告警**。全仓库对 `rollout_steps` 的引用只有透传与范围校验（`src/ironzero/training/ppo.py:29,271`、`scripts/rwpp_service/launch.py:31,69,105`、`web/backend/app/models.py:76`），没有一处比较它和 `episode_decisions`。默认值仍然偏小：

- `PPOConfig.rollout_steps` 默认 **128**（`src/ironzero/training/ppo.py:29`）；
- GUI 表单默认 **64**（`web/frontend/index.html:727`）；
- 后端默认 **64**（`web/backend/app/models.py:76`）与 **20**（`models.py:76` 之下的 `RwppPpoRequest`，L76 `rollout_steps: int = Field(default=20, ...)`）；
- 服务端兜底 **20**（`scripts/rwpp_service/launch.py:69` → `payload.get("rollout_steps", 20)`）；
- 旧版前端 `web/frontend/app.js:7378` 仍是 `rollout=20 / envs=2 / ticks=3600`（这条路径被 `main.js` 的 ES module 版本取代，但代码还在）。

按 800 帧/局算，`rollout=64` 时每 env 每 update 只走 `64/800 = 8%` 局，`episodes` 长期为 0 —— 这正是 `b194f361` 的 119/200。

### 2.2 奖励：符号、量级是否合理？是否塑形主导、终局几乎不出现？稀疏奖励有课程/warmstart 支撑吗？

**结论：❌ 塑形主导，三个关键项结构性死零，课程只有「半个」。**

各分项的代码定义（`src/ironzero/rwpp/reward_shaping.py:392-423`）与系数（`src/ironzero/rwpp/config.py:190-240`）：

| 分项 | 定义（文件:行） | 系数 | 符号 | 实测（见 §3） |
|---|---|---|---:|---|
| `potential` | `micro.potential_coef * (φ - φ_prev)`，φ 为 combat-value 差（`reward_shaping.py:393`；φ 定义 `rwpp/reward.py:129-149`） | 0.5 | 应为 ± | **-0.63**（每局恒负） |
| `engagement` | `engagement_coef * (prev_dist - dist)`（`reward_shaping.py:383-391`） | 0.3（`config.py:190`） | ± | +0.003（≈0） |
| `strategy` | `strategy_coef * (ψ - ψ_prev)`（`rwpp/env.py:261-269`，ψ 见 `rwpp/strategy.py:64-86`） | 0.5（`config.py:195`） | ± | **+0.2469 恒定** |
| `kills` | `kill_bonus * max(0, prev_enemy_alive - enemy_alive)`（`:396`） | 0.25（`config.py:196`） | + | **0.000 / 0 次非零** |
| `losses` | `-loss_penalty * max(0, prev_own_alive - own_alive)`（`:397`） | 0.25（`:197`） | − | 0 ~ -0.06 |
| `income` | `extractor_reward * Δ(income_rate) / 10`（`:398`） | 0.5（`micro_config.py:138`） | + | **+0.97**（最大正项） |
| `bonus_build` | `build_bonus * new_buildings`（`:403`） | 0.20（`config.py:204`） | + | **+0.51** |
| `invalid` | `-invalid_penalty * #{rejected}`（`:404`） | 0.05（`:198`） | − | -0.05 |
| `idle` | `-idle_penalty`，仅在「发 stop/hold + 敌人在交战半径内」（`:405-414`） | 0.02（`:199`） | − | 0.000（0/199） |
| `terminal` | `±win/loss_reward`，仅当引擎给 `victory`/`defeat`（`:427-434`） | ±1.0 | ± | **0.000 / 0 次非零** |
| `timeout` | `-timeout_penalty`，达到 tick 上限且无引擎裁决（`:465-479`） | 0.20（`:240`） | − | **-0.200 / 199 次非零** |
| `bonus_produce` | `produce_bonus * new_combat`（`:421`） | 0.10（`config.py:212`） | + | **0.000 / 0 次非零** |
| `building_lost` | `-building_loss_penalty * lost_buildings`（`:422`） | 0.30（`config.py:217`） | − | 0.000（0/199） |

**判定：**

1. **符号全部正确**，每个分项的意图都能从注释里读出（`reward_shaping.py:321-391` 的注释质量很高，逐条解释了为什么不能用 hp 差、为什么 `income` 要奖励「增长」而不是「水平」）。这一层没有可挑的符号错误。
2. **`terminal` 0/199、`kills` 0/199、`bonus_produce` 0/199 是结构性死零，不是统计噪声。**
   - `kills` = 0 意味着 **1675 局里没有任何一局打死过任何敌兵**（`kills = 0.25 × 击杀数`，0 即击杀数 0）。
   - `bonus_produce` = 0 意味着 **1675 局里没有出现过任何新的非建筑、非建造者单位**（`bonus_produce = 0.10 × 新战斗单位数`）。这与 eval 里 `own_alive` 停在 5 完全吻合：`指挥中心 + 建造者 + 3 个建筑 = 5`，一个战斗单位都没有。
   - `terminal` = 0 是**可解释的**：`reward_shaping.py:427-434` 只在引擎给出 `victory`/`defeat` 时付钱，而桥日志（`runs/_rwpp_ppo/game-5140-8209.log:148`）末行是 `bridge finished frames=4410 tick=4410 result=timeout` —— 引擎确实没判。这一点与 `docs/P0修复后训练结论.md` §四的 B6 裁决一致（旧的 `_decide_by_army` 启发式已被显式废弃，见 `reward_shaping.py:91-98` 的 `TIMEOUT_DECISIVE_RATIO` 标记为 DEPRECATED）。**「timeout 率 100%」不是 bug，是「我方从没打到能判胜负」的诚实读数。**
3. **塑形确实主导**：`income + bonus_build + strategy = 1.73`，`|potential| = 0.63`、`timeout = -0.20`，剩余所有项合计 `|·| < 0.06`。reward_components 的量级表见 §3。
4. **`timeout` 恒 -0.200 变成了「终局」的唯一代表**。它在每一局末尾精确付一次（`reward_shaping.py:470-479`），是**唯一一个稳定的终局信号**，但它只区分「超时 / 没超时」，不区分「打得怎么样」。
5. **`strategy` 项疑似退化为常数**：`612bdc58` 的 200 个 update 里，该分项的每局均值是 **bit-identical 的 0.246934（distinct=1 / 199 个样本）**，`econ_fix_long` 也是 distinct=1。原因是 `RuleStrategy` 在 189/200 次给出 `intent=defend`，而 `strategy_potential` 的 target 退回到「我方质心」（`rwpp/strategy.py:76-79`：`elif rally:` → `rally_point` 就是 own centroid），于是 ψ 在整局里基本不动。
   > ⚠️ **诚实限定**：`metrics.json` 只记录**每局累计值**，而势函数项在局内会望远镜求和（`Σ = coef × (ψ_T - ψ_0)`）。局累计恒定**不能证明**逐步增量也恒定，只能说它在「局」这个粒度上对策略完全不敏感。要判定它是否提供逐步梯度，必须加逐步埋点（见 §5 待补项 D3）。**不建议在拿到逐步数据前直接删掉它。**
6. **稀疏奖励的课程支撑只有「半个」**：
   - ✅ 有：`RwppGameConfig.opening_extractor = True`（`rwpp/config.py:261`，实现在 `rwpp/env.py:368-384`），在 reset 时替智能体排下第一个矿场。这是**必要**的，因为建造需要约 140 tick 不被打断，而从零随机会把在建工程反复取消（`config.py:244-261` 的实测注释）。
   - ❌ 缺：**「造工厂 → 出兵」这一段没有任何课程**。而且 `opening_extractor` **连一个关闭开关都没有**——CLI 找不到 `--no-opening-extractor`（`src/ironzero/training/train_rwpp.py` 全文没有 `opening` 字样），`rwpp/config.py:259` 的注释却写着「Set `--no-opening-extractor` to disable it and measure the difference」。**注释承诺的 A/B 能力不存在**，所以「课程到底带来多少收益」这件事从来没有被测量过。
   - ❌ `produce_unit` 的掩码在「工厂在建」期间是关的（桥故意报空菜单，`IronZeroBridge.java:854-856` + 注释 L835-853），而 `masks.py:167-168` 又把「只有 builder 的菜单」判为不可生产。两者都是正确的防护，但叠加起来 = 一局里真正能发出 `produce_unit` 的窗口极窄，而 `bonus_produce = 0.10` 是**一次性**奖励（`reward_shaping.py:341-346` 明确排除 builder，防止刷分）。稀疏 + 窗口窄 + 无课程 = 这个动作在本轮 1675 局里**一次都没成功过**。
   - ⚠️ warmstart 通道**存在但在本轮 run 里没被使用**：`--init-checkpoint`（`train_rwpp.py:114-115, 226-246`）、BC 权重（`runs/experiments/bc_ironzero{5,10,15,20,25}/checkpoint.pt` 都在盘上）、服务端解析（`scripts/rwpp_service/ppo.py:337-409`）。但 `612bdc58` 的 `rwpp_summary.json` 里没有 `init_checkpoint` 字段，`train.log` 首行也没有 `"init_checkpoint"` / `"initialized": true` 记录 → 该 run 是**从零 scratch**。

### 2.4 评估口径：N 局、Wilson CI、独立评估集、确定性策略、eval/train 一致性

**结论：❌ 现有评估数字不能支撑任何胜率结论。**

**(a) N 太小，结构上无法证明任何事**

- 训练期评估 `eval_episodes=4`（`rwpp_summary.json` `config.eval_episodes: 4`，L202），`eval_every=20`，10 轮评估全部是 `wins=0 / timeouts=4 / win_rate=0.0`。
- Wilson 95% CI 实现是正确的（`src/ironzero/training/evaluate.py:109-128`），逐局明细也写了（`evaluate_rwpp.py:158-176` → `eval_report.json`）。**这两点是加分项**，优于 `docs/闭环差距分析.md` §2.7 描述的历史状态。
- 但 N=4 时 CI 的宽度决定了它证明不了任何东西：**即使 4 局全胜，Wilson 下限也只有 0.510**（`wilson_interval(4,4) = [0.5101, 1.0]`）。当前 0/4 的 CI 是 `[0.0, 0.490]`。
- 按用户「>70%」的目标反推所需 N（`%TEMP%\an19.py` 复算）：

  | 观测胜率 | 要让 Wilson 下限 > 0.70 所需最少局数 |
  |---:|---:|
  | 75% | **N ≥ 306** |
  | 80% | **N ≥ 77** |
  | 85% | **N ≥ 30** |
  | 90% | **N ≥ 15** |

  （若门禁放宽成「Wilson 下限 > 0.50」即「显著好于抛硬币」：观测 70% 需 N≥21，观测 60% 需 N≥91 —— 与 `docs/闭环差距分析.md` §6.2 的 N≈91 结论一致。）
  **所以「N=4」连「比随机好」都证明不了，更不用说 70%。** 建议把训练期评估最低 N 提到 20（验收评估 N=77–100，见 §5）。

**(b) 不是独立评估集**

- 每一次评估都用 **同一组种子**：`seed = 70_000 + config.seed`（`training/rwpp_ppo.py:92`），再在 `evaluate_rwpp_policy` 里按 `seed + index` 展开（`evaluate_rwpp.py:130`）。
- 实测 10 次评估的 `episode_results[].seed` **全是 `[70000, 70001, 70002, 70003]`**（`metrics.json` → `evaluations[]`）。
- 这意味着 200 轮里所有 10 次评估都在**同样的 4 个种子**上打分。若引擎真的 deterministic，这就是一个 N=4 的固定测试集被反复查询 —— 既没有 holdout，也支持不了「泛化」的说法。
- 而引擎**并不** deterministic（见下条），所以这 4 个种子实际上每轮都在跑不同的对局 —— 于是它既不是固定评估集，也不是随机抽样，而是一个**记录了但不生效的种子**。

**(c) 种子没有注入引擎（历史问题仍在）**

- `RwppDuelEnv.reset(seed=...)` 只做 `self.seed = int(seed)` 和拼 `episode_id`（`src/ironzero/rwpp/env.py:114-118`）。
- 启动命令里**没有任何 `--seed` 参数**：`src/ironzero/rwpp/process.py:65-113` 的 `_bridge_command()` 全文无 seed（我 grep 过，只有 L46 的注释提到 seed）。
- 桥日志里的引擎种子是随机的：同一次评估的三个端口分别打印
  `global Seed: 339105372` / `312311947` / `251557689`
  （`runs/_rwpp_ppo/game-5204-17523.log:138`、`game-5205-17524.log`、`game-5206-17524.log`）。
- 结论：**「同 seed 重跑 = 同一对局」不成立**，`eval_report.json` 里的 `seed` 字段只是标签。

**(d) 确定性策略在 argmax 下退化（新增证据，直接解释「eval 与 train 行为不一致」）**

评估固定 `deterministic=True`（`evaluate_rwpp.py:93`），训练是采样（`training/policy.py:112-115`）。我在 `%TEMP%` 用 `load_policy` 载入 `612bdc58/checkpoint_best.pt`，对 400 条随机观测做前向（全开掩码，= 最宽松的合法集合）：

| 模式 | 不同动作元组 | kind 分布 |
|---|---:|---|
| `deterministic=True`（评估用） | **68 / 400** | `build_extractor 358, move_group 42` |
| `deterministic=False`（训练用） | **333 / 400** | 9 种 kind 都出现，`build_extractor 203 / move_group 80 / noop 46 / produce_unit 22 / attack_move 21 ...` |

`kind` 头平均熵仅 **1.514 nats**（最大 1.951，均匀为 2.303），`build_extractor` 的平均概率 **0.4704**，`upgrade_building` 只有 0.0008。

即：**在评估的 argmax 下，策略有 89.5%（358/400）的动作是「造矿场」**，只在少数状态下切到 `move_group`；采样时才会偶尔碰到 `produce_unit` / `attack_move`。这正好解释了 `docs/P0修复后训练结论.md` §五.2 记录的「同一 checkpoint 在 probe 里 900 步只发 hold」——**不是 hold，是 argmax 塌到一个 kind 上**。评估度量的是一个「几乎只会造矿场」的确定性策略，而训练一直在优化一个分布；两者不是同一个对象。

> 说明：这个实验用的是随机观测而非真实状态，目的是测**策略头对输入变化的敏感度**（=是否塌缩），不是预测实战动作分布。它能证明「argmax 严重偏向单一 kind」，不能证明「实战里 89.5% 都在造矿场」。真实比例的判定需要在实机上加逐步动作直方图（§5 待补项 D3）。

**(e) `best` 的选择规则在 win_rate 恒 0 时退化**

`maybe_save_best` 的排序键是 `(win_rate, mean_return)`（`training/ppo.py:215-228`），`score <= best_score` 时跳过（`ppo.py:242`）。当所有评估 `win_rate` 都是 0 时，排序**完全由 `mean_return` 决定**。而 `mean_return` 的主成分是 `income + bonus_build + strategy` 三项塑形（§3）—— 于是：

- `612bdc58` 的 `best` 落在 **update 100**，`best_eval.mean_return = 1.073`；
- 而 update 100 的 `eval` 是 `own_alive=[5,5,5,5]`、`enemy_alive=[17,15,14,13]`、`timeout_rate=1.0`；
- 也就是说，**「best checkpoint」= 「造矿场造得最勤的那一轮」**，而不是「最会打仗的那一轮」（后者不存在）。

`docs/闭环差距分析.md` §2.8 担心的「保存的是最后一轮而非 best」这个问题**形式上已修**（确实有 `checkpoint_best.pt`，且 `best_update` 被正确记录为 100），但**语义没修**：在没有胜负信号时，任何基于 return 的 best 选择都只是在选塑形项的最大值。

## 5. 算力与时长估算（含完整算式）

### 5.1 实测吞吐锚点（全部来自 `runs/platform/rwpp-ppo-ppo-612bdc58`）

```
配置：updates=200, num_envs=8, rollout_steps=256, eval_every=20, eval_episodes=4
总墙钟                = 2618.25 s                      (rwpp_summary.json L206 附近 total_seconds)
名义决策总数          = 200 × 256 × 8 = 409,600        (ppo.py:271 每 update 采 rollout_steps 次)
  → 决策/秒           = 409,600 ÷ 2618.25 = 156.4 dec/s
  → 决策/小时         = 156.4 × 3600    = 563,185 dec/h
每 update 墙钟        = 2618.25 ÷ 200   = 13.09 s
完成的局数            = 1675                          (sum(updates[].episodes))
  → 局/小时           = 1675 ÷ (2618.25/3600) = 2,303 局/h
  → 决策/局           = 409,600 ÷ 1675 = 244.5
每 env 每局占用       = 2618.25 × 8 ÷ 1675 = 12.51 slot·s
  → 单 env 引擎速度   = 8000 tick ÷ 12.51 s = 640 tick/s
  → 单 env 决策速度   = 244.5 ÷ 12.51 = 19.6 dec/s（在 33 tick/决策 的实际节奏下）
```

**这条链的关键结论**：`156.4 dec/s = 8 envs × 19.6 dec/s`，即**吞吐与 env 数线性相关，单个 env 被引擎钉在 ~640 tick/s**。8 envs 已经是这台机器的实际上限（i5-14400F，10 核 16 线程；`decisions/episode` 从 4 envs 的 480 掉到 8 envs 的 245，就是资源争用的直接读数）。

### 5.2 前提：先扣掉「白扔的样本」

修掉 B-1 之后，同样的墙钟能采到的样本变成：

```
当前：244.5 决策/局（8000 tick，桥应给 800 帧）→ 只消费了 31%
修后：保守取 700 决策/局（留 12% 余量，不假设 100%）
  → 局数/小时不变（引擎决定，2,303 局/h）
  → 决策/小时 = 2,303 × 700 = 1,612,100
  → 决策/秒   = 1,612,100 ÷ 3600 = 447.8 ≈ 448 dec/s（取 450）
  → 相对现状 156.4 dec/s = 2.87×
```

**这一步不花额外的机器，也不花额外的墙钟**（引擎本来就把这 800 帧算出来了，只是被 `session.py` 扔掉了）。代价是 PPO 每 update 多做 2.9 倍的策略前向 —— 511 维输入 × 256 隐藏的 MLP，RTX 4070 上是毫秒级，相对 640 tick/s 的引擎可以忽略。下面所有估算都给「现状 / 修后」两列。

30 M  ÷ 244.5 ≈ 122,700 局
100 M ÷ 244.5 ≈ 409,000 局

### 5.4 墙钟小时（核心算式）

**先明确一个前提**：局数与决策数是两个不同的预算口径，**B-1 只改善后者**。

```
引擎侧（硬约束，不随代码修复改变）：
  单 env 640 tick/s  →  8000 tick 的一局 = 12.5 s slot 时间
  8 envs            →  8 × 3600 ÷ 12.5 = 2,304 局/小时

客户端侧（现状 vs 修 B-1 后）：
  现状：244.5 决策/局 → 2,304 × 244.5 = 563,000 决策/小时 (= 156.4 dec/s)
  修后：700   决策/局 → 2,304 × 700   = 1,612,800 决策/小时 (= 448 dec/s)
```

**主表（按「局数」口径 —— 这是真正的稀缺资源，B-1 不改善它）**

| 档位 | 局数 | **墙钟（现状与修后相同）** |
|---|---:|---:|
| 下限「学会打仗」 | 12,300 | **5.3 h** |
| 中档「能打赢」 | 122,700 | **53.3 h**（2.2 天） |
| 上档「稳定 70%」 | 409,000 | **177.6 h**（7.4 天） |

**副表（按「决策数」口径 —— 若样本预算以决策计，B-1 有效）**

| 档位 | 决策数 | 现状 156.4 dec/s | 修 B-1 后 448 dec/s | update 数（2048/update） |
|---|---:|---:|---:|---:|
| 下限 | 3 M | 5.3 h | **1.9 h** | 1,465 |
| 中档 | 30 M | 53.3 h | **18.6 h** | 14,648 |
| 上档 | 100 M | 177.6 h | **62.0 h**（2.6 天） | 48,828 |

**两表为什么在「下限」档重合、在「中档」档分岔**：下限档的 3 M 决策本就是用现状 245/局折算出来的（`3M ÷ 244.5 = 12,300 局`），所以两个口径必然一致。中档/上档的 30 M / 100 M 是独立取的「训练所需经验量」，若用修后 700/局去消费，同样 122,700 局会产生 8,589 万决策 —— 那时「30 M」这个预算会在 18.6 h 就被超过，但那**不代表提前学会了**，只代表每局看了更多帧。**保守起见请以主表（局数口径）为准。**

**逐步算式（下限档，现状）**

```
3,000,000 决策 ÷ 156.4 dec/s = 19,182 s
19,182 s ÷ 3600              = 5.33 h
对照：本轮最长 run 612bdc58 = 2618 s = 0.73 h
→ 5.33 ÷ 0.73 ≈ 7.3 倍于目前已跑过的最长 run
```

**逐步算式（中档，局数口径 —— 推荐采信）**

```
每局 slot 时间  = 8000 tick ÷ 640 tick/s = 12.5 s
8 envs 每小时局数 = 8 × 3600 ÷ 12.5        = 2,304 局/h
122,700 局 ÷ 2,304 局/h                    = 53.3 h
```

**逐步算式（中档，决策口径 —— 仅在修 B-1 后成立）**

```
2,304 局/h × 700 决策/局 = 1,612,800 决策/h
30,000,000 ÷ 1,612,800  = 18.6 h
（等价：30M ÷ 448 dec/s ÷ 3600 = 18.6 h ✓）
```

**一个必须写下来的判断**：`53.3 h` 与 `18.6 h` 的差距，本质是**「我们到底缺局还是缺步」这个尚未回答的问题**。见 5.6 待判项 2。

### 5.5 横向对比：加 env 的收益为什么打折

`156.4 dec/s = 8 × 19.6`，但**单 env 的引擎速度在两个 env 档位上几乎一样**（这点与直觉相反，值得记下来）：

| run | envs | slot·s/局 | 单 env tick/s | 决策/局 | 占应得帧(800) |
|---|---:|---:|---:|---:|---:|
| `612bdc58` | 8 | 12.51 | **640** | 244.5 | **31%** |
| `8e080d15` | 8 | 12.85 | 622 | 242.1 | 30% |
| `b194f361` | 4 | 12.42 | **644** | 430.3 | 54% |
| `econ_fix_long` | 4 | 14.32 | 559 | 480.0 | 60% |
| `econ_fix_verify` | 4 | 18.30 | 437 | 512.0 | 64% |

（`slot·s/局 = total_seconds × envs ÷ episodes`；`tick/s = 8000 ÷ slot·s`；应得帧 = `8000 tick ÷ 10 tick/帧 = 800`。）

**修正一个我最初写错的判断**：env 数 4→8 **并没有**让单 env 引擎变慢（`b194f361` 644 tick/s vs `612bdc58` 640 tick/s，基本相同）。真正的差别全在**观测消费率**：4 envs 时能吃掉 54–64% 的帧，8 envs 时只吃掉 **30–31%**。

**所以这台机器加 env 是「赚的，但赚得打折」**：

- **局数/小时**：4 envs ≈ 1,005–1,160 局/h → 8 envs ≈ 2,241–2,303 局/h，**≈1.9–2.0 倍，接近线性**（引擎不是瓶颈）；
- **每局学到的决策数**：从 ~480 腰斩到 ~245（客户端消费不过来）；
- **净效果**：`决策/小时` 从 482k–499k 只涨到 542k–563k，**+12~17%**，远低于 env 翻倍应有的 +100%。

这就是 B-1 的价值：修掉丢弃后 8 envs 的 `决策/小时` 应变成 `2,303 局/h × 700 = 1,612k`，是现状的 **2.9 倍**，且**不增加任何墙钟成本**（引擎本来就把这 800 帧算出来了）。

同时它也说明：**继续加 env（16/24）在这台机器上收益会更差**，因为瓶颈本来就在消费侧而非引擎侧。**加 env 之前必须先修 B-1。**

要真正提速只有两条路：
1. **修 B-1**（免费，+2.9× 有效样本）；
2. **提高单 env 引擎速度**：`process.py:40-62` 的 `effective_frame_ms` 把 `frame_ms<1` 钳到 1，理由是「0 ms 会让引擎用零步长推进、改变战斗结果」（注释里有实测：同一策略同一种子在 0ms 输、1ms 赢）。而 `physics_ms=16` 已经把仿真步长钉死（`rwpp/config.py:172`），所以 `frame_ms` **理论上**可以继续往下压而不改仿真 —— 但 `effective_frame_ms` 仍拒绝 <1。这需要一次单变量实测确认（`--frame-ms 0` + `--physics-ms 16` 是否真的安全），**不能直接改**。`runs/_rwpp_perf/a_frame0_1x40.json` 记录的 `frame_ms=0 → 6453 tick/s`（vs `frame_ms=1 → 472 tick/s`）**不能当证据**：那份 bench 没有同时钉 `physics_ms`，测的是另一个仿真。
3. **缩短 `episode_ticks`**（若瓶颈是局数而非步数）：`train_rwpp.py:43-47`、`rwpp/config.py:110` 允许传显式值；把 8000 砍到 3000–4000 可让每小时局数翻倍。**这是一个待验证的实验，不是既定结论**（见 5.6 待判项 2）。

### 5.6 估算里必须承认的 3 个未定项

1. **「需要多少样本」是外推，不是测量。** 见 5.3 的可信度列。任何低于 3 M 的估算都在暗示「当前 0.41 M 已经接近」，而 `kills` 恒 0 直接否定了这一点。
2. **「局数 vs 决策粒度」哪个是瓶颈，未判。** 如果瓶颈是局数，必须缩短 `episode_ticks`（5.4 末尾）；如果瓶颈是决策粒度，必须修 B-1。**建议第一个实验就是同时跑这两个变体各 50 update，看 `kills` 是否脱离 0** —— 这是整个项目最便宜、信息量最大的一个实验（每个变体约 11 分钟）。
3. **评估成本没算进主表。** `eval_every=20` / `eval_episodes=4` 时，10 次评估共 **126.8 s**（`metrics.json` 的 `evaluations[].elapsed_s` 求和），占 2618 s 的 **4.8%**。若按 B-3 把 N 提到 16，评估开销约 4 倍 ≈ 507 s = **19%** —— 这已经不可忽略，训练时长的估算要相应上浮。
   验收评估（N=77）成本另算：`evaluate_rwpp_policy` 按 `parallel=episodes` 起线程（`evaluate_rwpp.py:129,152-156`），但 `RwppPPOTrainer._reserve_eval_ports` 的端口池只有 16（`rwpp_ppo.py:44` `EVAL_PORT_POOL = 16`），且 `max(1, num_envs)` 已经打满 8 个进程。**实际并发会退到 ≤16**：
   ```
   单个游戏进程独占时 8000 tick ÷ 640 tick/s = 12.5 s
   N=77、并发 16  →  ceil(77/16) = 5 轮 × 12.5 s = 62.5 s（理想）
   但在 16 并发下客户端消费率会更低（8 envs 时已只有 31%），
   保守取 2 倍膨胀 → 一次 N=77 验收评估 ≈ 2–3 分钟
   ```
   **这个成本可以接受**，而且远好于「用 N=4 得出一个什么也证明不了的结论」。
